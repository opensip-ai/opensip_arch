# Fallow broadens analysis; OpenSIP strengthens trust

**Yes: current Fallow does several useful things better than our fully implemented design**, particularly JS/TS framework coverage, frontend analysis and editor feedback. OpenSIP's strongest advantages are trustworthy policy decisions, retained evidence, regression attribution and controlled repair, plus native Rust analysis. The biggest OpenSIP gaps worth addressing are framework/component coverage and the deliberate limits on large default analysis requests; editor integration follows closely. Specialized complexity, style, public-API and security analyses deserve individual product decisions. Much of Fallow's general workflow was already incorporated into our design, so baselines, audit, graph queries, agent support and review briefs are not missing foundations. ## Fallow answers more frontend questions immediately

Fallow's strongest practical advantage is **application recognition breadth**. Its registry covers Astro, Angular, Nuxt, SvelteKit, NestJS, Electron, React Native and many build/test tools. Registry tests assert more than 100 plugin names, although that count includes tooling integrations rather than 100 equally deep framework analyzers. OpenSIP selects nine recognizers: node-package, typescript-config, npm-workspaces, pnpm-workspace, cargo-package, cargo-workspace, nextjs, vite and vitest-jest. An unknown framework leaves origins unrecognized and universal-negative reachability incomplete. That is honest behavior, but compiler-quality symbol binding cannot recover application entry points that the product never recognizes. Framework expansion is consequently a capability gap even under full implementation. ([Fallow registry](https://github.com/fallow-rs/fallow/blob/1b1b9dd6d5015f77cf911887c2e9a1d0f4256e5c/crates/core/src/plugins/registry/builtin.rs#L5), [registry check](https://github.com/fallow-rs/fallow/blob/1b1b9dd6d5015f77cf911887c2e9a1d0f4256e5c/crates/engine/src/plugins.rs#L102), [OpenSIP recognizers](</Users/sb/code/opensip-ai/opensip_arch/docs/v2/contracts/product-v1/native-evidence.md:2754>))

Fallow also asks concrete maintainability questions our selected contracts do not yet answer. It implements cyclomatic/cognitive complexity with contribution spans, React context, template complexity for Angular/Vue/Svelte/Astro, and CSS analytics spanning design tokens, class references, duplicate declaration blocks and CSS-in-JS. Its template scanners are not full framework compilation; its cognitive metric includes product-specific React adjustments. OpenSIP's bundled code grammars cover Rust, TS and JS, and its native table does not select equivalent complexity or component/style relations. We should choose useful metrics and explain their contributions before adopting an aggregate health score. ([Complexity](https://github.com/fallow-rs/fallow/blob/1b1b9dd6d5015f77cf911887c2e9a1d0f4256e5c/crates/extract/src/complexity.rs), [templates](https://github.com/fallow-rs/fallow/blob/1b1b9dd6d5015f77cf911887c2e9a1d0f4256e5c/crates/extract/src/template_complexity/mod.rs), [CSS analytics](https://github.com/fallow-rs/fallow/blob/1b1b9dd6d5015f77cf911887c2e9a1d0f4256e5c/crates/engine/src/health/css_analytics/mod.rs), [OpenSIP grammar set](</Users/sb/code/opensip-ai/opensip_arch/docs/v2/contracts/product-v1/native-evidence.md:260>), [native matrix](</Users/sb/code/opensip-ai/opensip_arch/docs/v2/contracts/product-v1/native-evidence.md:584>))

Two further specializations merit attention: public-signature type coupling/API leakage, and source/sink security candidates with external-verifier joins. Fallow implements both. The security analysis explicitly generates syntactic candidates rather than proving taint flow, and type coupling remains advisory. These are gaps in selected analyzer families, not evidence that OpenSIP lacks general graph impact or extensibility. General graph/path/reach queries already overlap; the additional value is a ready-made answer to a specific engineering question. ## Editor feedback and request capacity deserve priority

Fallow supplies a concrete LSP/VSCode experience: diagnostics, hovers, quick fixes, export/complexity code lenses and analysis trees. Its analysis uses disk state, with document versions and exact disk/buffer comparisons to suppress stale results. Scheduling coalesces changes while limiting cancellation starvation. OpenSIP's typed agent/query surfaces do not provide this editor lifecycle, and speculative buffer overlays are explicitly parked. A snapshot-backed LSP projection would give immediate value; unsaved-buffer analysis needs its own advisory contract and safe handoff to existing repair authority. ([LSP capabilities](https://github.com/fallow-rs/fallow/blob/1b1b9dd6d5015f77cf911887c2e9a1d0f4256e5c/crates/lsp/src/server_capabilities.rs#L8-L29), [buffer state](https://github.com/fallow-rs/fallow/blob/1b1b9dd6d5015f77cf911887c2e9a1d0f4256e5c/crates/lsp/src/document_state.rs#L1-L45), [scheduler](https://github.com/fallow-rs/fallow/blob/1b1b9dd6d5015f77cf911887c2e9a1d0f4256e5c/crates/lsp/src/schedule.rs#L1-L37), [OpenSIP surfaces](</Users/sb/code/opensip-ai/opensip_arch/docs/v2/contracts/product-v1/workflows-and-surfaces.md:1089>), [parked overlays](</Users/sb/code/opensip-ai/opensip_arch/docs/coop/architecture/08-surfaces-and-topology.md:355>))

The most consequential capacity issue is **94 selected TS units under the default request exceed the 1,024 requested-capability bound**: eleven capabilities per unit yield 1,034 rows, while 93 units yield 1,023. The request refuses with `PROJECT.SCOPE_LIMIT` before Plan/Run. This means units, not 94 files: marker directories and language families determine units; Cargo workspace members fold into a workspace program unit. Narrower roots or fewer requested capabilities can fit, but narrow the analysis. Automatic sharding and raising limits are explicitly unselected capabilities. Additional bounds include 128 native contexts and 256 imports. These are documented resource decisions, yet still a significant product gap for large monorepos. Revisit the bounds and whole-workspace orchestration together; independent shards can miss cross-unit consumers. No measured Fallow capacity advantage is asserted here. ## OpenSIP makes uncertainty and regression accountable

OpenSIP's completed design is stronger when findings become policy decisions. Compiler-bound TS identities and Rust-native universes bind source, dependencies, toolchain and prepared inputs. Exhaustive examination is separate from complete edge resolution; dynamic loading, unknown consumers and dispatch remain explicit uncertainty. Universal negatives require complete admitted populations, and the pure evaluator retains a full predicate tree with three-valued logic. Retained inputs support independent replay rather than trusting a producer's PASS flag. This is a stronger enforcement contract, not proof that OpenSIP finds more bugs. ([Native semantics](</Users/sb/code/opensip-ai/opensip_arch/docs/v2/contracts/product-v1/native-evidence.md:584>), [completeness](</Users/sb/code/opensip-ai/opensip_arch/docs/v2/contracts/product-v1/native-evidence.md:1878>), [evaluation and replay](</Users/sb/code/opensip-ai/opensip_arch/docs/v2/contracts/product-v1/identity-and-evidence.md:1489>))

The clearest comparison difference is what happens when semantic identities cannot be compared. Fallow explicitly falls back to syntactic audit keys and demotes semantic-only introductions so they cannot fail a new-only gate. OpenSIP keeps missing required comparison evidence indeterminate and separates code, detector, policy, scope, waiver and evidence changes. Its portable baseline carries the prior detector closure, permitting old-detector/current-source pivots; disabling a rule cannot silently make a newly introduced problem look fixed. There is a deliberate limitation: changing observational import identity does not supply an old-source/new-observation counterfactual pivot. That remains a scope decision requiring additional comparison semantics if desired. ([Fallow fallback](https://github.com/fallow-rs/fallow/blob/1b1b9dd6d5015f77cf911887c2e9a1d0f4256e5c/crates/api/src/audit_keys.rs#L92-L133), [OpenSIP baseline](</Users/sb/code/opensip-ai/opensip_arch/docs/v2/contracts/product-v1/workflows-and-surfaces.md:257>), [multi-axis attribution](</Users/sb/code/opensip-ai/opensip_arch/docs/v2/contracts/product-v1/workflows-and-surfaces.md:330>), [observational limitation](</Users/sb/code/opensip-ai/opensip_arch/docs/v2/contracts/product-v1/workflows-and-surfaces.md:1640>))

## OpenSIP controls edits more rigorously

Fallow has real fix safeguards: staged writes, content/path revalidation and conservative type-aware negative decisions. Its inspected promotion loop nevertheless persists files individually and records partial failures; earlier writes can remain if a later promotion fails. Its MCP preview/apply calls also recompute using options rather than carrying an immutable preview-plan identity. OpenSIP binds approval to exact preview bytes, source/evidence/recipe identities and authorization; journals apply states, restores already-renamed targets on failure, handles crash recovery explicitly and verifies a fresh snapshot. These stronger guarantees matter when agents propose multi-file edits. ([Fallow write promotion](https://github.com/fallow-rs/fallow/blob/1b1b9dd6d5015f77cf911887c2e9a1d0f4256e5c/crates/cli/src/fix/plan.rs#L221-L275), [MCP fix handoff](https://github.com/fallow-rs/fallow/blob/1b1b9dd6d5015f77cf911887c2e9a1d0f4256e5c/crates/mcp/src/tools/fix.rs#L1-L66), [OpenSIP preview](</Users/sb/code/opensip-ai/opensip_arch/docs/v2/contracts/product-v1/workflows-and-surfaces.md:707>), [apply/recover/verify](</Users/sb/code/opensip-ai/opensip_arch/docs/v2/contracts/product-v1/workflows-and-surfaces.md:1008>))

OpenSIP additionally keeps ordinary analysis within host-owned authority: no implicit config execution, downloads, hooks or ambient evidence, and Rust build scripts/procedural macros require inert preparation or disclosed unavailable results. Imported observations require source correspondence and cannot independently establish universal non-use. Rust-native analysis is itself a substantive scope advantage over Fallow's JS/TS focus. The narrower signed first-party extension model is a deliberate safety/distribution tradeoff. ([Admission boundary](</Users/sb/code/opensip-ai/opensip_arch/docs/v2/contracts/product-v1/admission-and-qualification.md:337>), [Rust preparation](</Users/sb/code/opensip-ai/opensip_arch/docs/v2/contracts/product-v1/native-evidence.md:2497>), [import semantics](</Users/sb/code/opensip-ai/opensip_arch/docs/v2/contracts/product-v1/workflows-and-surfaces.md:473>))

## Conclusion

Prioritize recognition/component coverage, capacity semantics and editor feedback, then select specialized analyzers using target-repository evidence. Preserve OpenSIP's existing authority model while borrowing Fallow's concrete questions and interaction details. The earlier borrow register already covers general baselines, audit, review, deterministic output and evidence workflows; repeating those as gaps would compare against obsolete scope. Source inspection does not establish comparative speed, accuracy or productivity, and full implementation alone does not supply those measurements.
