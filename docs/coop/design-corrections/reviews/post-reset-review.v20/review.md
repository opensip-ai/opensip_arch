On public routes rather than helper claims: `adopt_baseline` is the named public caller and reaches the verifier **only** when a retained analysis spec is supplied. With `analysis_spec=None` the docstring states plainly that the digest assignment is a record of what was passed and not evidence of selection. ## 3. The one new SHOULD

**NEW-SHOULD-1 — a claimed precedence that no control discriminates.**

`workflows_model.v1.py:689-696` argues at length that the at-most-one guard must run *before* the payload comparison, and `check-identity.py:1364` is named `the-scope-binding-verifier-refuses-an-ambiguous-selection-before-any-digest-match`. But both existing controls supply a document that **is** one of the two candidate rows, and for those inputs the guard-first and match-first orderings both yield `CONFIG.INVALID`. Neither control discriminates the ordering it is named after.

The discriminating input is an ambiguous spec plus a document that is **neither** candidate:

| ordering | outcome |
|---|---|
| shipped (guard first) | `CONFIG.INVALID` / `CONFIG.INVALID` |
| reordered (match first) | `REQUEST.PRECONDITION_FAILED` / `BASELINE.SCOPE_PARAMETER_DIGEST_MISMATCH` |

That is the *only* input where the ordering is observable, and it is absent from the suite. I moved the guard to after the payload match and `check-identity.py` still passed at 1592/0 against a passing unmutated control.

To be precise about severity: the shipped ordering is **correct**, and the specific harm the prose names — obtaining a `verified` digest under an ambiguous spec — *is* covered, because deleting the guard outright was detected. What is unpinned is the weaker diagnostic-precedence property. This is a control-evidence defect, not a design defect, so it is a SHOULD. It matters because the review standard applied to this candidate is that tests must really contain competing faults where precedence is claimed, and the native unit already meets exactly that standard with `cb8-unregistered-capability-outranks-the-ownership-tuple-rule`. The remedy is one negative vector.

## 4. The preserved complete design around the changes

A correction review is only as good as its check that nothing *else* moved, so I read the surrounding design rather than only the twelve changed files. The five product contracts and their index still read as one intended product: one host owning discovery, admission, authority, orchestration, evaluation, evidence storage and output; language analyzers contributing facts and Coverage through versioned protocols; a pure evaluator; and only an authoritative analysis sealing a source-bound Run.

Zero-config discovery, capability selection and configuration remain coherent with the tuple change. Discovery still prunes installed dependencies and refuses a real capability typed rather than silently degrading, and the boundary inventory joins security discovery to native unit discovery — both are covered by named invariant sweeps rather than single cases. The defaulted selection path is judged by exactly the same pre-Plan boundary as a configured one, which is what makes the guard-first/schema-first distinction a routing detail rather than two different laws.

Native ownership and clone progression are untouched by the RC-6 work and remain self-consistent: clone ownership disclosure is derived from committed ownership plus the scope's own subjects and the universe edition map, missing ownership yields `BODY_LANGUAGE_OWNERSHIP_REQUIRED`, and ambiguous Rust compilation ownership stays an honest `unknown` rather than being coerced. That is precisely the case RC-6 must not break, and the implication-not-equality shape is what preserves it. The native corpus carries roughly 26 TypeScript, 19 clone, 28 import and 16 coverage vectors alongside the tuple and RC-6 additions, so the new laws sit inside an existing body of evidence rather than replacing it.

Static, runtime, test, history and import evidence keep one closed payload registry: runtime, test and history admit only workflow payloads, with native adapters normalising their grammars *before* import, while dependency and prepared inputs admit only the native payload domains. Deterministic typed identities and closure are unchanged in shape — 32 registered domains, `wid`-minted identities recomputed rather than trusted from callers, and closure admission that recomputes each typed identity. Changed-code and baseline behaviour keeps its own joins: baseline entries stay sorted and unique by fingerprint, `verify_baseline_artifact` recomputes `baselineId` from the descriptor, legacy fingerprints migrate identity only, and custody records retention pins.

Invocation, repair, replay and error surfaces are exercised across 45 commands, 43 goldens, 34 comparison cases and 32 invocation cases, with four declared boundaries. Authorization and availability are carried by the security unit's 456 cases and ten invariant sweeps, weighted toward root chain (65), lease (31), transition journal (29), repair (16), revocation (15) and trust (15) — including a sweep asserting that the public domain details are a closed, fully registered set, which is the same property V20-ROOT-3 repaired for the two baseline-scope names. Availability composes per step rather than as one flat invocation-wide array, so two admitted 1023-request steps produce 2046 notices without truncation, and the collection is advisory in every carrier: it terminates nothing, mints no Coverage and grants no repair authority.

I reused unchanged evidence only where I had verified source identity — every file I relied on was hash-checked against the manifest, and the reference reports regenerate byte-identically — and I have stated the scope honestly where it is narrower than it looks.
