# Root design tradeoffs — pending actual Grok proposal

No option is selected; this is root preparation, not new blind-consumer input or accepted design.

Preserve inventory file/path and package/name+manifest identities, unary source occupancy, existing symbol identity, exact producer and selected-input custody, and immutable historical profile interpretation. Removing advertised support does not meet the product intent.

A typed sidecar projection can preserve opaque native payloads but requires a concrete trusted provider-output capture, exact kind/path/name/manifest mapping joins, selection and ambiguity rules, a new incoming compare law, graph projection changes and explicit unknown behavior when mapping is absent. Retaining unconditional payload-native-ID-first comparison for file/package subjects would fail to fix the gap. Missing projection cannot become a known nonmatch merely because raw opaque and portable strings differ. Symbol positive/negative comparisons and trusted external attribution should remain coherent.

A kind-discriminated target identity in the import payload may be smaller: retain portable inventory identities and let resolved imports carry the correct file path, package name or symbol identity under a closed field grammar and explicit cross-kind admission. That changes native payload schema/profile and affected fact preimages but avoids a second identity mapping for ordinary first-party targets. Assess whether providers need to preserve a separate opaque raw file/package ID, or whether the provider facade can directly emit the declared portable identity. Do not conflate provider extraction truth with host-verifiable identity joins.

Both require exact version/digest profile handling so old frozen Runs are not silently reinterpreted. This preimplementation repository does not require fictional deployed migrations; preserving the old checker/schema or explicitly refusing unsupported old profiles is different from retroactively changing old IDs.

Positive incoming file/package targets do not automatically create file-to-file multi-hop import graphs: importer remains a symbol kind, while a file target is a different vertex. Do not invent an alias between a module symbol and its file. Current raw graph projection promises must be assessed as published; the erroneous two-hop claim in a consumer example is an example issue, not an automatic new architecture requirement.

Required correction controls include ordinary file and package known positives, duplicate package names with explicit manifest disambiguation, symbol behavior, external targets, absent/unresolved/ambiguous mapping, conservative incoming negative outcomes, and query endpoint identity/evidence selection consistency. A full false-none counterexample must actually admit all prerequisites before being called a measured Run failure; P4 C14 did not do that.
