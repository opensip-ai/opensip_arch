# Asset build enumeration and verifier integration trial

Candidate02 after actual review01; new bytes pending delta review. This provides the build-side real filesystem enumeration missing from the accepted asset verifier unit. It does not build the actual browser report, publish a release, compile a product HostAssetPin or select a production build channel. fixtures/release/report contains three explicitly labelled synthetic files, used only to test interoperability.

The pure build helper takes a retained trusted asset-root directory descriptor, an exact explicit release-relative role map, supported projection schema digests and the build channel. It visits every directory entry, refuses any symlink/nonregular entry without following it, streams each regular file through SHA256, and returns the exact canonical private manifest bytes plus private HostAssetPinV1 data. A prior manifest is excluded only by exact path; a directory or symlink at that path refuses. An unlisted regular file, missing declared member, unknown role or undeclared manifest alias refuses. No extension/hidden-file filter silently omits files. The helper does not write the tree or read a package manager/network. Caller build custody supplies the root handle and admits schema digests; the returned pin record is build data, never a file the runtime may treat as authority.

The selected trial build namespace is lowercase ASCII path segments, starts with a letter/digit, then letters/digits/dot/underscore/hyphen, no trailing dot, at most 255 bytes per segment, 4096 for a release-relative path and 16 path segments. This narrower private output namespace eliminates casefold and Unicode normalization aliases without changing the public LogicalPath or generic verifier grammar. All paths, including directories and the sole manifest, obey it. The manifest is a direct member of the chosen asset root for this build profile. Future asset pipelines needing other names must explicitly revise the profile, not silently normalize filenames. Roles are supplied explicitly, not inferred from extensions.

Trial build caps are 16 supported projection digests, 4096 files, 4096 directories, 16 MiB per member, 4 MiB manifest and 32 MiB aggregate member-plus-manifest bytes. These are root-selected build limits pending review and actual browser bundle measurement, not runtime/performance qualification. Reads are streamed and size-bounded; JSON manifest allocation and directory listing happen before their final size/count checks, under a quiescent trusted build tree. This is not a malicious filesystem resource sandbox. Oversized build inputs fail before returning a pin, never truncate. The runtime must still enforce its accepted 4 MiB manifest profile and exact compiled member sizes. The observed sample is 648 manifest bytes + 151 member bytes, which is fixture sizing only.

File/parent inode comparisons and before/after size/mtime/ctime detect observed replacement or writes. They are not an atomic snapshot or proof against malicious same-process/concurrent writers. Actual build custody must quiesce or retain the selected immutable inputs and publish the manifest/assets together; load-time independent digest verification remains required. Empty directories are permitted because the private manifest inventories regular file bytes; release assembly separately owns directory/delivery nodes.
