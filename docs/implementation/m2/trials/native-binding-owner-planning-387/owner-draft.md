## Where the five-field value comes from

A native StoreGenerationBindingV1 is the canonical derived view `{schemaVersion:1,namespaceId:N,storeInstanceId:S,storeGeneration:G,stateSchema:K}` under admitted owners. It is not a separately stored sixth metadata file. The durable inputs and their authority are:

- N: the one registry/root/project-marker admission, never caller fields, cached ProjectId matching or a directory census. The same N feeds leases, journal, witness, high-water and ledger paths. ProjectId remains a distinct identity and never replaces N in the five-field record.
- Selected S: the actually opened selected store's immutable marker, compared with the admitted installation selection. For a specifically authorized retained-store operation, use THAT opened store's marker and the operation's exact retained full-triple selection; never today's selection or a numeric pair search.
- G/K: the independently captured, full-key-joined immutable lineage node admitted to a complete component chain. The selected pair locates the node; the node's own exact G/K, S and admitted predecessor chain must independently agree. S alone, copied pair fields, a caller's node value or a matching digest cannot supply this owner. There is no fallback if the node or any required predecessor is absent, unreadable, contradictory or over budget.

The selected core closure must also be independently admitted and support that store schema through its existing core/profile owner. Current C.store is a separate three-field comparison against the admitted store binding, never the sole source of G/K or a substitute for N/root/registry/lineage admission. Admitting a binding establishes operational identity only; it does not prove current trust, authoritative execution, a committed receipt, ledger validity or permission to write. The ordinary current-authority facade must still complete its own current/census/original-history/clock/revocation/custody duties.

The canonicalizer is the existing product-profile implementation; no second hand-assembled serializer. The digest is raw SHA-256 over those exact five canonical fields, not a framed product H identity. Generic N remains1..4096characters in the unchanged schema; this native profile only obtains canonical UUIDv4 N from the registry. SchemaVersion1 and field order normalization retain the existing digest recipe; unrelated metadata never enters it.

## Intermediate lineage is not an open store

The current S9.3 phrase 'every lookup ... instance component is read from the store-root marker of the store concerned' is clarified prospectively as an ENDPOINT rule. To enter a chain through a physically selected/opened store, obtain its S from that store's admitted marker. Once an admitted node names its predecessor FULL triple, follow that immutable node key directly. Do not inspect, enumerate or require any intermediate `stores/S` root or marker merely to traverse ancestry. Nodes live outside stores and remain retained after store reclamation; their own complete custody/schema/key/chain checks remain mandatory.

Thus a selected Y→historical X chain can remain readable after X's store bytes are lawfully reclaimed. Missing X's NODE still makes the chain unavailable. A node for a physically missing X is historical evidence, never a usable rollback target or store-data handle. Actually re-selecting/opening X requires its real retained store and readable exact marker plus all original transition/current/floor requirements. A different store with equal numeric G/K off the verified chain never qualifies.

An explicit store-root observation is three-way: readable exact marker; positively observed missing store ROOT through its retained parent/name; or present-but-unreadable marker. A missing marker LEAF alone is not a missing store root. Inaccessibility or an unperformed observation is not absence. No automatic create, repair or quarantine follows a generic read error.

## Creation and transition sequencing

A first-current record cannot serve as the independent G/K source required to create itself. Creation is a distinct typed act. For an authorized forward transition, G/K come from the independently admitted ORIGINAL intent target, with freshly allocated S and the exact registry/lease scope required by that transition. The store trust capsule is INSTALLATION/store-scoped and its binding has three fields, not N; an empty freshly installed registry need not contain any project. For initial installation or independently authorized restore/adoption outside a transition, G/K come from that act's admitted initial/restored declaration, with fresh S. No invented transition intent/journal/origin digest. An installation/store creation context must not invent N or require a five-field per-project binding to create an install-level three-field C.store. The current CreationStoreBindingV1 explicitly fixes G=0; other root/restore acts must use their own concrete admitted typed declaration, not weaken that creation schema or invent an intent. The five-field view is formed only when a real namespace is admitted. Root predecessor and origin are null together, and copied source S is replaced before first publication; no imported local authorization or floor authority.

This creation context permits ONLY the publication steps authorized by that enclosing act, not ordinary existing-store admission. It cannot serve as a fabricated already-existing lineage node or bypass complete initial trust-census/capacity/predecessor-durability obligations. Failed ordinary reads never enter this creation path. Exact root/forward publication order still needs a concrete selected owner before native creation is implemented.

S9's owner recovery decides first. REFUSE/BUSY/QUARANTINE yields no companion marker reads or mutation. Where recovery inspects a current transition, its from/to endpoint marker obligations remain phase-bound: original source required; an early/aborted forward target can be positively absent; settled committed selection requires the real selected target. Only a forward transition creates a node, after durable COMMITTED and selection publication, before DONE/terminal slot retirement. Same-store and ancestor re-selection validate retained nodes and never overwrite their original origin or predecessor. Exact existing node bytes are idempotent only after full chain admission, not a shortcut.

All full-triple nodes in the traversed component must be shape-correct, key-equal to their actual location, null predecessor/origin together or nonnull together, non-self, acyclic and terminating at exactly one root for THAT component. Multiple authorized root components may coexist. Repeated intent digests are not collisions or lookup keys. G is not a monotonic counter; rollback can select an earlier G including0. Nodes and all referenced ancestry are retained independently of store GC; there is no generic node deletion in this profile.

## Budgets, failures and limitations

Complete traversal is iterative and bounded by the authoritative operation's shared object/edge/byte budget; private caller max_nodes is merely an additional engineering cap, not that budget. Exact full-key lookups avoid directory census. Charge before reads/allocations as required by the actual shared-budget owner; retain and recheck every observed node. A limit yields incomplete/unavailable, never 'no ancestor exists', a partial binding or permission to repair. Misbound/contradictory nodes follow the enclosing operation's existing contradiction route; ordinary read-only evidence unavailability is not automatically transition quarantine.

No cryptographic attestation of arbitrary filesystem history is claimed. Custody, cooperative trusted publisher protocol and complete operation admission remain assumptions; coherent whole-installation substitution/rollback has the previously disclosed detection limits. A checksum, immutable-looking path, ancestry graph or pure model result is not an authorization root. A native binding alone does not authenticate any ledger receipt, journal association, cross-generation lookup, original evaluation time or imported authority.
