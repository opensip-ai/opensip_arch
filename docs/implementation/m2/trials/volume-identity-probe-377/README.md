# Volume UUID ABI probe377

Read-only private exploration for owner question376, not product source, admission, qualification, authority or a proposed schema. A fresh nested directory under the native user TMPDIR and the mount root discovered through its original descriptor fstatfs both returned40-byte fgetattrlist frames for RETURNED_ATTRS + VOL_INFO|VOL_UUID. Returned masks were common RETURNED_ATTRS, volume UUID, and other masks zero. Both returned the same nonzero UUID and device/FSID; device/inode/FSID comparisons were stable during these calls. This is one host/run; there was no reboot/remount, duplicate-volume/clone/collision experiment or full custody/metadata sampling.

The SDK manpage lists EINVAL for volume requests not rooted at a volume. This local successful nested-directory call does not establish portable support. Any future native implementation must handle unsupported/missing/invalid attributes honestly and require explicit profile qualification. The discovery root pathname in this probe is not an authority source. The original-directory call may avoid a mount-root pathname dependency on this qualified behavior, but its complete protocol remains undesigned/unreviewed. UUID observations cannot prove unforgeable history, original repository continuity or absence of a cloned volume. Linux requires its own genuine native and supported-filesystem design; no fallback has been invented.

Probe prints raw frames even when calls fail and does not act as a production decoder. Results establish ABI feasibility only. The temporary fixture was removed by its creating process. No product/registry/owner mutation occurred.
