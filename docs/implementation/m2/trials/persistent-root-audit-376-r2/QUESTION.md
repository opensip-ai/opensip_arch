# Persisted native device numbers — owner review question376

Root identified a possible availability/design gap before native registry reuse is implemented. This is not proof of unsound admission or a deployed defect; source codec373 correctly implements the selected schema. No owner/source change is selected here.

Selected NativeProjectRootV1 persists platform/path/deviceId/inodeId/birth. Registry admission requires exact root equality; native incarnation includes deviceId. The selected reference produces MATCHED_ACTIVE for its original root and CONTRADICTION if only deviceId changes while ProjectId, marker, canonical path, inode and birth remain equal. The original path is still present, so the explicit move rule (old locator positively absent) cannot repair this ordinary same-path case. counterexample.json records this conditional reference case; it is not an executed reboot/remount.

Primary evidence to review:

- GNU C Library manual, Attribute Meanings, says st_dev need not stay consistent across reboot/system crashes. Search-accessible official snapshot: https://snapshots.sourceware.org/glibc/trunk/2024-12-11_22-12_1733955121/manual/libc.pdf (printed page437). The current GNU/sourceware HTML endpoints failed to fetch in this session, so do not claim them fetched.
- Installed macOS SDK CoreFoundation CFURL.h, kCFURLVolumeIdentifierKey comment (lines831-832), explicitly says its volume identifier is not persistent across system restarts; kCFURLVolumeUUIDStringKey (1090-1091) supplies a persistent UUID when available. This is NOT by itself proof that that CF value is exactly st_dev; that mapping requires independent verification. Apple online volumeUUIDString documentation confirms the persistent/optional UUID distinction: https://developer.apple.com/documentation/foundation/urlresourcevalues/volumeuuidstring .
- Current filesystem observer already describes f_fsid as an operation-scoped mounted-filesystem ID, not a persistent UUID. Replacing stored st_dev with f_fsid alone would not resolve this.

Questions for actual peer: Is a durable registry rooted in the raw native device number compatible with legitimate restart/remount of supported profiles? Does an already selected owner supply an explicit safe same-path rebind? If not, define the smallest owner correction BEFORE native reuse is built. Options to evaluate include a qualified stable volume identity in durable root records plus volatile device/FSID only for live handle checks, or a separately authorized rebind protocol with independently proved continuity. Neither raw numbers nor same marker/caller flags may become proof, and no silent read-time repair/auto-adoption or destructive move workaround is acceptable. Persistent-volume support may itself require an explicit platform/FS gate, complete descriptor-native acquisition, clone/collision handling and updated schema/model/codec reviews. Do not invent a new CLI command or assume a UUID proves unforgeable history.
