## Exact carrier

The sole registry is `I/project-registry.v1`, relative to the admitted installation-root descriptor under the lifecycle fence. The proposed `lifecycle.sqlite` ProjectId-registry locator is superseded for this role only; journal/ledger SQLite owners are unchanged. No duplicated authoritative registry row lives in SQLite or a cache.

The file is product-canonical JSON, maximum 4,194,304 bytes before parse, maximum depth32 and maximum4096 entries. No truncation, extra members, duplicate keys, floats/exponents, -0, invalid UTF-8 or surrogate values. Re-encoding must equal the exact input bytes. Bounds are this new native resource policy, not claims about typical repository counts or performance. The generic S9 NamespaceList schema remains maxItems65536; this native profile intentionally refuses the4097th registry row despite that larger generic schema allowance. It neither relabels4096 as the generic maximum nor widens any parser silently.

Closed envelope: `{schemaVersion:1, entries:[Entry...]}`. Entries are strictly increasing by namespaceId's raw ASCII bytes. Each closed Entry has exactly:

- `projectId`: `prj1-` plus64 lowercase hexadecimal digits.
- `namespaceId`: canonical lowercase UUIDv4, including RFC variant; a locator, not a credential.
- `root`: the closed NativeProjectRootV1 below.
- `status`: `RESERVED`, `ACTIVE`, `RETIRED` or `ABANDONED`.

NativeProjectRootV1 has exactly `platform`, `canonicalPathBytesHex`, `deviceId`, `inodeId`, `birthSeconds`, `birthNanoseconds`. Platform is `macos` or `linux`; native paths are raw POSIX bytes encoded as even-length lowercase hex. Decoded path is absolute, 1..4096 bytes, with no NUL, repeated separator, trailing separator except `/`, or `.`/`..` component. These are native path bytes, not UTF-8 repository paths or a source of authority. The path must be obtained and checked through the selected native root admission, never supplied as proof by a request.

Device and inode are shortest unsigned decimal strings in0..18446744073709551615 (no sign or leading zero except `0`). Birth seconds is an integer in signed64 range; nanoseconds integer0..999999999. macOS uses the retained directory descriptor's device, inode and native birth time. Linux uses the retained descriptor's statx identity with STATX_BTIME present and canonical Linux device encoding. Missing reliable birth identity is unavailable, with no mtime/ctime/marker fallback. This is an explicit new native qualification gate, not a claim that identity §2 itself already required birth-nanosecond metadata. In particular missing Linux STATX_BTIME refuses ordinary reuse AND first-use without creating anything. These requirements need native implementation and platform qualification; a fixture's matching numbers establish neither.

Every namespaceId is unique across ALL entries forever within this registry history. RESERVED and ACTIVE entries have mutually unique projectId, `(platform,canonicalPathBytesHex)` and native incarnation `(platform,deviceId,inodeId,birthSeconds,birthNanoseconds)`. Terminal rows may repeat historical ProjectIds/root locators but never namespaceId. No terminal row admits current access. This successor explicitly resolves identity §2's one-to-one law as LIVE ProjectId↔namespace uniqueness, not a prohibition on retaining a retired historical ProjectId↔old-N record after explicitly authorized fresh-N adoption. N itself is never reused across history. No empty/all-zero ProjectId spelling is treated specially: the grammar admits it; allocation still requires real OS randomness.

## Registry snapshot and first-use observations

Before selecting any row, capture the complete bounded registry under the installation fence; validate encoding, every row, ordering and all global uniqueness constraints. No early match, partial scan, directory listing or cached index can replace this check. During fenced admission, keep actual root, marker, registry and parent descriptors with the selected custody checks; enforce ownership, no-follow and admitted filesystem policy. Missing entire registry in an established installation is unavailable, never an empty registry. Only the separately authorized pristine installation creator can publish the initial empty registry; directory emptiness alone is not proof of a pristine installation.

Against an admitted project root, classify observations without writing:

| Observation | Result |
| --- | --- |
| Exact92-byte valid marker and exactly one matching ACTIVE row, same ProjectId, root path and incarnation, no competing live row | eligible for native namespace admission under the required guards |
| Marker positively absent and no ACTIVE/RESERVED binding to this locator/incarnation or marker identity | first-use candidate only; terminal history is not live admission |
| Matching RESERVED row, with marker absent or exact | explicit reservation recovery needed; never ACTIVE on read |
| Marker present without a matching ACTIVE/RESERVED row, or ACTIVE row with missing marker | one-sided identity, explicit recovery/adoption needed |
| Positive disagreement/duplicate live identity | contradiction; refuse |
| Inaccessible root/registry/marker, failed custody, unsupported birth identity, malformed/oversized registry or marker | unavailable or malformed evidence; never observed absence |

A marker is the immutable92-byte ASCII frame `opensip-project-id-v1\n` + `prj1-` +64 lowercase hex + `\n`. No JSON, BOM, CRLF, padding, trimming or trailing bytes. The selected project marker must be untracked; a tracked marker is refused, not silently untracked or overwritten. The registry cannot by itself establish marker absence, repository tracking or root custody.

A retired or abandoned entry is historical correlation, not a grant to reuse its namespace or to delete its old files. At a terminal-history root, ordinary first-use with genuinely absent marker allocates a NEW ProjectId and NEW namespace. A still-present old marker requires explicit recovery/adoption; it never revives the terminal entry.

## States and durability

Legal row state changes are insertion as RESERVED, RESERVED→ACTIVE, RESERVED→ABANDONED and ACTIVE→RETIRED. No other state change, row deletion, namespace reuse or automatic tombstone compaction. A later independently authorized adoption may insert a new RESERVED row for a historical ProjectId with a fresh namespace, only when no ACTIVE/RESERVED row has that ProjectId. Ordinary random allocation must reject a ProjectId present in ANY history row. This separates continuity by explicit adoption from accidental reuse by allocation.

All registry replacements require the installation fence and completed active-transition recovery. ANY active transition slot, including a terminal slot not yet retired by its owner, blocks registry mutation. No shortcut edits a registry to make a frozen journal match. Before ANY registry write, independently confirm exact predecessor file and parent durability under custody; prior-process success is not a substitute. Publish complete canonical replacements via an admitted same-directory temporary file and atomic rename with required file/parent barriers. Initial publication is no-replace. A failed or uncertain barrier stops; it grants no blind retry, rollback, deletion or activation. Plain reads never flush or create anything.

Before reserving, validate all current entries and serialize/bound the complete resulting RESERVED and ACTIVE envelopes, future terminal spellings, and the worst legal all-registered transition wrappers WITHIN THIS NATIVE PROFILE's4096-row bound. Check capacity before any registry, namespace or marker effect. At4096 entries or any byte/transition-capacity overflow refuse non-destructively; no history discard or partial NamespaceList. The extra marker/namespace files have their own native path and publication bounds.

For ordinary first-use: obtain up to eight independent32-byte OS-CSPRNG ProjectId candidates; reject collisions against ALL history before durable reservation. Allocate fresh native namespace UUIDv4 with its own independent16-byte draw, required version/variant bits and at most eight candidates; reject any recorded N or occupied target namespace path. Exhaustion or entropy failure produces the existing host failure projection and no partial guessed identity. Perform all candidate/capacity/precondition checks before publishing RESERVED.

Then, under the same fence: (1) durably publish RESERVED; (2) durably publish the new namespace directory with stable writer/readers lease inodes through the explicit initial-namespace publication profile below; (3) create-new the exact project marker, make the file and parent durable; (4) durably replace RESERVED by ACTIVE after rechecking every original root/marker/namespace observation. No project ledger, grant, Run or authoritative analysis is created before ACTIVE. Marker publication must not overwrite a tracked, foreign, different, malformed or unreadable object. Any one-sided or uncertain state ends the ordinary operation and requires explicit recovery.

ABANDONED is the durable terminal record of an allocation that never reached ACTIVE; it does not pretend a namespace and its stable leases were completely published. This explicitly replaces deletion of an uncommitted reservation in the historical ProjectId selector, preventing namespace reuse after a crash. It grants no orphan cleanup. Registry is the retention owner of these tombstones and possibly published namespace remnants: this profile retains both for the installation lifetime, with no per-namespace deletion/compaction operation. Ordinary store GC/purge does not touch them. A separately specified, reviewed installation-removal or future cleanup owner would be needed to delete them; none is implied here. This is the complete conservative V1 retention choice, not a promise that an unspecified automatic GC already exists. An abandoned N directory never occupies a different freshly allocated N; only exact candidate-path occupancy matters.

## Initial namespace publication profile

This is a new physical clarification, not a revival of the historical SQLite registry. RESERVED durably allocates N under the installation fence before publication. The initial namespace directory contains exactly two empty regular files, `writer.lease` and `readers.lease`, and no other entry. Namespace directory mode0700 and both leaf files mode0600 are host-owned, with custody/ACL/no-follow/single-link and qualified-filesystem checks; permissions are admission constraints, not authority by themselves. Project journal/witness/other files are initialized by their own owners only after ACTIVE.

Prepare this whole initial tree beneath an exclusively created same-parent temporary directory whose random name grants no recovery authority. Make both lease files and the tree durable, then publish the complete tree to `I/host/projects/N` using qualified no-replace directory publication and the required parent barrier. Never directly expose a partly constructed final namespace, overwrite an occupied N, or infer publication success from an uncertain rename/barrier. The admitted RESERVED row plus whole initial footprint is the explicit recovery join; a string-shaped directory alone is not. Before effects recheck exact registry predecessor file and parent durability and the positively absent final name under the same fence.

On restart, a present namespace may be admitted for reservation completion only when the exact RESERVED row/root join and this COMPLETE initial two-file footprint are admitted together under custody. Reconfirm both lease files, directory and publication-parent barriers before ACTIVE. An absent namespace can be freshly published by this same owner only in the completion modes explicitly admitted below; an incomplete, foreign, symlinked, unreadable or extra-entry namespace is unavailable and grants no repair/deletion. Unpublished temporary trees remain untouched after crash; only the process retaining its original unpublished handles may clean its own temporary tree under the existing publication cleanup rule. There is no scan-and-adopt recovery.

## Explicit reservation recovery

Recovery is an independently authorized local operation, not the constructor's fallback. It first performs the same whole-registry/root/marker/custody admission and observes the actual recorded state under the fence. RESERVED cannot grant a project lease or data access. RESERVED and ABANDONED are unregistered for project-lease admission: attempting flock on their file names is refused as lease-on-unregistered-namespace before lock acquisition, never treated as BUSY or permission to continue. Publishing empty lock carriers is not acquiring a lease.

Completion requires positively proved agreement of the recorded root incarnation/locator, exact marker, and the reservation's admitted complete initial namespace/stable lease footprint, with all required durability barriers reconfirmed. Missing namespace publication may be completed only under the initial-namespace profile above from positively observed absence; an occupied incomplete or foreign namespace is unavailable and cannot be adopted from its spelling. An absent marker may be created only after the same untracked/absence/root checks as the original allocation. Only then may RESERVED→ACTIVE be published. These observations are not proof that every combination is reachable by an ordinary first-use crash. Ordinary first-use publishes the complete namespace before creating its marker; RESERVED plus an exact marker and absent namespace is NOT its lawful crash prefix. An ordinary reservation-recovery continuation refuses that combination. It must not infer adoption authority from the marker, RESERVED row, caller flag or directory name; completion requires the independently admitted adoption context below. Unreadability/incomplete namespace still refuses in either mode.

Abandonment publishes RESERVED→ABANDONED without deleting marker or namespace bytes; it must prove no ACTIVE binding or live authorized operation was ever admitted through that row. A matching already-created marker remains one-sided and requires explicit adoption/recovery thereafter. Contradictory or unavailable original observations do not authorize abandonment as a way to hide evidence. A registry update with uncertain durability ends recovery; later recovery must freshly observe rather than replay the previous decision.

## Move, retirement and adoption

Any change to an ACTIVE entry's root or status requires the installation fence plus that namespace's EXCLUSIVE lease, acquired non-blocking with S7's ordinary release/backoff rules. All readers and writers must be absent, not merely the append writer. Existing immutable objects/receipts remain bound to their historical owners; an edit to a registry never rewrites them.

An authenticated move preserves ProjectId and N. The target must have the identical admitted marker; the old recorded root locator must be positively absent (not inaccessible), and the target must pass fresh native root/custody/tracking and global uniqueness admission. An explicit same-object rename may preserve incarnation; an authorized cross-filesystem relocation may bind the new incarnation only under this move act. No implicit move follows matching marker bytes or a new pathname. Both old and new simultaneously live roots refuse. Persist the single changed root entry atomically; uncertainty stops and may require explicit recovery. Stable N lease/journal/floor paths never move with the repository.

Retirement requires EXCLUSIVE, no active operation bindings that block retirement, and the operation owner's explicit authorization. ACTIVE→RETIRED retains the namespace's stable lease carriers and history; this owner grants no deletion. Terminal N never returns to ACTIVE. Adoption of a portable project preserves its ProjectId only under the existing admitted-bundle/source-target disclosure law; allocate fresh LOCAL N and carry no foreign credentials, grants, leases, execution receipts or local commit authority. A live local ProjectId collision refuses; adoption does not silently retire it. A fork uses a new ProjectId/N and separately retains the admitted origin metadata.

## Explicit adoption reservation and completion

Adoption first admits the portable bundle and its ProjectId, shows the source and target as required by the existing adoption owner, checks the native target root and complete registry, and establishes the existing operation-specific authorization. Marker bytes alone, a ProjectId string, a RESERVED row or a caller mode flag cannot supply any of those capabilities. A live local ProjectId collision refuses. Allocate a NEW local N under the same history/occupancy/8-candidate/capacity constraints; publish RESERVED only after those prerequisites. Registry completion never imports source grants, credentials, leases or execution receipts and never completes the bundle import/evidence transaction by itself. Those original operation owners remain mandatory after registry activation.

If the target already contains the EXACT untracked92-byte marker of that ADMITTED bundle's ProjectId, retain it as an existing owner: do NOT call create-new, overwrite, replace, normalize, or remove it. Publish the fresh namespace footprint from positively observed absence (or explicitly recover its complete initial footprint under the reservation), then independently reconfirm the existing marker FILE AND PARENT durability with all bytes/root/registry/custody joins. Publish ACTIVE only after these steps succeed. This is the adoption-specific existing-marker branch. If the target marker is positively absent, the same admitted adoption context may create-new the bundle ProjectId marker AFTER namespace publication; it may not choose a random replacement ProjectId or silently turn adoption into a fork. Different/malformed/tracked/unreadable markers refuse in both branches.

After interruption, adoption completion must independently reacquire the admitted bundle/source-target/authorization context; a saved mode string is not a capability. In particular RESERVED + exact marker + absent namespace may be completed only through that fresh admitted-adoption path, never ordinary crash-continue. If the context cannot be reacquired, return unavailable/refused without creating a namespace or activating the row. Registry-only ordinary recovery of a complete namespace/marker pair does not claim to finish or authorize any interrupted bundle import, origin linkage or evidence transaction.

The pure model's mode argument is a label for an externally supplied admitted context, not a host API and not a verifier. Its observation matrix is a grid of conditional plans, not a native crash-reachability proof. A separate ordinary durable-prefix table is limited to: RESERVED with neither namespace nor marker; RESERVED with complete namespace and absent marker; RESERVED with complete namespace and exact marker; ACTIVE after all barriers. Durability-uncertain publication stops the original attempt and requires fresh explicit observation; these labels prove no OS barrier behavior.

## S9 and operation-lifetime bridge

The native S9 NamespaceList is the sorted unique list of ACTIVE and RETIRED entries. A RETIRED namespace keeps its stable lease carriers and any retained evidence, so it remains in the exact transition/GC census. ABANDONED rows were never admitted and do not join that list. Any RESERVED entry blocks starting a new installation transition until explicit recovery settles it; never omit a possibly incomplete allocation from an otherwise claimed complete registry. Recovery of an already-active S9 slot retains its frozen registry checks first; it cannot silently repair or settle reservations before that check.

This choice is a native projection into the existing string-list schema, not added fields in the closed InstallationTransitionIntentV1/JournalV1. There are TWO named projections: RegisteredNamespaceList is sorted ACTIVE∪RETIRED and is the only string list put into S9 registry/registryDigest and the derived leaseSet; RegistryStartGate requires zero RESERVED entries plus completed retirement of every previous active slot. The full RegistryDocument includes all four statuses and is never substituted for the unchanged S9 string-list hash. RegistryStartGate applies even to same-schema core-update/core-repair, whose affected leaseSet is empty. A transition captures the complete validated RegistryDocument, checks RegistryStartGate, and projects RegisteredNamespaceList and its exact affected leaseSet/capacity under its whole-transition fence. Registered retired namespaces with unavailable stable lease carriers make required admission unavailable; no recreation from a name. For example ACTIVE N1 plus RETIRED N2 with an unreadable or missing writer.lease makes store-migrate unavailable, never BUSY and never permission to omit N2. This is an explicit NEW native registered-set choice, not an assertion that S7 had already defined RETIRED.

Ordinary project admission holds the installation fence while it validates the registry, root and marker and acquires the required project lease without waiting. The project context then retains its immutable admitted row snapshot, root/marker/namespace handles and held lease; it follows S7's existing fence release, checkpoint and end-handoff protocol. It does NOT hold the global fence throughout evaluation, reacquire it while holding a lease, or require the old registry file to remain the current filename after a different project's lawful registration. Same-N root/status mutations require EXCLUSIVE and are blocked by this lease; unrelated N updates remain independent. Current capability is lost on release, failed relevant retained-handle recheck or the existing lifecycle/security stop condition. Copied fields/digests outside those guards remain correlation only.

Short fenced trust/selection observation sessions and long operation contexts are different types and stages. Private provisional readers borrowing InstallationReadFence are not automatically promotable to the post-fence project context. At handoff, the retained registry file is provenance for the immutable admitted row snapshot only; do not call its filename-binding recheck from the ordinary context. Relevant retained root/marker/namespace handles and the project lease remain live obligations. The old registry FD need not remain linked or be the currently named inode, and the operation must neither reread that path nor reacquire the fence to revalidate it. Core same-schema updates may change selection.pair while existing operations pin their immutable admitted generation; this owner does not require their old selection filename to remain current. Store schema changes/re-selection still take the exact affected EXCLUSIVE set and cannot proceed past those operation leases.

## Recovery and detection limits

Registry and namespace lease state are installation-local control state, excluded from ordinary project/store evidence restore and portable import. Readable old canonical bytes or a valid checksum prove syntax, not freshness. This profile has no independent monotonic registry counter and does not claim to detect coherent restoration of registry plus markers/namespace/control domains by an actor outside the cooperative custody protocol. An established installation with a missing/invalid registry stops instead of synthesizing an empty one. Lost registry recovery must be independently specified and authorized; neither a store scan nor matching ProjectId marker reconstructs authority here.
