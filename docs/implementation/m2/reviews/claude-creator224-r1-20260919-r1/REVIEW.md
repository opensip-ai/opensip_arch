## 3. Findings

### C-1 (Medium) — directories the creator must create *above* `I` are unaddressed, and the reconfirmation covers only `I`'s own parent entry
`I` is `…/Library/Application Support/OpenSIP/preview-v1` or `…/.local/state/opensip/preview-v1`. On a fresh account `OpenSIP/` (macOS) or `opensip/` — and on Linux possibly `.local/state/` — do not exist. CREATOR says "create an exclusive 0700 sibling named preview-v1.creating.H" under "retained parent custody", which presupposes the parent; the foundation model checks `ancestors` but has no creation case for them. These intermediate directories cannot be part of the atomic rename, so they are created individually and **each new directory's own entry in its parent needs a barrier**. CREATOR's reconfirmation rule is "the exact I directory and its parent-entry durability": if `OpenSIP/` was itself just created and its entry in `Application Support/` is not durable, a power loss removes `OpenSIP/` and everything under it — including a P1 floor that a later writer published after "reconfirming" — which is exactly the loss the rule exists to prevent.
**[P] bounded rule:** (i) before staging, create each missing fixed ancestor with exclusive no-follow mkdir in custody-conforming mode, confirm it and its parent, re-admit it; an existing one is admitted, never adopted-as-ours; (ii) the next-writer reconfirmation covers **every directory from `I` up to the account home** (a fixed, small number of `fsync`s), since a later process cannot know which of them the creator made. Add model cases with a two-level durable chain.

### C-2 (Medium) — the fixed directory skeleton is not enumerated, yet 203 makes a missing required parent *unavailable*
**[E, working 203]** "A missing required parent is unavailable unless its absence was lawfully admitted as part of explicit first creation." CREATOR item list creates `stores/S`, the registry, `trust/publications/initial/S/D`, `trust/stores/S/state.v1`, a lineage node and the pair, and otherwise says "initial directories … are bounded before effects". The very first ordinary operations then need parents the list does not name: 222's by-predecessor bucket requires `trust/publications/by-predecessor/` ("each new predecessor directory is exclusively created … durable with its parent"); signed objects and private records need `trust/objects/`, `trust/records/`; the SC-TRUST commands must admit **absence** of `transitions/active.slot`; the first project needs `host/projects/`; journal floors need `trust/journal-floors/`; forward staging needs `stores/.staging/`. Either the first `trust import` refuses as unavailable, or each owner lazily creates its fixed parent later — outside the creator's all-or-nothing visibility and outside "absence admitted as part of first creation".
**[P]:** one rule — *every fixed (non-variable) directory of the current layout table is created, empty, in the staged root; variable-keyed directories (`N`, `S`, `H`, `E`, `G`) are created only by their owners under an admitted fixed parent.* Then "missing fixed parent in an existing installation" keeps its single meaning (partial/foreign root) everywhere.

### C-3 (Low–Medium) — the fence-wait numbers in CREATOR conflate two retained bounds
CREATOR: "Do not import the recovery 5s limit into all ordinary commands (ordinary profile currently 30s)." **[E]** S7 lock table, level 0: "lifecycle fence … flock LOCK_EX | **bounded wait 5 s, then `PROJECT.BUSY`**" — for every holder; the 30 s figure is a different thing: "A second writer or an EXCLUSIVE request gets `PROJECT.BUSY` at once, releases the fence, and may retry **outside the fence** with backoff 1/2/4/8/15 s within a 30 s budget." Product 223 agrees: `FENCE_WAIT_BOUND = 5 s`, `PROJECT_RETRY_BOUND = 30 s`, with the comment "The five-second fence budget can never extend this budget." The normative sentence ("use the actual invocation's existing bounded fence policy … existing causal mapper") is right; the parenthetical should be removed or corrected, otherwise an implementer will give the loser a 30 s blocking fence wait that S7 does not allow. (My earlier note's "existing 5 s bound" was the S7 value.)

### C-4 (Low) — a loser running a *different* delivery
Two deliveries on one machine (closures C₁, C₂) can race first creation; the winner's pair names C₁, and the loser — running C₂ — "re-enters ordinary admission of the winner's complete root". Say explicitly that a running closure different from `pair.coreClosure` is handled by existing pair/launcher law (refusal or an authorized core transition) and is never a creator case: the loser must not rewrite the pair "because it was also first".
