## 2. Answers
**(a) Can a structural pair name the current delivery while denying executable authority?** Yes, under existing law, and no INITIALIZING/ACTIVE union is needed. The pair is a *selection*; 203 itself says it proves neither binding nor closure. Authority is derived at use: pair ∧ closure content admission ∧ **current capsule role standing** ∧ leases. At P0 every role is never-established `UNBOOTSTRAPPED`, so `EV-INSTALL` refuses and no component is admitted; what runs is the delivered core's management functions, admitted by the payload-chain custody of `root_observation` — exactly the retained management-only / authoritative-closure distinction. `trust import` therefore never requires a trusted CORE. The **P0 capsule is the recognized owned incomplete phase**; adding a second phase marker to the pair would create a second authority to keep consistent with it.
**(b) How is P0 durable before S4, with S located?** By making creation a purely structural act with **no evaluation in it**, published atomically, *then* running the invoking command under ordinary law on an ordinary (P0) installation. Root's objection — staging an install whose S4 was evaluated privately and discarding it on refusal would erase floors — does not apply to a staging that contains no clock state: an unpublished P0 staging holds nothing a later attempt could lose.

## 3. Proposed minimal owner **[P]**
**Owner:** the existing host root-observation step, for state-using invocations only. One act, *installation creation*, the only producer of a P0 capsule.
1. Admit root **absence** under full ancestor custody (invalid parent custody never establishes absence).
2. In the admitted parent, create an exclusive private sibling `preview-v1.creating.<hex32 entropy>` (0700). Inside it, in dependency order with file/parent barriers: `lifecycle.fence` (created and **LOCK_EX held from here on**); fresh entropy `S` → `stores/S/store-instance.v1`; the creation event; the initial publication descriptor at `trust/publications/initial/S/D`; capsule `trust/stores/S/state.v1` = revision 1, `previous:null`, `clock:{phase:"unevaluated"}`, `heads:null`, six never-established `UNBOOTSTRAPPED` roles, `staged/batch/history/sourceFence:null`; whatever the lifecycle owner defines as its initial registry, **closed** before publication; last, `selection.pair` naming the delivering closure `C`, `S`, `G`, `K`. No S4, no S5, no payload, no network, no role event.
3. Publish the root by **exclusive no-replace directory rename** onto `preview-v1`, then confirm the parent barrier. Only after that barrier may the invocation continue — in particular before any S4 write-ahead, so a P1 floor can never sit in a root whose directory entry is not durable. Uncertain ⇒ stop.
4. Continue the command under the still-held fence: e.g. `trust import` performs its S4 write-ahead (P0→P1) and outcome (→P2) as 215/222 already define; a refusal leaves a lawful P0/P1 installation.
**Amendment needed — one:** the foundation effects `create-new-private-root → acquire-permanent-fence → publish-initial-state` keep their content but change **visibility order**: the root becomes visible only complete. The alternative that keeps the order (mkdir final root, then fence, then state, pair last) makes a crash leave a visible partial root, which retained law refuses forever (`RECOVERY-REFUSAL`; "absence of the pair … never permission to initialize"); to make that resumable one would need exactly the INITIALIZING marker and idempotent-resume rules root hopes to avoid. The staged form needs neither.
**Race and crash properties.** Two first invocations each build their own staging; one rename wins, the loser gets `EEXIST`, leaves nothing adopted, and admits the winner's root through its fence (existing 5 s bound ⇒ `PROJECT.BUSY`). The fence inode is created inside staging and keeps its identity across the rename, so exclusion is continuous from before visibility. A crash before the rename leaves an orphan sibling that is never the root, never adopted, never resumed and left untouched (a creator may remove only the staging **it** created in this invocation). A crash after the rename and before the parent barrier either shows a complete root or none — and nothing of value existed yet.
Native probe (macOS, APFS, scratch): plain `rename(2)` of a directory onto an existing **empty** directory **succeeds, silently replacing it**; `renamex_np(RENAME_EXCL)` returns `EEXIST`; with the fence locked inside staging, after exclusive publication the inode is unchanged and a second opener through the final path is blocked (`EAGAIN`). So the exclusive variant (`renamex_np` / `renameat2(RENAME_NOREPLACE)`) is **required**, not optional, and is a native-qualification item.
**Distinguishing owned-incomplete from foreign-partial.** Owned-incomplete exists only in two recognizable forms: an unpublished `preview-v1.creating.*` sibling (ignored) and a complete root whose capsule is P0/P1 (lawful, usable for management). Everything else — root without fence, pair, marker or capsule, or with mismatching bindings — is a foreign/partial root and keeps the retained `RECOVERY-REFUSAL`. No third category, no side file.

## 4. The specific constraints, checked
- **Fresh unused S / init bucket.** In first creation everything is new. For any later store creation inside an existing installation, `stores/S`, `trust/stores/S` and `publications/initial/S` must all be *admitted absent* first (222 r5 S-5); an occupied footprint refuses and a different S is **not** a remedy for a missing selected state.
- **Absent selected capsule.** Pair names S, `trust/stores/S/state.v1` absent ⇒ unavailable (rollback-to-absence law), never creation, never a new S.
- **Read-only / ephemeral.** Retained: non-state-using on an absent root ⇒ `ABSENT`, no effects. `doctor` / `trust doctor` (authorizationClass `none`, report steps) must therefore be non-state-using for creation purposes; creation is triggered only by invocations whose steps mutate.
- **Restore / portable adoption.** S9.3's "imports no floor" is about the **copied source bytes**. The installation's own known protections live in the currently selected store's capsule, and the only owned mechanism that gives a new store a capsule while preserving them is 222's forward continuity ("Null targetBefore is admitted ONLY for the forward target whose explicit creation path proved absence"). Smallest coherent position: **first installation creation is the only P0 producer**; a restored/adopted lineage-root store becomes selected only through the existing forward transition, whose target capsule is the carried one (floors/heads/history copy-max, standing reset, revoked-before-BEGIN preserved). I found no owned selection path for such a store in the sources read, and S9.3's "no transition is invented to give it an `intentDigest`" concerns the store's *lineage origin*, not its later selection — root should confirm that reading. Portable adoption onto a machine with **no** installation is simply first creation followed by the adoption act; there are no same-install protections to preserve.

## 5. Actual availability limits (no repair invented)
1. Selected capsule absent, unreadable or unprovable ⇒ the installation is unavailable for trust; the only path is removing the root outside the product, which discards every floor and revocation. No reset command is proposed.
2. Deleting the whole installation root yields a lawful fresh P0: installation-level rollback-to-nothing is undetectable without an external anchor — the retained "coherent rollback of the entire install root" limit, now at its extreme. 222 S-5 covers only capsule-absent-with-publications-present **inside** a root.
3. A foreign or partial root is refused permanently; the product neither adopts nor cleans it. Orphan `creating.*` siblings accumulate.
4. P0 with no embedded bootstrap payload and no presented payload stays P0 (`TRUST.NO_ADMITTED_TIME_CONTEXT`); a state-using command that then refuses has still created the installation.
5. Exclusive directory rename, directory-entry durability and flock-across-rename are native qualification obligations (macOS and Linux); my probe is one machine, one filesystem, not qualification.
6. Actual-core-immutable, OS-account identity and custody joins remain owed producers, as root states; this proposal consumes them and does not supply them.
