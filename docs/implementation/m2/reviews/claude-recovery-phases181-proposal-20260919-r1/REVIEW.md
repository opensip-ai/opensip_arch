## 0. Answer in one paragraph

The proposed direction is right and — importantly — it is **already what the executable owners do**; only prose and one schema description disagree. `recover_transition_journal` reads exactly `fenceHeld`, `namespaceRegistry`, `leasesReacquired`, `storeFootprint` across all 11 owner recovery vectors (spy-dict, demo §A): no trust, time, profile, target or new-intent input; `integration-host-model.recover_installation_transition` rebuilds the intent **from the journal** and scopes it over the **journal's** registry. So 181 is a wording-and-composition correction, not new authority. But "no owner requires current trust before recovery" must not be assumed: I found **four unqualified sentences** that a host implementer could lawfully read as pre-recovery trust dependencies (§2). They need deliberate qualification.

## 1. The three phases, as a closed law (suggested shape; owner authors the words)

**Phase A — pre-recovery gate (closed; nothing else may be evaluated).**
A1 recognised grammar: the parsed invocation is exactly one of the five S14/S15 spellings. Unknown syntax, aliases, a role flag or a caller assertion never reach A2 (they fail ordinary grammar admission).
A2 S3 installation custody of the install root / fence carrier / active-slot carrier (mode/ACL/owner — all time- and trust-independent).
A3 fence held (S7 level 0).
A4 active-slot observation admitted **internally**: the 173 reader law verbatim (closed keys, reconstructed ten-field intent, recomputed digest, registry digest, affects/leaseSet = `core_transition_affected_namespaces(journaled intent, frozen registry)`). Unavailable/inconsistent ⇒ `unknown-custody`, stop. Absent ⇒ skip to Phase C.
A5 current registry == frozen registry, else `MIGRATION.CORRUPT` (existing).
A6 **exactly the journaled lease set** re-acquired, non-blocking, all-or-nothing, else `PROJECT.BUSY` (existing). The invoking command's own would-be lease set is irrelevant here: a `core repair` recovering a journaled `store-migrate` takes every journaled namespace.
*Excluded by name until Phase C:* VERSION/target resolution, new-intent projection or admission, S4 decision evaluation **and its write-ahead floor write**, S5 chain/expiry, S6 epoch capture, S8/S9.1 profile-set admission, rollback-window/deadline comparison, catalog/revocation freshness.

On "existing operator consent": **the inventory gives the five executors none** — `authorizationClass: core-transition-leases`, `flags: []`, no `user-consent`. Their authority today is *explicit invocation + custody + the lock set*. Do not write "operator consent" into the gate unless the owner deliberately adds a consent class; that would be new authority in the other direction (a new refusal), and CI semantics (`--yes-policy`) would need deciding. I recommend: explicit invocation only, stated as such.

**Phase B — historical recovery and retirement.**
B1 `recover_transition_journal` by state, S9 footprint table for store operations, under the journal's operation — never the requested one.
B2 terminal state durable → **durable active-slot absence** under the same fence (175/178 law).
B3 failed or durability-uncertain retirement ⇒ stop: release journaled leases/fence per existing rule, report, **no Phase C**, no new-intent projection, no SC-TRUST read-for-decision or write. The next authorised executor re-enters at A4 and finds a terminal journal (release-only + retire). `BUSY`/`QUARANTINE`/`REFUSE` outcomes likewise end the invocation before Phase C.

**Phase C — post-retirement ordinary admission (only after B2 is durable, or A4 found absence).**
C1 only now: observe generations/schema/store, resolve target under current trust, run S4/S5/S6/S8/S9.1 as today, project the eleven-field intent, `admit_transition_intent`, acquire **this** intent's lease set (the journaled set from Phase B is released first or reconciled by the S7 owner — owner must say which; simplest: release all, re-acquire by the new intent, still under the fence), `admit_transition_journal`.
C2 any Phase C refusal leaves the slot **absent**. Therefore a later `trust refresh|import|recovery-*` passes the reader barrier. This is the sentence that breaks the 178 F-1 cycle.
C3 outputs must distinguish "recovered prior `<operation>`; requested `<command>` refused: `<detail>`" from a plain refusal — otherwise the user cannot tell cleanup succeeded (receipt/`migration-state` parity fields already exist).

Why the ordering is *forced*, not just preferred (worth stating in the owner text): SC-TRUST floors live in the state store (S9: "Floors … copy forward into the new store; the boot anchor and any pending challenge do not", l.1141–1148). Before recovery of a nonterminal store transition the host does not know which store is selected, so an S4 evaluation — which **writes** F write-ahead — or a new challenge would land in a store that may be abandoned. The same fact is the real justification for 178's nonterminal block on the trust-only commands, and S10.2 already sets the precedent in its own words: "rollback/cleanup never consults recipe trust, commit re-consults it" (model header).

## 3. Minimum executable composition and vector pair

No new oracle is needed; every piece is an existing selector (demo §A–C ran them together on the 178 bytes):

`executor_phases(invocation, slotObservation, recoveryCtx, retirementObservation, trustRecord, clockObservation, newIntentInputs)` — a pure composition in the integration host model that
1. refuses unless `invocation.command ∈ FIVE` (closed constant, shared with W2's inventory field);
2. calls `readonly_transition_reference.observe`-law admission of the journal (or reuses `recover_installation_transition`'s identity/intent/scope checks — it already does the reconstruction);
3. calls `S.recover_transition_journal(journal, recoveryCtx)`; **the function signature must not accept** `trustRecord`/`clockObservation`/`newIntentInputs` in steps 1–3 — enforce by construction: phase A/B is a separate function that does not receive them, and the checker asserts by spy-dict that `recoveryCtx` reads ⊆ {fenceHeld, namespaceRegistry, leasesReacquired, storeFootprint} (exactly what I measured);
4. takes `retirementObservation ∈ {('absent',None), ('present',journal'), ('unavailable',None)}` — the **same asserted tuple type the 173 observer already takes**; nothing simulates the physical act. Only `absent` proceeds;
5. Phase C calls the real `S.clock_decision`, then (where applicable) `verify_root_chain`/target admission, then `core_transition_scope` + `admit_installation_transition`.
Output: `{recovered: action|None, retired: bool, newAdmission: ADMIT|refusal|not-attempted, slotAfter}`.

**Vector pair (same hostile trust in both):** journal = owner record `journal_StoreMigrate_prepared` + RESTORED footprint (→ `RESUME-COMMIT`), invoked as `core-repair`; trust = (i) everything-expired record, (ii) floor-years-ahead record (the two I ran: S4 yields `CLOCK-EXCURSION-FORWARD`, and `CLOCK-REGRESSION`+`TRUST.FLOOR_AHEAD_OF_WALL` with all three expiry states true).
- **V1 cleanup not blocked:** `recovered=RESUME-COMMIT`, reacquire = the journal's three namespaces (not repair's empty set), `retired=true`, `newAdmission` = the real S4/S15 refusal, `slotAfter=absent`; then `observe(absent)` → `permit` for the trust-only selector (demo §C). Proves expired/floor-ahead trust cannot block cleanup **and** the new transition still refuses under the real owner.
- **V2 no projection before durable absence:** identical but `retirementObservation=('unavailable',None)` (and a second with `('present',DONE)`): `newAdmission=not-attempted`, spy shows `trustRecord`/`clockObservation`/`newIntentInputs` **never read**, `slotAfter` unchanged; trust-only selector → `unknown-custody` / `permit`-on-coherent-terminal respectively (existing law).
Useful extra negatives (cheap): unknown command string → refused before any slot read; `core-repair` with `leasesReacquired=[]` against the three-namespace journal → `PROJECT.BUSY` (kills "uses own lease set"); control with healthy trust → V1 shape with `newAdmission=ADMIT` (shows the refusal in V1 is caused by trust, not by the harness).
Mutants the owner should plant: trust read moved into phase A; repair's own scope used for reacquire; Phase C run on `unavailable`; new intent projected from pre-recovery generations (detect via `preconditionGeneration` differing across `RESUME-COMMIT`).

Honest limits to state in 181: this proves ordering over asserted observations; it does not qualify physical retirement, authentication of the journal, or the host's actual process-start behaviour (D4) — that is a host conformance obligation.
