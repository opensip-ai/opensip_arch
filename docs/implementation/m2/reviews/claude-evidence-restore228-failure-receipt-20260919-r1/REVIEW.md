# Failure-receipt ownership for evidence-restore (α) — resolved against the actual sources

Reviewer: Claude. Date 2026-09-19. **Read-only on candidates/product/architecture; written only here; no commit/push; not approval.** Sources: my verified reference-201 extraction, hashes in `claude-out/io/source-hashes.txt` — workflows `8d8551c6…`, identity `5c7de36c…`, security-and-lifecycle `7c982d87…`, build plan `56c7fa72…`, `evaluator3/repair.schema.json` `678d8a4f…`, `evaluator3/invocation-record.schema.json` `3377d456…`. **[E]** inherited, quoted · **[P]** proposal · **[?]** open.

## 0. My earlier suggestion is withdrawn
"A FAILED receipt is written … for a refusal after admission to the final checkpoint (its own tiny transaction)" was wrong for the reasons root gives — it is a second ledger effect after a single-use permit, possibly under a latch, and could contradict an uncertainly durable COMPLETED body — and, as §1 shows, inherited law never required it.

## 1. What the sources actually require
1. **A receipt is required only for a *completed* step. [E]** `invocation-record.schema.json` `StepResult.allOf`: `if outcome == "completed" then required: ["result"]`; `MutationResult` requires `{kind, receiptId, effectOutcome, replayed}`. For `rejected`, `failed`, `cancelled`, `abandoned` no `result` — hence no `receiptId` — is required. `StepOutcome`: "rejected: admission or precondition refusal. failed: operational fault … abandoned: assigned only by crash recovery".
2. **The failed attempt is already durably described without a receipt. [E]** `Attempt` = `{executionId, outcome ∈ completed|rejected|failed|cancelled|abandoned, faultCause?, retried?, …}`, up to 3 per step, plus the step's `termination`. workflows §1: RequestId is "retained for refusal as well as success".
3. **A refused mutation with no receipt is an inherited, exact precedent. [E]** the pinned-purge refusal: "PurgeRefusalProjection with exactly runId, **receiptId:null**, and availability" (workflows l.1704), and the schema pins that StepResult to `outcome: rejected`, one `rejected` attempt, no `result`.
4. **"Retained even when the effect FAILED" is a retention rule for receipts that exist, not a duty to mint one. [E]** schema description: "Retained record of an attempted host mutation. Retained even when the effect FAILED or a later verification failed"; workflows l.212: mutation receipts "remain retained when an effect or later verification fails". The mutations that produce such receipts have *partial, observable* footprints: repair-apply's receipt carries `fileOutcomes`, `rollback ∈ not-needed|completed|blocked|not-attempted`, and "A fault during `APPLYING` restores every renamed target". α's effect is one atomic ledger transaction: it has no partial footprint to describe.
5. **What a stopped session may do. [E]** build plan l.151–156: "security returns a stopped session that still owns the operation lease and **admits cleanup only, with no further analysis/effect APIs** … the host uses that stopped session to record pending REV/cleanup through a fresh lawful level-3→level-4 append" — a **journal** append. F38: "the stopped cleanup-only session **may not settle it**". identity l.1719 / S6: "No writer may reopen a stopped session merely to settle it; settlement is the separately authorized sweep."
6. **The only inherited later-writer is proof-only. [E]** F53: the settlement sweep "runs as a per-namespace step of the existing store-gc operation under the install fence with non-blocking EXCLUSIVE … reads ONE coherent ledger snapshot and writes only committed or refused, **never undetermined** … reuses none of the dead attempt authority, obtains no new execution grant and **never retries the commit**."
7. **Durability unknown. [E]** F40: "durability-undetermined: Report DURABILITY.COMMIT_FAILED, operational-failed, exit 4. Retain ExecutionId for correlation … A latch does not convert this into uncommitted." S6: "no automatic write retry".

## 2. Scrutiny of root's candidate (typed cleanup-only outcome-recorder under the still-held lease)
It is careful, but it conflicts with items 5 and 6: a `MutationReceiptV1` row is an evidence-ledger write, and the stopped session is limited to journal cleanup and explicitly may not perform even the *settle* write for its own attempt. It also needs the failing attempt to decide "definitively failed" — the judgement root rightly distrusts when a barrier is uncertain — and it spends a second ledger transaction after a single-use permit. Every one of those problems disappears if no FAILED receipt is owed, which is what item 1 says.

## 3. Proposal **[P]** — smaller, and faithful: the failing attempt writes no receipt; the COMPLETED receipt exists iff the publication committed
| Case | What happened | Ledger | Journal | Invocation record (inherited carrier of failure) | Later reader |
|---|---|---|---|---|---|
| **A. Pre-effect refusal** — any admission/precondition failure, including the final checks and a latch winning at state 0 (gate fails) | no native publication attempted | nothing; staged blobs stay unreferenced orphans | stopped session's ordinary REV/CLN cleanup, if the operation has a journal generation | step `rejected` (precondition) or `cancelled` (cancellation before terminal result); attempt likewise; typed termination; **no result, receiptId absent** — exactly the purge-refusal shape | nothing for this ExecutionId ⇒ unknown, never negative (my previous note §3) |
| **B. Definitive native failure after the gate** — the transaction returned a definite error and its rollback is confirmed | effect attempted, zero footprint | nothing (the COMPLETED receipt was inside the rolled-back transaction and never existed durably) | cleanup as A | step `failed`, attempt `failed` with `faultCause`; no result. **No FAILED receipt**: the permit was single-use, a latch may be set, and an atomic transaction that rolled back has nothing for `effectOutcome:FAILED` to describe | as A |
| **C. Durability unknown** — commit error or unconfirmed barrier, with or without a latch | may or may not be durable | **nothing more is written by anyone in this attempt** | cleanup as A | step `failed` with the durability-undetermined termination and the ExecutionId; never `completed`, no `runId`-like claim; no automatic retry | if the transaction did commit, the COMPLETED receipt + association + body are all present (same transaction) ⇒ *published*, historical; otherwise unknown. No INDETERMINATE receipt is ever needed, because the receipt's presence is itself the footprint |
Consequences: (i) exactly **one** ledger effect per attempt, ever — no second effect after a latch or an uncertain barrier; (ii) the inherited receipt law is untouched — same schema, same `receipt2:` recipe, and a receipt, once it exists, is retained through later failures (e.g. a later availability loss or purge tombstone); (iii) a caller who wants to try again issues a **fresh request** (new RequestId ⇒ new scope, new ExecutionId); if case C had in fact committed, the second admission is simply another imported-evidence admission record over identical content-addressed objects, which 228 already allows.
**If root later wants a provable negative or an audit trail of failed restores,** the faithful extension is the inherited sweep pattern, not an in-attempt recorder: the optional sibling custody row from my mutation-owner note (`admitted → settled{published|refused}`), settled **only** by a separately authorized proof-only sweep under the fence with non-blocking EXCLUSIVE, "never undetermined", never retrying and never minting a receipt. That remains optional and is not needed for α's safety.

## 4. Remaining unknowns, stated honestly
- **[?]-1 Where and when the invocation record is durably retained**, and that finalizing it is not an S6 "effect" forbidden after a latch. The sources say refusals are retained and that required delivery still reports after a latch (F39: "reported through the existing DELIVERY.REQUIRED_FAILED … path"), but I found no carrier/transaction rule for the invocation record itself.
- **[?]-2 Exact step-outcome and D9 termination/detail codes** for A (latched gate: `cancelled` vs `rejected`), B and C for a *mutation* step; F40's `DURABILITY.COMMIT_FAILED` is stated for commits. Owed to the public-detail registry; not invented here.
- **[?]-3 How "definitive rollback" is established natively** (which SQLite results are definite vs uncertain). Until qualified, any doubt is case C, which needs no further write — so the proposal is safe under misclassification in that direction; the unsafe direction (treating an uncertain commit as B) changes nothing durable either, because B also writes nothing.
- **[?]-4 My reading of "retained even when the effect FAILED"** rests on the schema's conditional `required` and the purge precedent; if root holds that every attempted generic mutation must mint a receipt, that would be new law for *all* generic mutations (none of which has a written publication owner today), not something specific to evidence-restore.
