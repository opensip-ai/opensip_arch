## 2. Is A–C now coherent?
**Largely yes**: authorization chain, prospective TR-BUNDLE, strict floor, deterministic locked batch, staged/begun distinction, per-role exits and the second pass fit together and none contradicts v14, 208/211 or S4 as written. Five specific points remain *inside* A–C (not D/E omissions); R-1 and R-2 are counterexamples, R-3–R-5 are precision.

### R-1 — counterexample: the deterministic batch can contain a role the replacement root cannot activate
Batch = signed ∩ state-applicable, and it "cannot omit an applicable listed role". Take the natural "recover everything" application listing all six roles, and a replacement root in which `TR-REPAIR` is typed-absent (keys `[]`, threshold 0 — the current preview configuration; v14: "DEFERRED with DR-110"). On essentially every install `TR-REPAIR` is `UNBOOTSTRAPPED`, hence applicable, hence in the batch. At COMMIT its RECOVER-COMMIT guard requires `recoveryTrustedEntry` (`roleToKeyAndDelegatedNamespace`, threshold) which a typed-absent role can never satisfy; "Any refusal commits no role/head" ⇒ **the whole batch is uncommittable, on every install, deterministically.** The publisher can avoid it by not listing such roles, but the owner should not rely on that silently. Minimal fix consistent with root's principle (derived, never chosen): batch = signed ∩ state-applicable ∩ **roles the authorized replacement root activates**; a listed role the replacement leaves typed-absent is treated as unlisted (it was never going to be TRUSTED under that root — 209/214 already say a typed-absent role "cannot become TRUSTED"). Staging step 5's "typed role availability" already has the information; only the derivation rule is missing.

### R-2 — counterexample: the payload's new revocation list is never dispatched to role machines
C says at COMMIT "Preserve REVOKED. Any other role with previously established non-revoked standing becomes UNBOOTSTRAPPED … ROOT_CHANGED". But the commit also accepts the payload's **new revocation list** (the head's revocation member advances). If that list revokes the namespace/keys of a *non-batch* role that was, say, `TRUSTED`, v14's named transition is `EV-REVOKE → ST-REVOKED`. C as written resets it to `UNBOOTSTRAPPED/ROOT_CHANGED` instead — and from there an ordinary payload is a lawful path to `TRUSTED`. That is the laundering root has ruled out, reintroduced through the commit's own side effect; the union history keeps the observation, but the role's *event state* no longer reflects it, so the rule "ordinary PRESENT cannot heal REVOKED" has nothing to act on. Needed in C: within the same publication, the newly accepted revocation observations are dispatched as `EV-REVOKE` to every role they affect (batch and non-batch) **before** induced resets are computed, each with its own evidenced event; a batch role revoked by the payload's own list makes the commit refuse (it cannot become TRUSTED and REVOKED at once) — which step 6 should then also detect at staging.

### R-3 — S4 time evidence from a recovery payload needs an explicit gate
B: the recovery payload "may supply signed time evidence through the same S4 witness mechanism", and S4's preflight refusals "still apply at staging". S4 step 2 writes `F := tEval` with `A` derived from presented documents *before* the outcome. Here authentication rests on the **prospective** root, authorized by the current recovery quorum. Say exactly when its times become admitted evidence: **only after steps 2–6 have all succeeded** (authorization, possession, manifest, members, second pass). A payload that fails any of them must contribute no `A`, no witness and no floor write — otherwise a payload carrying a forged authorization could still advance `evalHighWater` by up to the 24 h future tolerance. The preflight (future-time refusal, "nothing is written") may run first; the write-ahead using payload-derived evidence must come last. r3's text is compatible with this but does not say it.

### R-4 — ordinary head change while a batch is begun
A begun batch binds `authorityRoot = current head N`. Nothing in C says what an ordinary payload for a *non-batch* role may do meanwhile: if S5 rotates the head N→N+1, the authorization's `authorityRoot` no longer equals the held head and COMMIT can only refuse; the batch must be aborted. That is safe, but it is an unstated interaction with a cheap rule either way (refuse head-advancing ordinary PRESENT while any ceremony is begun, or state that such a PRESENT interrupts the batch exactly as REVOKE does). Also state what ABORT does to the *staged* reference (I would discard it, so a retry re-presents and re-authenticates under the then-current context).

### R-5 — the ancestry condition can be an invariant instead of a walk
A requires each non-null `acceptedUnder` to be "the exact ancestor identity on the installation's retained admission chain", and E rightly refuses to bound that walk by 64. But `acceptedUnder` was, when recorded, the store's head, and the head only ever advances along one admission chain (ordinary link, authorized recovery edge) or is replaced by the ancestor carry, which itself requires the old head to be an exact ancestor. So **"every non-null `acceptedUnder` is an ancestor-or-equal of `heads.root`" is an inductive invariant of the capsule**, established at each head change, and BEGIN needs no traversal at all — only equality of the descriptor's predecessor with the capsule's recorded binding. The single place a traversal is unavoidable is the ancestor-carry admission (target head → carried head), once per transition; there "bounded walk, exhaustion refuses the transition" (E's rule) is fail-closed and sufficient. Writing the invariant into C removes a lifetime-unbounded read from the ceremony path. ("Ancestor" should also be stated as inclusive: the common case is `acceptedUnder == authorityRoot`.)

## 3. E's ancestor carry
Coherent with my 215 §5 analysis and tighter where I was loose: exact ancestry including authorized-recovery edges; no numeric-max or fork guessing; `acceptedUnder` never overwritten; "The carried root supplies current authority, never role standing"; no new S5 acceptance, no Phase-B S4; catalogs historical with their head/counter representation left to the capsule owner. One observation: R-2 applies here too — if the *source* had accepted revocation observations the target never saw, the merged history must also be dispatched to the target's role states (or every affected role is at least left non-healable); "reset all other established roles" alone would launder them the same way. That belongs with the continuity carrier work E already lists, so I note it rather than count it.

## 4. Second-pass detail (not a flaw)
Filtering the revocation list's **own** signers by the list itself is correct for a self-consistent payload, and it is finite as stated. If the *ordinary* PRESENT path does not apply the same self-filter today, identical bytes would be judged differently on the two routes; worth one sentence saying the recovery route is deliberately stricter, or aligning the ordinary route when its owner is next touched.
