## 1. Root-ceremony application: what exists, and the smallest explicit owner

**Located [E]:**
- *Delivery route exists.* `payload.schema.json` (v2): `payloadKind ∈ {ordinary, recovery}` inside the signed preimage (v14: "AUTHENTICATED discriminator … a presenter cannot relabel it"), and `members.envelopes[]` — a list of `{path, sha256}` — can carry any envelope. `rootChain` (1..64) carries the replacement root.
- *Authority key set exists.* `root.schema.json` `recoveryAuthority {keys: 5..16 hex64 unique, threshold: 3..16}`; product `QuorumRole::Recovery` with authority label `"RECOVERY"`.
- *Requirements exist.* v14 `recoveryAuthorityShape.requiredOnRecoverCommit`: oldRootIdentification, recoveryAuthoritySet "distinct from the replacement root's self-signature", recoveryAuthorityApplication, threshold, `oldRootNewRootRoleBinding`, `newRootDoesNotSelfAuthorize`, `antiRollback`; standing "SHAPE ONLY".

**Not found [GAP] — confirmed independently of root's search** (`io/ceremony_search.txt`: tree-wide scan of the 201 reference, v1/v2/v8/v14 and both schema sets for recovery payload / root recovery / rotation application / RECOVER-COMMIT): no schema, preimage, digest domain, envelope kind or import owner for the *application* exists. The only `RECOVERY`-authority kind is `trust-recovery-epoch` (`opensip.metadata.recovery-epoch.1`), which is S4.5's clock-floor document: bound to a per-install challenge nonce and `recordDigest`, "Counters, revocation entries, role states … are untouched" (S&L l.503–506). It must not be repurposed: its body cannot express old/new root or role, and its install binding is wrong for a publisher-wide ceremony.

**[P] Smallest explicit owner — a ninth envelope kind beside the existing metadata profile:**
```
kind   "root-recovery-authorization"     domain "opensip.metadata.root-recovery.1"     authority RECOVERY (QuorumRole::Recovery)
body   RootRecoveryAuthorizationV1 = {
  "authorizationSchema": 1, "kind": "root-recovery-authorization",
  "roles":   [ "TR-…" ]            // 1..6, unique, sorted; the roles this application recovers (Q2)
  "oldRoot": { "rootVersion": n, "sha256": hex64 },   // the root being replaced FOR THESE ROLES
  "newRoot": { "rootVersion": m, "sha256": hex64 },   // m > n; exact bytes present in the payload's rootChain
  "issuedAt": ts, "notAfter": ts }                     // temporal applicability, evaluated at tEval like every other document
```
- **Distinct domain ⇒ no cross-protocol replay**: a `recovery-epoch` signature can never verify as a root-recovery authorization, although the *same key set* signs both. Reusing `recoveryAuthority` (not minting a second authority) is the least change; v14's "distinct from the replacement root's self-signature" is satisfied because root keys never count toward `RECOVERY` (S4.5 already says "Root keys never count").
- **Verification = existing mechanisms, in this order:** `verify_quorum(authorityRoot, QuorumRole::Recovery, namespace, message, signatures)` → revocation filtering → `QuorumReport` at `recoveryAuthority.threshold` (3-of-5 minimum by schema) [*positive authorization*]; **and independently** the replacement root admitted by `admitted_roots` with its **own** `rootKeys`/`rootThreshold` possession proof (S5's possession half) [*replacement proof*] — continuity from the old root keys is what the authorization replaces; `newRootDoesNotSelfAuthorize` holds because possession alone is insufficient. Exact digest joins: `sha256(rootChain[last] bytes) == newRoot.sha256`; `oldRoot` equals the retained per-role binding (Q2); `roles` ∋ the role of the event.
- **Which root supplies the authority keys** is the one real choice; see Q2 — *the store's current accepted head root* (or, before any accepted root, the core's embedded anchor root: v14 "or there is no prior root because the role is UNBOOTSTRAPPED", `bootstrapAnchorCustody`).
- **No install binding** (unlike the clock epoch): a root ceremony is publisher-wide and delivered on removable media; replay is bounded by `notAfter`, by the exact `oldRoot` digest, and by anti-rollback.
- **No payload-schema change:** the envelope travels in the existing `members.envelopes[]`; a recovery-kind payload lacking exactly one applicable authorization is `PAYLOAD-NOT-ADMISSIBLE` at staging (existing reason).

**Exact changes this implies (to author, not done here):** (1) v8 §2.1 closed domain-tag registry + the S&L envelope-kind list: eight → nine, by explicit successor; (2) a new closed schema file beside `root`/`revocation`; (3) reference model: kind routing, body admission, the staging/BEGIN/COMMIT joins; (4) `complete-envelope-cases` fixture family extended with the ninth kind incl. cross-domain replay negatives (epoch signature presented as authorization and vice versa); (5) product `EnvelopeKind` + `route()` + a private `admitted_root_recoveries` owner parallel to `admitted_recovery_proposals`; (6) v14's `recoveryAuthorityShape` "SHAPE ONLY/reserved" explicitly superseded for these members, numbers from v1 §4.1 and the root schema. ## 2. Per-role `oldRootIdentification` vs one global root head

**[E]** The root is *one document for all roles* (`root.schema.json`: `rootKeys`, `roles`, `recoveryAuthority` in one body), `clock.rootVersion` is one counter per store, and S5 advances it globally. **[E]** v14 is per-role: "Identify the role being recovered (never a collapsed 'trust')", `oldRootNewRootRoleBinding`, and no event exists for "the root changed because *another* role recovered". **[GAP]** Nothing reconciles the two.

**[P] Least additional retained identity: one member per role — `acceptedUnder: {rootVersion, sha256} | null`** = the root under which this role's standing was last *established* (ordinary TRUSTED-entry or its own RECOVER-COMMIT). `null` only for `bootstrap.kind == "initial"`. No scalar, no derivation of state from it.

**[P] Rules, stated without a counter exception:**
1. **Authority is always the current head.** The signatures on an authorization are checked against `recoveryAuthority` of the store's *current accepted head root* (pre-genesis: the embedded anchor). An older root's keys are never treated as current, for any role.
2. **Anti-rollback is against the store floor, never relaxed.** For the first role that commits a ceremony: `newRoot.rootVersion > clock.rootVersion` (strict), and the head/counter advance in that capsule revision. For a role that recovers *after* the head has already moved to M: its authorization must have `newRoot == heads.root` (**equal to the current head, not below any floor**) and `oldRoot == that role's acceptedUnder`; the global counter does not move and nothing decreases. "Strictly advances" thus means *relative to the role's previous root* **and** *never below the store floor*; equality with the floor is lawful only for joining the existing head. That is a rule, not a silent exception — it should be written exactly so.
3. **Other roles when the head moves by ceremony** — new choice, two candidates:
   (a) *Explicit reset in the same revision* (recommended): every other role in `TRUSTED/EXPIRED/STALE/QUORUM-LOST` becomes `ST-UNBOOTSTRAPPED` with `bootstrap.kind:"reset"` (evidence = the committing event) — exactly the standing-reset rule root already retained; `ST-REVOKED` stays `ST-REVOKED`; a role mid-ceremony stays `ST-RECOVERY` and its later COMMIT fails rule 1/2 naturally (`RECOVERY-COMMIT-REFUSED`, stay) until aborted. The continuation join then stays truthful using raw states only. It needs a third reset cause besides `RESTORED`/`MIGRATED` (private capsule vocabulary, not a public code).
   (b) *Leave states, gate on `acceptedUnder != heads.root`* — rejected: the join consumes raw states, so a `TRUSTED`-under-the-old-root CORE would still permit continuation unless the host derives a different state, which is the scalar/derived pattern root has ruled out.
4. **How other revoked roles recover without laundering or old keys:** only by their own `EV-RECOVER-COMMIT` with an authorization naming them — either the *same* authorization (hence `roles` is a list, so a publisher can recover several roles with one new root and the host dispatches per role) or a later one signed under the **new** head's `recoveryAuthority` with `newRoot == head`. Ordinary PRESENT never reaches them (v14: "ST-REVOKED is not this member").
5. Ordinary S5 chain rotation is unchanged: an ordinary payload is dispatched to every role by the host (v2 §4.7 "every role's state shown"), each accepted entry updating that role's `acceptedUnder`.

**Existing vs new:** the single root/counter, S5, per-role ceremony identity and "never TRUSTED by silence" are existing; `acceptedUnder`, rules 1–3 and the `roles` list are proposals.

## 3. Genesis — absent clock is necessary, but not as the equivalence I wrote

**Exact owner [E]:** S&L S4, decision evaluation step 2 (l.415–419): "**Fresh install (F absent)**: without admitted time evidence the evaluation refuses `TRUST.NO_ADMITTED_TIME_CONTEXT` (the core's embedded bootstrap payload or an ordinary payload is required); nothing is written. With it, W > A + 90 d refuses `CLOCK-EXCURSION-FORWARD` and initialises nothing. Otherwise tEval = max(W, A); **F := tEval, L := A, anchor := (B, M, W)**; expiry states are evaluated from the presented documents, never set to false." The model agrees (`clock_decision`: "fresh install when evalHighWater is None").
Consequences **[E]**: (i) creator/bootstrap documents do **not** seed counters without a TRUSTED-entry — the embedded bootstrap payload is itself an ordinary payload that must be presented; (ii) the write-ahead happens **before** the entry outcome, so a validly signed but expired/rejected first payload leaves durable `evalHighWater`, `lastAccepted`, `anchor` and **no accepted root**; (iii) the closed record cannot hold that state (`rootVersion/indexSnapshotVersion/revocationVersion: I64Positive`, all eleven required). So an absent *retained record* is necessary, and so is a place for the three written members.

**[P] Minimum closed distinction** (no member added to the 11-member record):
```
"clock": null                                                     // nothing ever evaluated with admitted time evidence
       | { "pregenesis": { "evalHighWater": ts, "lastAccepted": ts, "anchor": Anchor|null } }   // S4 step 2 wrote; no accepted root
       | { "retained":   { …exactly the 11 TrustClockRecordV1 members… } }                       // after the first accepted TRUSTED-entry / RECOVER-COMMIT
"heads": non-null  ⇔  clock is "retained"
```
Monotone: `null → pregenesis → retained`, never backwards; on the step to `retained` the three members carry over by the floor law (`evalHighWater`, `lastAccepted` never decrease).
**[P] What I withdraw from my reconciliation note §1:** the chain `clock == null ⇔ heads == null ⇔ eventHead may be null ⇔ all roles initial`. It would have banned exactly what root lists. Replacement invariants, deliberately one-directional:
- `clock` not `retained` ⇒ every role `bootstrap.kind == "initial"` and `acceptedUnder == null`. **Not the converse.**
- `eventHead` is unconstrained by phase: refused attempts are audited before any acceptance (v14 "Every ATTEMPTED event"), and S4 refusals in pregenesis are attempts.
- `ceremony.staged` (and `begun`) are lawful in any phase: v14 stages and BEGINs from `ST-UNBOOTSTRAPPED` ("including from ST-UNBOOTSTRAPPED"); authority is then the embedded anchor (Q1/Q2).
**Role `initial` vs `reset` when other roles have accepted metadata:** `initial` is a fact about *that role* — it has never had an accepted TRUSTED-entry or RECOVER-COMMIT, hence `acceptedUnder == null` — and is independent of the global record. `TR-BUNDLE` or a typed-absent `TR-REPAIR` can be `initial` beside a `TRUSTED` CORE with a `retained` clock. `reset` requires `acceptedUnder != null` (the role provably had standing) plus the resolvable reset evidence; an audit reason is never the proof. v14's "`EV-REVOKE` from `ST-UNBOOTSTRAPPED` refuses" then applies precisely to `acceptedUnder == null` roles — which makes the 208-successor conditional input a statement about `acceptedUnder`, not about a reason flag.
