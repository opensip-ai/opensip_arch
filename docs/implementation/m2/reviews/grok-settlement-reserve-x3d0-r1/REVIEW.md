## Item 8 and the X3d-0 unit

The reserve is owner-only. `reserve_settlement` and `settle` are inherent methods on `WorkLedger`. `WorkScope` and `ReservedPostchecks` have neither. The eight `compile_fail` doctests pin clone, a second `settle` of a moved reserve, `Default`, a struct literal, and both methods on `WorkScope` and on `ReservedPostchecks`. `lib.rs` re-exports `SettlementReserve` once, beside `WorkLedger`, `WorkScope` and `ReservedPostchecks`.

Taking it charges through the existing `charge` while `prepaid` is `None`, so the cost lands in `used` immediately and is never refunded. `BudgetFailure` gains no variant. A closed ledger, a second reservation, and a cost past the remaining limits return `Closed`, `Objects`, `Edges`, `Bytes` or `Arithmetic`, take nothing, and latch. A second call is `Closed` whether the first reserve is still outstanding or already `Spent`, and the outstanding token stays spendable because `settle` does not consult `failed`.

`SettlementReserve` has private fields and no derives, so it is not `Clone`, `Copy`, `Default`, `Debug` or `PartialEq`. The platform has no serde. `reserve_settlement` is the only constructor. The issue number is a process-wide `AtomicU64` starting at 1. `fetch_update` stores `n + 1` only when `checked_add` succeeds and returns the previous value, so numbers are unique inside the process and are not reused. Exhaustion returns `Arithmetic` and latches before `charge`. A reserve is not `Send` across a process restart in any way that matters: the value is in-memory and not serializable, and ledgers do not outlive the process.

`settle` moves the reserve in. If `settlement` is not `Reserved(issuer)`, it sets `failed` and returns `Closed` before `action`. Otherwise a `Settling` guard saves `prepaid` (none, at the owner: a live scope holds `&mut WorkLedger`, so `reserve_settlement` and `settle` cannot run inside `prepaid`), installs the allowance in that same slot, and sets `Active { latched: false }`. `action` runs through ordinary `scope`. On `Ok`, `Err` or unwind the guard restores the saved credit and sets `Spent`.

Inside `Active`, `closed()` is the settlement latch and `latch()` sets both `failed` and that latch. `charge` with `prepaid` set subtracts from the credit and does not touch `used`. Nested `effect` still charges its total once up front; nested `prepaid` saves that credit, carves its own, and restores the reduced allowance on drop. An overrun is `checked_sub` failing with `ReservedPostcheck` before the action that would have used it. A returned `Err`, a swallowed nested `Err`, and an unwind all latch both, so a later step in the same `settle` is `Closed`. Nothing adds to the allowance. After `Spent`, another `reserve_settlement` is `Closed`.

## Judgment calls

1. **Instance binding.** The issue number is the right binding. It moves with the ledger, it does not borrow the ledger, so X3d-1 can store the reserve in `StoppedSession` while the attempt ledger is in use, and ledgers that never reserve do not draw one. Pointer identity breaks if the ledger moves. A lifetime on the reserve would hold the ledger borrowed for the whole attempt. An id stamped in `new` and `with_limits` would touch every ledger since 412. Drawing before `charge`, and refusing `Arithmetic` without charging when the counter cannot advance, matches the law's "takes nothing".

2. **Return type.** `reserve_settlement` returns `Result<SettlementReserve, BudgetFailure>`. It runs no operation, so there is no `E`. `settle` returns `Result<T, Failure<E>>` because `action` can fail operationally. That split matches item 8.

3. **A foreign reserve.** The refusal latches the instance it was offered to and does not run `action`. If that instance holds `Reserved(its own issue)`, the state stays that way, so its own `settle` is still admitted after the latch. The tests cover a target with no reserve and a target with its own. The moved token is gone on the issuer. The issuer's `failed` and `used` are unchanged, and its state remains `Reserved`, which refuses a second take. The issuer is not reachable from the refused call.

4. **A second reservation.** `settlement != Untaken` is refused `Closed` and sets `failed`, both while a reserve is outstanding and after `Spent`. The outstanding token still settles. A refusal on an already closed ledger, or a charge that fails the limits, leaves the state `Untaken` and the latch set, so every later reservation is `Closed`. A failed charge burns the issue number it drew and returns no reserve. That number is never installed, so it cannot be presented later.

5. **A successful settlement on an open ledger** does not set `failed`. The guard still moves the state to `Spent`. Ordinary `charge` works afterwards, and `used` stays at the reserved cost. Dropping the token unspent leaves `Reserved` and `failed == false`; the charge stays in `used`. There is no `Drop` impl that refunds, and no second constructor. Item 8 allows that drop.

6. **`is_failed`.** It reports the permanent flag on `WorkLedger` and on `WorkScope`, including inside `settle`. Scope admission uses `closed()`, which is the settlement latch only while `Active`. Changing `is_failed` to follow that latch would make an already-failed attempt ledger report success for the duration of `settle`. The production readers of `is_failed` are the attempt, admission, session and read gates, which run outside `settle`. No journal append path reads it. X3d-1's end path has to call `settle` and then append, and must not treat `is_failed()` inside that `settle` as "the allowance is closed".

7. **The allowance is the existing `prepaid` slot.** `charge` already draws from `prepaid` when it is set and leaves `used` still. `Settling` and `PrepaidCredit` are the same save/restore. Nested `effect` then `prepaid` is one draw of the effect total from the settlement allowance, then a carve inside it. There is no second accounting path.

8. **The source pin.** Item 8's one-caller sentence and item 13's pin are X3d-1's, because that is when `StoppedSession`'s end-path step and `finish` exist. X3d-0's `no_production_source_reserves_or_settles_yet` is that property with zero admitted callers: every `.rs` file under `crates/` and `apps/`, other than `tests/`, `target` and `node_modules`, may name `reserve_settlement` or `SettlementReserve` only in `work_ledger.rs` and `lib.rs`, and `lib.rs` names `SettlementReserve` once and does not name `reserve_settlement`. It does not search for `.settle(`. `ordinary_writer.rs` has an unrelated private `settle`, and `lib.rs` has `settled`. A `WorkLedger::settle` call needs a `SettlementReserve`, and the only constructor is `reserve_settlement`, so forbidding both names excludes both methods. X3d-1 replaces this pin with the one-caller pin. The API can carry that pin: both methods are on the owner's `WorkLedger` only, and the reserve is a distinct type.

9. **No `Debug`, `PartialEq` or `#[must_use]`.** Item 8 requires private fields and forbids `Clone`, `Copy`, `Default` and serialization. It allows dropping a reserve unspent, which is the forfeit, so `must_use` would warn on a lawful drop. A zero-cost reserve is a successful `charge` of zero. The law sets no minimum.
