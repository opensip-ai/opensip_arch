## 2. Residual contradictions and gaps inside A–C.1 and D

### K-1 — `release` is in the PROSPECTIVE frame but not in the OLD frame (my table caused this)
C.1: OLD role subjects = "namespaces admitted for that role by its acceptedUnder root and its accepted catalog snapshot"; yet "A prospective namespace/catalog/**release** that is revoked refuses activation." v14 defines role revocation over "this role's current **snapshot or namespace**" only. `release` (and `keyId`) are *not* role-level subjects: a revoked release is a member-level inadmissibility (that manifest is refused; registry status `revoked`) and an S6 closure match — which C.1's own first paragraph keeps distinct. As written the two frames are asymmetric: a release revocation can block a whole recovery commit but can never revoke a role. I introduced "delivered release" into the PROSPECTIVE column in my assistance; that was a mistake. Fix: role-level frames (both) = namespace(s) + TR-INDEX catalog snapshot; `release` → member admission and S6 only; `keyId` → signature filtering and availability only.
Related owner choice to state, not a contradiction: a role may be delegated **several** namespaces (root schema: `namespaces` list). v14's singular "namespace" does not say whether one revoked namespace revokes the role or only that namespace. The conservative reading (any hit ⇒ `REVOKED`) is v14-faithful but makes a one-namespace revocation require a ceremony; whichever is chosen must be the same in both frames.

### K-2 — null `acceptedUnder` and the RECOVERY exits
C: "Null is allowed for a role that has NEVER established standing even if observations moved it from UNBOOTSTRAPPED." Checked against the machine: from `ST-UNBOOTSTRAPPED`, `EV-REVOKE` refuses and `EV-QUORUM-OBSERVE` is an accepted *stay* (211's full 7×4 test pins this), so the only way a never-established role moves is `EV-RECOVER-BEGIN → ST-RECOVERY`; and from `ST-RECOVERY` v14 names `EV-REVOKE → REVOKED` and below-threshold `EV-QUORUM-OBSERVE → QUORUM-LOST`. Under C.1's subject projection a null-`acceptedUnder` role has **no** OLD subjects, so a role-level revoke guard can never be true for it — consistent, but only if the producer is required to assert `newer_and_byte_valid = false` when the role has no subjects; today that boolean means only "newer and byte-valid". And for the quorum exit, *which root's role key set* is "available" for a role with no `acceptedUnder`? Nothing says. Minimal statement: availability is evaluated against the role's `acceptedUnder` root's key set filtered by the retained revocation history; a null-`acceptedUnder` role has no key set and therefore no `EV-QUORUM-OBSERVE` transition (accepted stay). Then "null forever" is coherent: such a role is only ever `UNBOOTSTRAPPED`, `RECOVERY`, or (after commit) `TRUSTED` with a non-null binding.

### K-3 — two quorums need their root stated once
C.1 separates "signature quorum" from "available-key quorum" but never says under which root each is computed once `acceptedUnder` and the head can differ (they differ after an ordinary rotation that one role accepted and another refused — v2 §4.7's "Payload carrying catalog 7 after 9 was accepted" row is exactly a per-role refusal inside an otherwise accepted payload). Proposed one-liner: *document signature quorums* use the root under which that document is being admitted (head, or the prospective root in a ceremony); *role available-key quorum* uses the role's `acceptedUnder` root. And state the reason for the asymmetry r4 already has: an **ordinary** head advance preserves other roles' standing because S5 proves continuity from the old root's keys, whereas a **recovery** head change breaks continuity and therefore resets them. Without that sentence `ROOT_CHANGED`-on-recovery-only reads as arbitrary.

### K-4 — the S4 write-ahead revision is not part of the "ONE capsule revision"
C: "Any refusal commits no role/head… publish ONE capsule revision: shared root/head/floor advances once". D: P0→P1 and every later decision write `F`/`L`/anchor **before** the decision (S4 write-ahead), "even if later role admission fails". So a dispatched COMMIT (and a dispatched staging) is *two* publications: the clock write-ahead revision, then the outcome revision. A refused COMMIT therefore does change durable state — `evalHighWater` (and possibly `L` with its witness) — while committing no role/head/counter. Both halves are lawful; the text should say so explicitly, name "floor" in C as the *root counter floor* (not `evalHighWater`), and D's owed crash rows must include "write-ahead published, outcome not". Otherwise C's "no effect on refusal" and D's "never erase a floor after an unsuccessful import" read as contradicting each other.

### K-5 — `timeEvidence` must not be a re-admission precondition
D: T's "proof must be sufficient to re-admit the witness from the immutable core anchor/current authority". After a **core update** the embedded anchor is a different (later) root, and after a root ceremony the "current authority" changed; a P1 witness authenticated from the old anchor may no longer chain from the new one. If re-admission of T were required to *use* the clock, a lawful S9 core update could make the clock phase unavailable — a new way to brick trust state, and S4 itself never re-validates why `F` was raised ("F only rises"). Proposed: T is **provenance**, verified once before the write-ahead and retained as an immutable locator with its proof; later inability to re-verify T is a diagnostic, never makes `F`/`L` unusable and never lowers them. (`L`'s later uses — S4.5's "no floor below L", `issuedAt ≥ L` — depend on the value, not on re-proving it.) Minor: in phase `retained`, `evalHighWater` is set, so by existing law `lastAccepted` is non-null and T can never be null there; the "null only where the existing record law permits null L" clause has no reachable case.

### K-6 — P1 with no payload
D gives P1's three document times as null and says presented expiry fields are passed per evaluation. An evaluation in P1 *without* a payload (any decision-mode command) has `F` present, so S4 step 2's fresh-install rule no longer applies and steps 3–5 run with null document times. The reference's freshness gate already fails closed on non-`False` states, but D should say it: in P1 null accepted times mean **unknown**, never "not expired", and no operation that needs an admitted trust state proceeds in P1.

### K-7 — a standing reset is a state change with no v14 event
`ROOT_CHANGED` (and `RESTORED`/`MIGRATED`) move a role `TRUSTED|EXPIRED|STALE|QUORUM-LOST → UNBOOTSTRAPPED`. None of v14's nine events produces that transition (abort's fallback is the only path *to* `UNBOOTSTRAPPED`, and only from `RECOVERY`), and v14's audit record is `{role, from, to, event, …}` with a closed event set. r4 requires "every induced reset is evidenced" but gives the evidence no event identity. Either the capsule writer mutates role state outside the interpreter — which undercuts "event-driven state" and the per-role audit trail — or a private *standing-reset* operation is added to the kernel successor and the audit vocabulary. This is a real amendment, not wording; see §3.
