## 1. What is already owned
1. **Portable baseline needs no import at all. [E]** workflows §2: the artifact "lives in the repository as tracked intent (`opensip.baseline.json`)"; "**Fresh CI.** Comparison never reads the origin machine's store. A fresh host admits the artifact by recomputing `baselineId`, checking schema major, recipe major, sortedness, context-document digests and project correspondence (same ProjectId, or explicit `--accept-origin`, else `BASELINE.PROJECT_UNMAPPED` and no comparison). It resolves each pivot closure from (a) a retained generation, (b) an installed signed release with the same `closure2`, or (c) the signed closure bundle; all under **current trust**." So `baseline adopt`'s input contract is the tracked artifact plus current-trust closure resolution; the origin Run is *pinned*, never transferred.
2. **Backup/export and import data law. [E]** identity §5 (l.1797–1805): "Backup/export holds a read snapshot plus short-lived object pins, writes a bounded relative-path inventory, hashes and verifies every object, then seals the bundle. Import checks path traversal, symlinks, sizes, duplicate paths, cryptographic identities and all referenced schemas before publishing anything. Source provenance/authenticity is reported separately from hash integrity. Trust floors, current authorization and local custody receipts are never restored backwards from an evidence backup … An import cannot silently claim a remote Run was locally evaluated: its imported-custody receipt names origin and local verification." The pin kind exists: **[E]** workflows l.1605–1607 "`baseline`, `repair-prerequisite`, `backup-export` or `other-authorized`".
3. **Who owns Run identity and replay. [E]** identity l.1580–1592: "independently reconstruct every subject … then reconstruct evidence, seal and Run IDs … The public identity-model.v3.close_run boundary performs complete replay … Cache and storage admission against an authoritative Run inherit the complete replay requirement." **[E]** l.1850–1855: "Verified restoration requires the same complete identity closure and replay result before availability returns to retained; a regeneration mismatch refuses." **[E]** l.1748–1752: availability is "a separate monotonic-generation record … Availability may improve through verified restoration or regeneration; sealed assurance and historical verdict never change." `run3` is content-derived, so the same Run has the same id on every machine; what is local is *custody and commitment*, not identity.
4. **Project identity. [E]** identity §1 (l.47–60): "Missing marker and registry is first use; agreement is reuse; either unilateral or contradictory presence is an admission refusal requiring explicit recovery/adoption. It never silently chooses one identity … Explicit adoption from an admitted portable project bundle preserves a ProjectId after showing its source and target; it never imports another machine's local authorization, credentials, leases or execution receipts … A root move preserves ProjectId only through an authenticated registry move with no live writer; duplicate simultaneous roots for one local namespace refuse."
5. **Transport seam for a new mutation. [E]** workflows l.142–152: the generic `mutation` step binds to "the command's row in `byCommandGenericMutationStep`" with "`MutationParams.mutationClass`, equal to `MutationReplayScopeV1.operation`"; binding is "by **step kind and not by request class**". A new command can therefore be a `mutation` step with a new `mutationClass`, with **no new step kind and no new `import2` kind**.
6. **[U]** I found the phrase "imported-custody receipt" exactly once (identity l.1805) and no schema for it in the 201 candidate. Its owner is identity §5; its closed shape is owed.

## 2. Proposed minimal successor **[P]** — two inventory rows, one flag
| | `evidence-export` | `evidence-restore` |
|---|---|---|
| CLI | `opensip evidence export PATH [--run run3:…]…` | `opensip evidence restore PATH [--adopt-origin PROJECTID]` |
| requestClass / steps | `mutation` / `mutation, render` | `mutation` / `mutation, render` |
| authorizationClass | `user-consent` | `user-consent` |
| lease | APPEND-WRITE on the project (it writes host-ledger pins) | APPEND-WRITE (adds immutable objects and rows, deletes nothing — S7's definition) |
| `mutationClass` | `evidence-export` | `evidence-restore` |
| flags | — | `--adopt-origin`, `--allow-backup-custody` (S3.1 join, as on `import`) |
| parity fields | bundle seal digest, run count, receipt-id, termination-class | per-Run outcome counts, receipt-id, termination-class |
**Bundle (owned by identity §5, shape owed [I]):** a sealed, bounded relative-path inventory of *evidence objects* for named sealed Runs of one origin ProjectId — each Run's complete identity closure and, for replayable Runs, the input closure — plus origin ProjectId, origin host release and export time as **custody metadata outside identity**. It contains **no** store marker, ledger/journal/SQLite file, lease, witness, grant, execution or custody receipt, trust object, floor or registry row; any such member, like any traversal/symlink/duplicate/oversize member, refuses the whole bundle before anything is published (the "hostile archive import" criterion).
**Restore semantics — per Run, all under CURRENT trust, nothing published until the whole bundle verified:**
1. Resolve every closure by the three inherited current-trust paths (retained generation, installed signed release, signed closure bundle); missing/revoked/incompatible ⇒ that Run is reported unavailable, never executed, never half-admitted.
2. Run the inherited complete replay through `close_run`; the reconstructed `run3` must equal the bundle's claimed id ("a regeneration mismatch refuses").
3. Then exactly one of: **(a)** the Run is already sealed locally and only its availability was partial/corrupt ⇒ availability generation advances to `retained` (inherited "verified restoration"); sealed assurance, verdict and the original local receipts are untouched. **(b)** the Run is unknown locally ⇒ it is recorded with an **imported-custody receipt** `{origin: bundle seal digest, origin ProjectId, origin host release; localVerification: replay result, closure trust origins, host release, admitted time}` and **no** local execution receipt, grant or commit-authority claim. Queries and reports show `custody: imported` beside the unchanged Run identity; it can be a baseline/comparison source only where those contracts already accept a replay-verified Run with its closures pinned.
4. Nothing under `I/trust`, `selection.pair`, lineage, journals' history or other projects is read for authority or written. If current trust is unavailable, behind, forked, poisoned or P0/P1, the restore is **unavailable** — it is not a recovery path for trust.
**Project adoption is request data, not an interactive approval.** `--adopt-origin PROJECTID` must equal the bundle's origin ProjectId; the *target* is the invocation's already-admitted project root; the rendered receipt shows both. Marker × registry cases at the target:
| Target marker | Registry | Without flag | With `--adopt-origin` = bundle origin |
|---|---|---|---|
| same ProjectId | agrees | restore | refuse: already this project (flag is redundant, never a rebinding) |
| absent | absent for this root **and** origin id unbound on this machine | refuse `PROJECT_UNMAPPED`-class: target has no identity | **adopt:** write marker with the preserved ProjectId, bind a **fresh local** namespace UUID, fresh journal/generation; then restore |
| absent | origin id already bound to **another** root | refuse | refuse — inherited "duplicate simultaneous roots … refuse"; moving is the separate authenticated registry move |
| different ProjectId | any | refuse | refuse — adoption never overwrites an identity; a fork is a new id with origin metadata (inherited) |
| present, equals origin | none (unilateral) | refuse (inherited) | adopt binds the registry only if the id is unbound elsewhere |
| none | present (unilateral) | refuse (inherited) | refuse — registry-only repair is **[U]**, not this command |
A differing origin without adoption (restoring project A's evidence into project B) always refuses; there is no `--accept-origin` analogue for whole Runs, because a Run's identity already commits its ProjectId.

## 3. Conflict with S9.3's "fresh S" — real, textual, and resolvable only by an explicit clarification
**[E]** S9.3: "A root is created by an authorized local act that materialises a new physical store outside any transition: installation, or an authorized evidence restore or portable adoption. Such an act allocates a fresh `storeInstanceId`, **replaces** any marker present in copied bytes …"; build plan l.382: "An evidence-bundle restore or portable adoption allocates its own identity". Read literally these say restore/adoption *is* a store-materialising act that copies store bytes. Under §2 no physical store is copied or created, so nothing can receive a fresh S, there is no marker to replace and no lineage root to write — the condition of S9.3's rule is never met. That is not a contradiction in behaviour (every prohibition in S9.3 — no node, floor, grant, commit authority imported — is kept, more strictly), but the wording will mislead an implementer into copying a store. **[P] clarification to adopt with the commands:** *"Evidence restore and project adoption as defined by `evidence-restore` publish verified objects into the currently selected store; they materialise no store, allocate no `storeInstanceId` and write no lineage node. S9.3's lineage-root rule governs only an act that materialises a physical store; besides first installation no such act is currently owned."* This also removes the collision I described in 228 §3 (fresh same-schema store vs per-namespace journals and floors).

## 4. How the acceptance criterion is met
"Backup restoration preserving trust floors" has two layers, both now with an owner: **evidence level** — this command never touches `I/trust`; the demonstrable property **[I]** is that the capsule, floors, journal floors and pair are byte-identical across every restore outcome and crash point, and that a bundle carrying trust/floor/receipt members is refused; **installation level** (a system backup restoring the install root) — 222's `acknowledge-restore` with the predecessor-keyed successor check, which keeps or re-raises floors and resets standing. Neither lowers a floor; neither imports authority.
