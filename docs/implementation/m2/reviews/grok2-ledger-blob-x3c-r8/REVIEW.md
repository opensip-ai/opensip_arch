## Identity and IE

6a.1 is the reading IE:104-107 and IE:1683 require. A RunId is content identity. ExecutionIds, receipts and operation references are excluded from it, so a second attempt of the same inputs is the same Run. The retry receives a new ExecutionId, its own attempt row, SEAL, receipt, association, Run-material row and the next `commitSequence`, and it ends `Committed(PublishedCommit)`. Returning the earlier receipt, refusing, or reusing the earlier attempt are the rejections the law states, and each contradicts IE:1683, J1 item 11, or `ac_no_replace`.

6a.4's reading of the commit order is lawful, and it does not need an IE passage successor. IE:1670-1673 lists what one transaction inserts when it establishes the Run: manifest, object references, the retained availability generation, the pins, and a receipt. IE:1683 then says a duplicate retry can share that Run and has a separate attempt receipt. IE:1721-1724 makes availability a separate monotonic-generation record, and IE:1814-1815 says a transition increments generation and does not rewrite a sealed Run. Inserting generation 0 again is the M2 defect (`availability_stale_generation` / `availability_no_replace`). The retry's transaction inserts the separate receipt and the per-attempt material and leaves the shared per-Run rows as they are. The regeneration-mismatch sentence (IE:1825-1827) is the refusal for material that does not match, which 6a.3 uses. The law does not claim availability regeneration; 6a.4 leaves that to the retention owner, with SL:1456.

## Standing

The standing read is inside the open level-3 transaction, before any insert, and it reads only the Run's current availability (`load_current_availability`, `ledger_store.rs:805-823`) and whether any `commit_run_material` row names the RunId. Neither row means a first commit, staged as r7 stages it. Both mean a re-commit. Exactly one is the existing item-10 quarantine row: `LEDGER.CORRUPT`, `ledger-corrupt`, `domainDetail` omitted. Both tables refuse delete (`availability_no_delete`, `run_material_no_delete`), and item 6 writes both or neither, so a one-sided Run is storage damage.

The writer lease and `BEGIN IMMEDIATE` (`ledger_store.rs:838-840`) exclude a second writer of the namespace across the read and the inserts. A second generation-0 insert still hits `availability_no_replace`. Standing does not read attempt phase, SEALs, objects or uncommitted state. An orphan SEAL therefore leaves a first commit (X9:1129, F36). A landed commit whose attempt is still `admitted`, or that was reported `CommitUndetermined`, leaves both per-Run rows, so the next commit is a re-commit and does not settle or rewrite the earlier attempt. That is the boundary J-RW:79-81 and J-RW:427 require, and item 15.2 cites it.

## Material equality

The comparison target is the material row of R in (S, N) with the least ExecutionId in byte order. ExecutionId is text, so the order is fixed. Every committed material row entered as the first commit or after passing the same comparison, and `run_material_no_update` blocks an in-place change, so the rows of a lawful history are identical. A mismatch refuses on the invariant row. That is the right row: the writer cannot tell a replay defect from a stored row changed outside this law, and `LEDGER.CORRUPT` would call the first one storage damage. The law rejects comparing every row; the induction is the reason that rejection is sound for writes this product can make.
