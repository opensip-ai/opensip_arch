## 2. What existing law actually says
1. **[E] There is no restore, adopt-store, backup or evidence-export command.** `command-inventory.v3.json` has 45 rows. The relevant ones are `import` (`opensip import KIND PATH --snapshot ID | --commit SHA [--build ID]`, mutation, APPEND-WRITE, flag `--allow-backup-custody`), `baseline export PATH [--closure-bundle PATH]`, `baseline adopt [--run run3:…]`, `purge`, `store migrate --to 2`, `store rollback --to 1`, `store gc`, `store status`, `core update|repair|rollback`. Workflows l.1099 lists the mutation class as exactly "`import`, `baseline adopt|export|upgrade`, `policy init`, `waive`, `review join`, `repair apply`, `repair recover`, `purge`".
2. **[E] Identity §5 describes the *data law* of backup/export and import, not a store act.** "Backup/export holds a read snapshot plus short-lived object pins, writes a bounded relative-path inventory, hashes and verifies every object, then seals the bundle. Import checks path traversal, symlinks, sizes, duplicate paths, cryptographic identities and all referenced schemas before publishing anything. Source provenance/authenticity is reported separately from hash integrity. **Trust floors, current authorization and local custody receipts are never restored backwards from an evidence backup.** … An import cannot silently claim a remote Run was locally evaluated: its imported-custody receipt names origin and local verification." Availability "may improve through verified restoration or regeneration; sealed assurance and historical verdict never change." "backup restoration preserving trust floors" is listed as an *implementation acceptance criterion*, "not unresolved design alternatives".
3. **[E] Identity §1 — project-level adoption.** "An ordinary fresh clone gets a fresh ProjectId. Explicit adoption from an admitted portable project bundle preserves a ProjectId after showing its source and target; it never imports another machine's local authorization, credentials, leases or execution receipts." Marker/registry disagreement is "an admission refusal requiring explicit recovery/adoption".
4. **[E] Build plan.** "Maintenance cannot insert an authoritative Run by using a restore or migration helper: imported evidence is revalidated before local adoption"; "An evidence-bundle restore or portable adoption allocates its own identity, restores no trust floor and grants no local authority … Portable adoption is a fresh locally authorized attempt, not recovery of local authority from a backup."
5. **[E] S9.3 lineage roots.** "A root is created by an authorized local act that materialises a new physical store outside any transition: installation, or an authorized evidence restore or portable adoption. Such an act allocates a fresh `storeInstanceId`, **replaces** any marker present in copied bytes …, imports no node from the source, and imports no floor, grant or local commit authority. No transition is invented to give it an `intentDigest`." This says what such an act must do **if** it materialises a store; it names no command, no selection step and no trust-capsule rule.
6. **[E] Selection changes are owned only by the five S9.2 operations**, and "a same-schema core operation keeps the store"; `store migrate`/`rollback` require a schema change. S4.5: if recovery authority is unavailable "the install must be re-established by fresh install or authenticated adoption" — *authenticated adoption* is named once and defined nowhere I read.
7. **[E] Prototype boundary.** "There is no prototype Run/baseline/state importer in this product … a separately admitted current-format observation may enter only through the ordinary closed import registry."
8. **[E] Per-namespace custody lives outside stores.** PSL: journal, witness and leases at `host/projects/N/…`, journal floors at `trust/journal-floors/N/G.floor`, ledger at `stores/S/projects/N/ledger.sqlite`.

## 3. Reading: is a selection change required at all?
**No existing text requires restore/adoption to change the selected store, and the texts that describe the user-visible behaviour (2–4) are all about *evidence entering a locally admitted store* with imported-custody receipts.** Only S9.3 speaks of a materialised store, conditionally. Moreover a same-schema fresh store selected under existing namespaces would collide with retained custody: the namespace journal and its high-water floors (item 8) would face an empty ledger in the new S — exactly the shape S7's rollback/`witnesslessRestore` detection exists to refuse. So "select the adopted store" is not merely unowned; with today's joins it is self-contradictory unless namespaces, journals and floors are also replaced, which identity §1 ("preserves a ProjectId") and "never restored backwards" forbid.

## 4. Recommended smallest complete direction **[P]**
**Adoption and restore are project-scoped evidence imports into the currently selected store. The selection pair never changes; no store is materialised; no lineage node is written.**
| Concern | Rule | Status |
|---|---|---|
| Authorization | user-consent + APPEND-WRITE lease on the target namespace; S3.1 backup-custody choice before the first source-derived write | inherited |
| Trust roots / floors | the **current** capsule only. Nothing in a bundle touches `I/trust`; no root, floor, grant, lease or receipt is imported; imported material is re-verified under current trust and recorded as imported custody (origin + local verification), never as locally evaluated | inherited (§5, §1, build plan) |
| Lost / poisoned / unprovable trust | the import is **unavailable**; it is not a way around S4.5, 222's behind/fork/unavailable denial or a missing selected capsule; no fresh S, no foreign roots | inherited limits; stated here as a boundary |
| Source reset / source fence | none — there is no source store of this installation; no `RESTORED` reset is implied by importing evidence (222's `acknowledge-restore` remains the separate *trust* declaration) | inherited |
| Selection pair / lineage | unchanged; S9.3's lineage-root clause stays dormant until a store-materialising act has an owner | **[P]** reading |
| Project registry | preserved ProjectId binds to a **fresh local** namespace UUID when the project is not registered; agreement is reuse; disagreement keeps the existing refusal | inherited §1; the bundle-level command is **[U]** |
| Journal / custody / leases | the namespace's own journal starts or continues locally; nothing of the origin's journal, witness, leases or grant generations is imported | inherited |
| Crash | ordinary import step law ("an import discards its…" partial state) and S7; publish nothing until the bundle is fully verified | inherited |
| Old history | nothing is replaced or rewritten; existing Runs, commit rows and store history stay; imported Runs keep their origin identity and imported standing | inherited |
**What already works with no new law:** portable **baseline** transfer — `baseline export PATH --closure-bundle PATH`, then `import`/`baseline adopt` on the other side (workflows §2) — and per-kind `opensip import KIND PATH`.

## 5. Unknown or unowned scope — called out, not filled in
- **[U] Bundle-level backup/export and project adoption commands.** Identity §5/§1 describe their data law, but no inventory row exists for "export an evidence backup", "restore it" or "adopt a portable project bundle". Whether these are intended for this product version or deferred is not stated in the sources I read (`10-mvp-and-future-scope.md` has no restore/backup/portable entry). Recommendation: record an explicit **deferral** rather than letting S9.3's sentence imply a mechanism.
- **[U] "Authenticated adoption"** (S4.5) as the remedy when recovery authority is unavailable: named once, never defined. It must not be read as permission to mint fresh trust inside an existing installation; today the only defined outcome is a fresh installation (224) on an unused root.
- **[U] Replacing a lost or corrupt evidence store while keeping trust** (pair names S, `stores/S` gone or unusable, capsule intact). This is the one case that genuinely needs a *same-schema* selection change. It has no owner. If root later wants it, the minimum it would need is new law, all of it: a sixth S9.2 operation kind (same closure, same schema, new store), a lineage **root** node at `(S′,0,K)` per S9.3, a trust capsule for S′ produced by 222 continuity from the current capsule (floors/heads/history carried, standing reset, revoked-before-BEGIN preserved — a new continuity case, since forward requires a schema advance), an explicit rule for every namespace's journal/witness/floors against an empty ledger (the collision in §3), and the active-slot/journal crash table. I recommend **not** starting it now: it is a recovery feature for damaged local state, which root has said must not be solved by silent fresh-S replacement.
- **[U] Working-203 and 224** are unfrozen; I used them only as context. 224's statement that adoption selection "still lacks a complete owner" is accurate against the sources above.
