# Part 1 — R-2 precisely

## 1.1 My literal sentence was wrong
I wrote "a batch role revoked by the payload's own list makes the commit refuse". As root says, that ignores whose subject is revoked. The normal ceremony **revokes the old compromised key and installs healthy ones**; refusing that would make explicit recovery impossible in the very case it exists for. Withdrawn; the rule below replaces it.

## 1.2 What the existing owners actually say
- **[E] v14** `ST-REVOKED`: "**This role's current snapshot or namespace** is revoked by a newer accepted revocation observation." `EV-REVOKE` guard: "Newer byte-valid revocation observation. ACCEPT. Advance monotonic last-known revocation"; named sources TRUSTED/EXPIRED/STALE/QUORUM-LOST/RECOVERY/REVOKED; from `ST-UNBOOTSTRAPPED` the fallback **refuses**. So role-level revocation is about the role's *current* snapshot or namespace — not about any key.
- **[E] keys are a different axis.** v1 §4.1: a role whose *available* keys fall below threshold enters `ST-QUORUM-LOST` (`EV-QUORUM-OBSERVE`). The product filters revoked keys out of signature quorums (`filter_envelope_revoked`; test `quorum_state_is_created_only_after_revocation_filtering`). A `keyId` entry therefore affects (a) signature counting and (b) key availability; it does not by itself make a role `REVOKED`.
- **[E] the current native predicate is per-operation, exact-subject.** `trust.rs::observe_revocation(current, start: &EpochAtStart, closure: &ClosureSubjects, …)`: acts only when `current.version() > start.revocation_version` ("never revoke on a lower counter"), and matches each entry **exactly** by kind — `release ∈ closure.releases`, `keyId ∈ closure.signing_keys`, `namespace ∈ closure.namespaces`, `catalogSnapshot == closure.catalog_snapshot` — returning `Revoke`/`Continue` for *that running closure*. It is the S6 checkpoint predicate; it is **not** a producer of per-role `EV-REVOKE`, and no code today projects "this role's current snapshot or namespace". **[AMEND-0, naming a gap, not a law change]**: a *role-subject projection* owner is missing — for each role, the namespace(s) delegated to it by the root it was accepted under, and for TR-INDEX the accepted catalog snapshot number. Exact-subject matching should be reused from `observe_revocation`'s rules, not reinvented.
- **[E] a list is bound to one root.** `verify_revocation` refuses unless `list.rootVersion == root.rootVersion` and verifies the ROOT-role envelope under that root with `previously_revoked_keys` filtered. A recovery payload's list therefore carries the *replacement* version and can be authenticated only under the **prospective** root.
- **[E] counters advance only at commit** (v14 RECOVER-COMMIT: "Counters advance"; root cites the retained fixture). Nothing is accepted at staging.

## 1.3 Attribution rule [P]
Every entry of the payload's new list is compared, by exact subject, against two sets per role:
- **OLD** subjects = the role's *current* subjects before this publication (namespace under its `acceptedUnder` root; TR-INDEX: accepted catalog snapshot). Empty for a never-established role.
- **PROSPECTIVE** subjects = what the role would hold after this publication (namespace delegated by the replacement root; TR-INDEX: the payload's catalog snapshot; releases/manifests the payload itself delivers), plus — on the key axis — the replacement root's key set for the role.

| Entry hits… | Batch role | Non-batch role |
|---|---|---|
| PROSPECTIVE namespace / catalog snapshot / delivered release, or leaves the replacement root's role key set below its threshold | **refuse** (staging step 6 and again at COMMIT): the role cannot enter TRUSTED holding a revoked subject | n/a (it acquires nothing) |
| OLD key only (`keyId` of a superseded key) | **no role event.** Key is excluded from every quorum (already law); recovery proceeds | no role event; availability is moot because the role is about to be reset or is already restricted |
| OLD namespace / OLD catalog snapshot, and the PROSPECTIVE one is different | **no `EV-REVOKE`**; recorded as evidence on the role's RECOVER-COMMIT event (see 1.4) | **`EV-REVOKE` → `ST-REVOKED`** if the role is in a named source state |
| OLD namespace that the replacement root *re-delegates unchanged* | this is a PROSPECTIVE hit too → **refuse** | `EV-REVOKE` as above |

## 1.4 Exact dispatch order inside the single COMMIT publication [P]
1. Evaluate all batch RECOVER-COMMIT guards under the prospective context, including the PROSPECTIVE-subject check and the second-pass quorums. Any refusal ⇒ nothing commits, no counter moves.
2. For every **non-batch** role whose state is a *named* `EV-REVOKE` source and whose OLD subjects are hit: dispatch `EV-REVOKE` → `ST-REVOKED`, with its own event (evidence: list reference + matched entries). This is v14's named transition and it **takes precedence over the induced reset** — so step 4 never sees these roles.
3. Batch roles: `EV-RECOVER-COMMIT` → `ST-TRUSTED` with PROSPECTIVE subjects and the new `acceptedUnder`. OLD-subject hits are attached to that event as evidence; historical entries stay in the retained history (Q1: nothing shrinks). **No `EV-REVOKE` is dispatched to them** — and this does not ignore v14's precedence: after the commit the hit subject is no longer "this role's *current* snapshot or namespace", so the `EV-REVOKE` guard is false for it. A previously `REVOKED` role recovers exactly this way, through BEGIN/COMMIT, with its old revoked entries retained.
4. Remaining non-batch roles with established, non-revoked standing → `UNBOOTSTRAPPED`/`ROOT_CHANGED`. Never-established roles: untouched; **no `EV-REVOKE` is invented from `ST-UNBOOTSTRAPPED`**.
5. One capsule revision: `rootVersion`, `revocationVersion` (and catalog) advance **once, here**.
**[AMEND-1]** Steps 2–3 rest on an *interpretation* of v14 ("current" evaluated per role relative to the publication: pre-commit for non-batch, post-commit for batch). v14 never contemplated a revocation list accepted *by* a recovery commit, so this must be written as an explicit owner rule, not presented as already covered.

## 1.5 The residual that current law does **not** cover
A non-batch role that is *already* `UNBOOTSTRAPPED` with established history (`acceptedUnder != null`, reset earlier by ROOT_CHANGED/RESTORED/MIGRATED) whose OLD subjects are now hit: v14 refuses `EV-REVOKE` from `ST-UNBOOTSTRAPPED`, so the role stays `UNBOOTSTRAPPED` and an ordinary payload may later make it `TRUSTED` — provided that payload's subjects are not themselves revoked (the entry predicates and the retained history block a *revoked* namespace or snapshot forever). What is lost is v14's requirement that such a role recover only by ceremony. **[AMEND-2]** (the same one as my 214 §3 / reconciliation §8): the `EV-REVOKE` refusal from `ST-UNBOOTSTRAPPED` applies to `acceptedUnder == null` only. Without AMEND-2 this laundering path remains, narrowly, for already-reset roles; with it, step 2 covers them. The ancestor-carry reset (E) needs the same two steps in the same order against the merged history.

## 1.6 Two concrete examples
**A — old key out, new key in (must succeed).** Head root 5: TR-COMPONENT keys {K1,K2,K3}, threshold 2, namespace `opensip.components`; K2 is compromised; TR-COMPONENT is `QUORUM-LOST`. Recovery payload: replacement root 6 with TR-COMPONENT {K1,K3,K4}, same namespace; list v9 (`rootVersion` 6) = `[{keyId:K2, key-compromise}]`. Staging: authorization under root 5's recovery quorum; root 6 possession; manifest under root 6's TR-BUNDLE; second pass — K2 signed nothing relied on. COMMIT: PROSPECTIVE check — namespace not listed, available keys {K1,K3,K4} ≥ 2 ⇒ guard passes ⇒ `TRUSTED`, `acceptedUnder = 6`; `revocationVersion := 9` in the same revision. `keyId:K2` hits no role-level subject ⇒ no `EV-REVOKE`; the entry stays in history and K2 never counts again. *Refusing variants:* the list also contains `{namespace: opensip.components}`, or `{keyId:K4}`+`{keyId:K3}` (availability 1 < 2), or for a TR-INDEX batch `{catalogSnapshot: <the payload's own snapshot>}`.
**B — non-batch laundering (must not happen).** Head root 5, all roles `TRUSTED`; TR-INDEX's accepted catalog snapshot is 41. A ceremony recovers `[TR-CORE]` only; its list v9 contains `{catalogSnapshot:"41", defect}`. *r3 as written:* TR-INDEX → `UNBOOTSTRAPPED/ROOT_CHANGED`; a later ordinary payload with catalog 42 → `TRUSTED`. v14 would have sent TR-INDEX `TRUSTED --EV-REVOKE--> REVOKED`, recoverable only by ceremony. *With 1.4:* step 2 dispatches `EV-REVOKE` to TR-INDEX (named source, OLD snapshot 41 hit) before resets are computed ⇒ `ST-REVOKED`, preserved; the ordinary payload with catalog 42 then falls to `PAYLOAD-NOT-ADMISSIBLE` ("ST-REVOKED is not this member").

# Part 2 — pre-acceptance clock, poisoned floor, audit boundary

## 2.1 Existing rules
- **[E] S4 step 2** (S&L l.415–419): "Fresh install (F absent): without admitted time evidence the evaluation refuses `TRUST.NO_ADMITTED_TIME_CONTEXT` (the core's embedded bootstrap payload or an ordinary payload is required); nothing is written. With it, W > A + 90 d refuses `CLOCK-EXCURSION-FORWARD` and initialises nothing. Otherwise tEval = max(W, A); F := tEval, L := A, anchor := (B, M, W); expiry states are evaluated from the presented documents, never set to false."
- **[E] the clock kernel consumes six members** — `evalHighWater, lastAccepted, anchor, revocationIssuedAt, catalogExpiresAt, rootExpiresAt` (S&L l.2494–2497; model `clock_decision`, "fresh install when evalHighWater is None") — all nullable types in the schema; the three counters are `I64Positive`.
- **[E] bounded poison heals:** "An accidental forward wall is accepted only up to 90 d beyond signed evidence, so a wrong write is bounded and **heals as signed time catches up; a larger jump writes nothing**" (S&L l.446–448).
- **[E] S4.5 cannot apply before acceptance:** the challenge's `recordDigest` is over `{evalHighWater, lastAccepted, rootVersion, revocationVersion, indexSnapshotVersion, recoveryEpochSerial}`; the epoch requires "every counter equals the challenged record's counter exactly"; authority is "the **accepted root's** `recoveryAuthority`". No accepted root ⇒ no authority, no counters ⇒ no challenge can be formed.
- **[E] the declared path when S4.5 is impossible:** "If the recovery authority is unavailable, recovery is impossible and the install must be re-established by **fresh install or authenticated adoption**" (S&L l.521–522).

## 2.2 Exact pre-acceptance phases [P]
```
"clock": null                                                   // P0 unevaluated
  | { "evaluated": { "evalHighWater": ts, "lastAccepted": ts, "anchor": Anchor|null,
                     "revocationIssuedAt": null, "catalogExpiresAt": null, "rootExpiresAt": null,
                     "timeEvidence": DocRef } }                  // P1: exactly the kernel's six-member projection
  | { "retained":  { …the 11 TrustClockRecordV1 members… } }    // P2
```
- P0: store creation; stays P0 through `TRUST.NO_ADMITTED_TIME_CONTEXT` and through an implausible wall ("initialises nothing").
- P0→P1: the first decision evaluation with admitted time evidence — S4 step 2's write-ahead, whatever the entry outcome. The three document-derived timestamps are **null and must stay null** in P1: they describe *accepted* documents, and S4 evaluates expiry "from the presented documents". `timeEvidence` references the authenticated document that supplied A (so `lastAccepted` — set from *presented* evidence by S4 itself — is attributable); for a recovery payload, only after complete staging authentication (my R-3).
- P1→P2: first accepted TRUSTED-entry or RECOVER-COMMIT; `evalHighWater`/`lastAccepted`/`anchor` carry by the floor law, counters and the three timestamps come from the accepted documents, `recoveryEpochSerial := 0`, `pendingRecoveryChallenge := null`. Monotone; never backwards. No zero counter exists in any phase.
- `trust recovery-challenge` in P0/P1: **refuse** — there is no record of the required shape to digest; the existing `RECOVERY.REFUSED` family applies (`CONTEXT_SHAPE`/`PENDING_SHAPE` exist; which detail is an owner choice, no new code).

## 2.3 Is a schema-2 challenge/epoch for the pre-acceptance phase necessary? **No — a declared lawful path exists.**
1. *Reachable poison is bounded.* Under current S4 the only floor a pre-acceptance store can write is `max(W, A)` with `W ≤ A + 90 d`. That floor **heals** by existing law as signed time catches up: a later embedded or ordinary payload whose documents are still valid at `tEval = F` enters TRUSTED normally. Nothing needs lowering.
2. *Unbounded poison* (a floor years ahead) arises, per S4.5's own opening, from "the superseded rule, or … a restore" — not from the current pre-acceptance write. For a P1 store in that condition, the declared remedy is already in the text: **fresh install or authenticated adoption**. A pre-acceptance store holds no accepted metadata, no role standing, no evidence-bearing history that a fresh install would discard — it is precisely the case where that path costs nothing. This is not "resetting a floor": the floor of *that* store is never lowered; a new installation is established.
3. *What a schema-2 epoch would cost:* a second signed protocol whose authority is the embedded anchor's `recoveryAuthority` (the only authority available pre-acceptance), a `recordDigest` over a different field set, new fixtures and a new reader — all to rescue a state with nothing in it. It would also blur the separation root insists on: the embedded-anchor recovery authority already has one job pre-genesis (authorizing a *root* ceremony, 215 A).
**Recommendation:** no schema-2. State in the owner: (i) S4.5 applies only in phase `retained`; (ii) in `evaluated`, bounded poison heals by S4 and anything else takes the fresh-install/adoption path of S&L l.521–522; (iii) root recovery and clock-floor recovery stay separate in every phase. **[AMEND-3, small]** S4.5 should say explicitly that challenge creation refuses before the first accepted metadata — today that is only implied by the field list.

## 2.4 Early S4 `writes: []` vs mandatory per-event audit — an explicit boundary [P]
**[E]** S4: several refusals write **nothing** (payload-future, no time context, excursion); report-only returns `writes: []` and "Doctor never persists". **[E]** v14: "Every ATTEMPTED event — including guard failure and fallback — appends" an audit record. Read together they conflict only if "attempted event" is stretched to cover things that never reached a role machine. Proposed boundary, three classes:
1. **Report-only** (doctor/trust doctor/store status): no clock write, **no audit record, no capsule revision** — nothing durable of any kind.
2. **Pre-dispatch refusals in decision mode** — S4 steps 1, 2 and 4, parse/shape failures, custody or capsule *unavailable*: the machine was never invoked, so no v14 event was "attempted". No clock write and **no audit record is claimed**; the caller-facing refusal is the only product. (S4's "nothing is written" is then literally true.) This is the honest reading for root's concern: no fictional durable auditing on refused/no-write paths.
3. **Dispatched events** (an admitted capsule, the fence held, an event handed to a role machine — accepted *or* refused by guard/fallback): audit event file first, then one capsule revision moving `eventHead` (roles unchanged for a refusal). This is where v14's "every attempted event" applies. If that publication fails, the refusal result still stands and the missing record is a disclosed storage failure, never converted into an acceptance.
**[AMEND-4]** v14's audit sentence needs this scoping written down in the current owner, together with the overlap it resolves: `PAYLOAD-NOT-ADMISSIBLE` is both S4 step 1's pre-dispatch refusal (unaudited, nothing written) and v14's PRESENT fallback (dispatched, audited). Same public reason, two different durability outcomes — the owner should say which is which rather than let the vocabulary hide it.
