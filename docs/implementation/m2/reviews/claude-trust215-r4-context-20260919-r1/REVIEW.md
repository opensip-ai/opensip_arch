## 1. Which root supplies which context — existing law first

| Context | Owner of the key/time set | Citation |
|---|---|---|
| Signature quorum of a **document being admitted** | the root passed for that admission: `verify_quorum(root, role, namespace, message, signatures)` filters and counts against *that* root's role keys | **[E]** `trust.rs` `verified_envelopes`; test `quorum_state_is_created_only_after_revocation_filtering` |
| Acceptance of a **new root** | threshold of version N's keys **and** of version N+1's keys | **[E]** v1 §3.1 "Rotation follows the TUF root chaining rule" |
| Role **key availability** (`EV-QUORUM-OBSERVE`) | the role's keys "listed in the current accepted root document, not expired, and not revoked" | **[E]** v1 §4.1 |
| **Expiry** | root expiry → "`ST-EXPIRED` for every role when the root expires"; index snapshot expiry → `TR-INDEX` only; evaluated at `tEval` | **[E]** v1 §4.2 table; v8 §4.2 |
| **Revocation freshness** | every role | **[E]** v1 §4.2 |
| Role-level **revocation** | "this role's current snapshot or namespace" | **[E]** v14 `ST-REVOKED` |
| `acceptedUnder` | **[P] only**: (a) the exact local predecessor bound into a ceremony (215 A); (b) the frame for a role's OLD namespace/snapshot subjects after it has been reset. **It is not an availability, expiry or signature context.** | 215 r3/r4 |

**What existing law does *not* say [GAP-1]:** whether an ordinary import is atomic across roles. v14 treats PRESENT per role; v2 §4.7 shows every role each time but no row with a root change accepted by one role and refused by another; `airGapPayload.missingMember` refuses incomplete payloads but says nothing about partial *acceptance*. Until an "ordinary import atomicity" owner exists, **no rule should be built on head ≠ `acceptedUnder` for a non-reset role** — under r4 the divergence is only *established* for roles that were reset (ROOT_CHANGED, ancestor carry), which are `UNBOOTSTRAPPED` and have no availability question. My K-3 rationale ("rotation preserves standing because S5 proves continuity, recovery breaks it") is reasoning from **[E]** v1 §3.1, but its consequence for role standing is **[P]**.

## 2. `EV-QUORUM-OBSERVE` — precise cases

**[E]** v14: from `ST-UNBOOTSTRAPPED` the event is the accepted-stay fallback; from `TRUSTED/EXPIRED/STALE/RECOVERY` with "Observed signers < reserved threshold AND REVOKED does not also hold" → `ST-QUORUM-LOST`; from `QUORUM-LOST`, "Restored quorum also stays". **[E]** v14 precedence note: "ST-RECOVERY is deliberately not EV-CLOCK-preempted: a ceremony underway because predecessor metadata expired or went stale **must survive those predecessor conditions**. EV-REVOKE, EV-QUORUM-OBSERVE (below threshold) … still leave RECOVERY because those are named transitions."

### 2.1 Counterexample: the literal composition cannot complete a quorum-loss recovery
Head root 5; TR-COMPONENT keys {K1,K2,K3}, threshold 2; K2 and K3 revoked ⇒ availability 1 < 2 ⇒ `QUORUM-LOST`. Operator stages a payload with replacement root 6 and BEGINs ⇒ `RECOVERY`. Any `EV-QUORUM-OBSERVE` now evaluates **[E v1 §4.1]** "the current accepted root document" — still root 5, still 1 < 2 — and **[E v14]** the named transition fires: `RECOVERY → QUORUM-LOST`. The batch is interrupted (r4 C) and can only be aborted. The ceremony exists precisely for this case and can never reach COMMIT if an observation is dispatched. This is a defect in the *composition of two existing texts*, independent of anything I proposed; and it sits oddly beside v14's own sentence that a ceremony "must survive those predecessor conditions".
Root's second point also holds: a never-established role in `RECOVERY` has **no** keys in the current accepted root at all, so the literal rule has nothing to count — yet it does have an *authenticated* prospective root.

### 2.2 Proposal [P] — the availability context is phase-dependent, with stated evidence
| Role situation | Key set counted | Evidence attached to the observation | Outcome |
|---|---|---|---|
| Not in a begun ceremony, state `TRUSTED/EXPIRED/STALE` | **[E]** current accepted root | head root reference + retained revocation history head | named transition if below |
| `ST-UNBOOTSTRAPPED` (initial or reset), staged-or-not | — | — | **[E]** accepted stay; **no key set is fabricated**; a merely *staged* payload changes nothing |
| `ST-QUORUM-LOST` | **[E]** current accepted root | as above | stays (restored quorum does not heal) |
| **In a begun ceremony** (`ST-RECOVERY`, batch member) | **[P]** the role's keys in the **prospective root bound at BEGIN**, filtered by the *current* retained revocation history | begun descriptor's replacement-root binding + role + history head | below threshold ⇒ v14's named `RECOVERY → QUORUM-LOST` (interrupts the batch); otherwise stay |
| `ST-RECOVERY` but **not** a member of a bound batch (should not exist under r4) | — | — | refuse the observation as inapplicable; never guess a key set |

Why this and not the literal reading: it removes 2.1's livelock without deleting the named exit — the exit now means what it can usefully mean *during* a ceremony: **the replacement this ceremony is bound to can no longer reach threshold** (e.g. a same-head revocation list accepted meanwhile revokes candidate keys), which is exactly root's "candidate key loss". It also gives a never-established member a real, authenticated key set, so nothing is withheld and nothing is invented. After ABORT the role is outside a ceremony again, so `toFunction`'s "still-true" quorum cause is evaluated under the **[E]** row — a recovery begun from `QUORUM-LOST` and aborted returns to `QUORUM-LOST`, as v14 intends.
This **is an amendment of v1 §4.1's "current accepted root"** for the begun-ceremony case and must be written as one. The kernel transition table is unchanged; the *producer contract* of `below_threshold` changes and needs fixtures for: QL-begun ceremony stays in RECOVERY; candidate-key revocation during a ceremony exits; never-established member observed against prospective keys; unbound RECOVERY refused.
**[GAP-2]** No owner says *when* the host dispatches `EV-QUORUM-OBSERVE` ("Signer-set cardinality is observed" — by whom, how often). With 2.2 the ceremony is safe at any frequency; the trigger should still be stated (I would tie it to a change of its inputs — head, bound ceremony, revocation history — but that is an owner choice, not derivable).

## 3. History note — merged historical revocations

Root's three-way distinction is right, and the S6 predicate must not be stretched. **[E]** `observe_revocation` acts only when `current.version() > start.revocation_version`, with the comment "never revoke on a lower counter" and "rollback is detected elsewhere" — it is a running-operation predicate over a *current list*, by construction blind to anything that does not raise the version.
**Concrete counterexample (lists are not assumed cumulative — nothing says they are):** target store accepted revocation v7, later v9; v9 omits subject X. Source store accepted v8, which lists `namespace X`. On ancestor re-selection the merged version floor is max(9, 8) = **9 — unchanged for the target** — yet X is a fact the target never observed. A version test reports "nothing new"; a role holding namespace X would be reset and become healable.
What existing law supplies and what it does not:
- **[E]** counters take the per-field max on rollback (S9); **[E]** v14 `monotonicStore.rule`: "No transition in this machine may decrease a counter or **forget a revocation observation** because an executable generation rolled back." That obliges retention of the *fact*.
- **[E]** v14 `EV-REVOKE` guard: "**Newer** byte-valid revocation observation… Advance monotonic last-known revocation" — novelty is expressed only as list newness.
- **[GAP-3] no owner supplies a history-merge law**, nor an event for "a fact newly applicable to this store although its list is not newer". It needs an explicit completion; it is not derivable.
**[P] minimal completion, in root's three terms:** (1) *historical facts* — identity `(subjectKind, subject, source list reference)`, retained on admitted ancestry, authenticated once under the root that signed their list; (2) *current-list/floor admission* — unchanged: heads and `revocationVersion` move only when a strictly newer list is accepted; **a lower-version list is never newly accepted by a merge, and the heads do not move**; (3) *newly applicable OLD-role-subject revocation* — novelty is "fact not in the target's retained history", **not** "version greater"; such facts are matched against each target role's OLD frame and dispatched **before** the standing reset, exactly as r4 C.1 orders a recovery publication. Equal version with differing identity still refuses. **Unavailable or exhausted bounded history refuses the transition; it is never an empty set.** The role event's input contract then needs the same rewording as in my r4 table ("newer list" → "newly observed applicable fact"), and the established-reset `EV-REVOKE` completion root already accepted covers roles reset earlier.
