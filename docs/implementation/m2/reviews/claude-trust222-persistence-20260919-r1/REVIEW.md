## 3. Findings

### H-1 (Medium) — `ceremony commit` takes no PATH, but nothing says which payload members were retained at staging
`staged = {payload:DocRef, authorization:DocRef, by}`; a `DocRef` is one body + one envelope ≤ 4 MiB. 215 COMMIT must "re-run complete authorization/member/quorum admission" on the *retained* payload — root chain, catalog, revocation list, role-member proofs — and a payload may also carry artifacts far above the object cap. As written, COMMIT either cannot re-admit (members gone) or silently depends on the original PATH still existing.
**[P]:** at staging, copy into `I/trust/objects` exactly the **relied-on closure** (manifest body/envelope, authorization body/envelope, root chain, catalog, list, and the selected-scope role-member proofs — the same closure r6 defines for a refused-import witness) and record it as one bounded immutable `StagedClosure` node that `staged` references; state that artifacts are **not** retained and **not** needed, because recovery COMMIT changes no executable selection. Then BEGIN/COMMIT are self-contained and the budget preflight covers them.

### H-2 (Medium) — the restore marker adds a global barrier and new stuck states without buying atomicity; and as written it can wedge
In a single-capsule design the whole declared reset (roles, anchor cleared, challenge cleared, floors kept, `sourceFence` kept) is **one capsule revision**. 222 publishes the marker only *after* a fully successful preflight, so the marker never records a declaration the reset could not complete; it only splits one atomic replacement into marker → capsule → unlink, and obliges **every** state-using entry to admit marker absence (a new install-wide `unavailable` cause if that one small file is malformed).
It also has a wedge: the marker "blocks ordinary mutators and execution", but lifecycle **transition admission** is not an SC-TRUST mutator. If a transition selects another store while a marker is pending, the marker's `store` no longer matches, the rule is "refuses", and nothing is allowed to remove it.
**[E]** v8 §5.5 requires only that "any declared restore marks every role `ST-UNBOOTSTRAPPED` with reason `RESTORED` and keeps the restored counters and `evalHighWater` as floors", and speaks of "the marker suppressed" without fixing a file.
**[P] smallest coherent owner:** drop the separate marker file. `acknowledge-restore` = one ordinary outcome publication (objects → `restore` event → descriptor → capsule); the durable `restore` event and `RESTORED` reset records *are* the declaration v8 calls the marker. Crash before the capsule barrier = nothing happened, re-run recomputes the same result because no S4/S5 evaluation is involved. This removes the marker codec, its barrier on every entry, the unlink barrier and ~half of the listed restore model rows.
**If root keeps the marker**, two corrections are required: (i) transition-intent admission, store reclaim and creation must also observe the marker barrier; (ii) state who may retire a marker whose store binding no longer matches (today: nobody).

### H-3 (Medium) — "ABSENT active transition slot" can make `acknowledge-restore` permanently unavailable
Ceremony commands accept "an admitted coherent terminal slot … without retiring or rewriting it"; restore demands absence, "stricter", with no reason given and no named owner that retires a terminal slot outside a new transition. After any completed transition the slot may simply stay terminal, and the restore declaration — the command an operator needs precisely after disturbance — refuses indefinitely. **[P]:** either align with the trust-only terminal allowance (a terminal slot's images are already final, and the reset preserves `sourceFence`), or name the retiring owner and its command.

### H-4 (Medium) — "documents still on disk": precise minimal reconciliation
**[E]** v1: "a restored store whose counters are LOWER than any **accepted** document still on disk … is quarantined"; v8 §5.5 "a trust store restored below any document still on disk". In 222, `I/trust/objects` also holds staged-unaccepted documents, proof-only roots (authenticated, never accepted), and orphans of crashed attempts, so raw presence proves nothing — and even a well-formed **descriptor** proves nothing, since a crash leaves exactly that.
**[P] definition (no new file, refusal-only):** *revision n is proven committed iff an admissible descriptor `D(n+1)` exists whose `previousCapsule` equals the SHA-256 of the capsule reconstructed from `D(n)` (`afterProjection` + the `publication` reference to `D(n)`).* Preparing `D(n+1)` required admitting capsule n as current under the fence, which an orphan of n can never satisfy. "Accepted document still on disk" then means: a head document named by the `afterProjection` of a **proven-committed** descriptor. Detection = the current capsule's hash has a proven-committed successor chain ⇒ the capsule is behind evidence ⇒ **quarantine/refuse** per v1; it never adopts, replays or raises anything (consistent with "cannot turn an orphan descriptor into a successful operation"). The last descriptor of a chain is unproven and ignored; staged documents, proof closures and orphans never count.
Costs to state: it needs a bounded census of the objects directory (detection-only, so it does not violate "no listing **selects** a record"; charge it to the same work profile, and on exhaustion report *detection unavailable*, not rollback and not clean); it cannot see a rollback of exactly one revision. Run it at `acknowledge-restore` preflight and in read-only diagnostics, not on every mutator. *Optional, only if root wants O(1) every-operation detection:* an immutable post-barrier commit witness at a revision-determined name (`…/commits/<revision>` = `{revision, capsuleSha256}`); it closes the one-revision gap at the price of one more write+barrier per revision. I recommend the definition alone as the minimal reconciliation.

### H-5 (Low–Medium) — publication order is stated by *kind*; two objects depend on events
Crash law step 2: "documents/proofs … then its ordered events, then its publication descriptor". But `BeginBatch` (contains `beginEvents`) and the continuity/restore **after-image capsules** (contain `eventHead`, `RoleRecord.by`) are objects that depend on events. **[P]:** state the rule as *publish in dependency (topological) order, each object only after every object it references is durable; descriptor last; capsule after the descriptor's barrier*. The model already treats objects as one barriered set, so this is a prose correction; add a model object that depends on an event so the rule is exercised.

### H-6 (Low–Medium) — "Ordinarily all three versions equal the clock's corresponding counters"
"Ordinarily" leaves `counter > head.version` reachable-by-wording. Then **[E]** v1 §4.2's "equal counter with different bytes refuses" cannot be evaluated for a document presented *at* the counter (no identity is retained there). **[P]:** make it an invariant — *every positive metadata counter is witnessed by a retained head document at exactly that version; a capsule or prepared image violating it is unavailable* — or, if a lagging head is intended after continuity, add: *a presented document must be strictly greater than the counter whenever no identity is retained at the counter*.

### H-7 (Low) — envelope-insensitive fork rule is an interpretation of v1, and the retained head should not flip
**[E]** v1 says equal counter "with different **bytes**" refuses; 222 compares the domain-separated signed **body** identity so two envelopes over one body are not a fork. I agree with the choice (same body ⇒ same facts), but label it an explicit completion, and add: re-presentation of an accepted body under a different envelope is a no-op for `heads.*.document` (the first accepted `DocRef` stays), so a head is never rewritten without a version advance.

### H-8 (Low) — event dispatch targets for refusals that have no derived set
BEGIN with an **empty** derived subset and staging with **no applicable role** are said to refuse "where an event is dispatched", but to whom? **[P]:** dispatch to every role in the **signed scope** (each is in a non-source state, so v14's own fallback yields `RECOVERY-BEGIN-REFUSED` / `PAYLOAD-NOT-ADMISSIBLE`, audited, state unchanged); with **no staged payload** there is no authenticated scope, so that refusal is pre-dispatch and writes nothing. (r6 G-1's `batchCompleteness` covers the non-empty failing case.)

## 4. Is this the smallest coherent command owner?
The three ceremony leaves map one-to-one onto v14's BEGIN/COMMIT/ABORT, take no role or store argument, and reuse `trust import` for staging — coherent, and I found no unsafe contradiction in them beyond H-1/H-8. With H-2 applied, `acknowledge-restore` is one command with one revision.
For root's decision, not a defect: a **strictly smaller** owner exists. Nothing multi-party happens locally between BEGIN and COMMIT (the 3-of-5 authorization is already signed inside the staged payload), and every BEGIN source state already refuses INSTALL, so a *durable* `RECOVERY` interval adds no protection. A single `trust ceremony commit` that evaluates everything tentatively and then dispatches BEGIN and COMMIT in **one** outcome revision — or, on failure, dispatches `EV-RECOVER-COMMIT` from the unchanged states, which v14's fallback already refuses and audits as `RECOVERY-COMMIT-REFUSED` — would make the begun-batch barrier, interruption, automatic termination, ABORT and the whole r5 F-1 class unreachable in the product, while the 211 kernel keeps v14's full table. Price: no operator-visible pause to inspect the derived batch (a read-only diagnostic can show it), and the product would not exercise durable `RECOVERY`. If root values that pause, the three-command surface is the right one; if not, this removes the largest share of remaining model work.

## 5. Model notes (conditional models; no finding beyond coverage)
The publication model has no restore/marker sequence (listed as owed) and its `durable_success` assertion restates how `step` sets the fields; its real checks are dependency closure under crash subsets, floor monotonicity and refusal-preserves-standing, which are meaningful. The history model charges bytes from the node after lookup, whereas the text (correctly) charges `BlobRef.bytes` before reading; and its repeated-edge case uses a merge with two identical parents, which the text forbids ("sorted distinct") — use two distinct parents sharing an ancestor instead.
