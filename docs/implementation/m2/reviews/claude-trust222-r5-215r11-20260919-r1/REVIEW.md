## 3. New finding in the changed scope

### T-1 (Medium–High) — the same restriction is still discharged by *interruption*: `REVOKED → BEGIN → RECOVERY → QUORUM-LOST → ordinary PRESENT → TRUSTED`, with no ceremony committed
r11 now states the principle: "**BEGIN did not discharge its restriction** … Current REVOKED and recovered pre-BEGIN REVOKED stay non-enterable through ordinary PRESENT." It enforces it for *private termination*. But a member can also leave `RECOVERY` through a named observation. **[E]** v14's guard for that transition is: "Observed signers < reserved threshold **AND REVOKED does not also hold**. If both, the EV-REVOKE rank wins and this guard is false." 215 C.2/C.3 let any `RECOVERY` member whose bound prospective availability drops below threshold take `QUORUM-LOST`, and `QUORUM-LOST` is an ordinary TRUSTED-entry source state.
Probe on the **unchanged** main model (`claude-out/probes/probes.py`, `io/probes.json`): pre-BEGIN `REVOKED` → `RECOVERY` → same-head list removes prospective keys → `QUORUM-LOST`, batch auto-terminated → next healthy ordinary payload → **`TRUSTED`**; nothing was committed. The exploration reaches this shape too (ABORT-result `REVOKED` worlds are re-begun and interrupted) and its oracle (`EXPECTED_BELOW['RECOVERY']='QUORUM-LOST'`, "heal an already-interrupted non-revoked sibling") accepts it, because the model's role carries no BEGIN source.
An operator does not need a rollback for this: stage any authorized recovery payload, BEGIN, present a same-head list that revokes enough of the *prospective* keys, then an ordinary payload. Whether an attacker can obtain such a list is a separate question (it is root-signed); the point is that the state machine itself permits `REVOKED` to end without authorized recovery, contradicting the sentence r11 just added.
**[P] one rule, v14-conformant:** for a `RECOVERY` member whose exact bound BEGIN source state was `REVOKED`, "REVOKED also holds", so the below-threshold `EV-QUORUM-OBSERVE` guard is **false**: the observation is the accepted *stay* (fallback), the member remains `RECOVERY`, the batch is not interrupted by it, COMMIT refuses on its own too-few-keys guard, and ABORT's `toFunction` returns `REVOKED` (first still-true candidate). Model: give `Role`/`BatchWorld` the BEGIN source, make `EXPECTED_BELOW` for `RECOVERY` depend on it, and add the variant "revoked-source member interrupted to QUORUM-LOST". 222's RoleRecord text ("REVOKED ends only through authorized recovery") then holds on every exit from `RECOVERY`: COMMIT (authorized), ABORT (v14), private termination (r11), observation (this rule).

## 4. Smaller points
- **U-1 (Low).** 215 C.4 says "Admit the exact bound BEGIN preimage **and current active restriction evidence** first". The reset model decides on `begin_state` alone; "current active evidence" is not an input. If the two can disagree (BEGIN says `REVOKED`, active evidence absent/unreadable), r11's text makes that *unavailable* — add that row (`Role('RECOVERY',True,'REVOKED')` with evidence missing ⇒ `Unavailable`), so the conjunction is asserted rather than implied.
- **U-2 (Low).** The reset model leaves a current `REVOKED` record untouched with **no** event, while r10's Q-1 rule records a new ROOT_CHANGED reset even for an unchanged `UNBOOTSTRAPPED` token. Both are root's stated choices; say in one sentence that the asymmetry is intended (REVOKED takes no reset projection), since a reader comparing C and C.4 will otherwise look for the missing record.
- **U-3 (Low).** 222 S-2: "exact already-existing admitted equality is idempotent" — true for the descriptor, but events carry invocation identity, so a retry normally builds a *different* descriptor and the idempotent branch is reachable mainly after a crash between descriptor barrier and capsule replace **within the same prepared operation**. Worth stating, so nobody relies on idempotence to conserve bucket capacity across retries.
