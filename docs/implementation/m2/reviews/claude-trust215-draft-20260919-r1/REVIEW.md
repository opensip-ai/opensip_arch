## 0. My 214 errors that 215 already corrects
- **"No payload-schema change" was wrong.** I did not read `envelope.schema.json`: an envelope's `subject` is `{kind, domain, storedSha256, preimageSha256}` — digests only, no body — and payload1's `members` is closed (`additionalProperties:false`, eight members). Listing an envelope cannot deliver a body. Root's payload2 is the honest repair.
- **Sequential same-authorization commit** under a head that has already changed was unsound for the reason C gives (the application need not verify under the new recovery keys) and it needed an equality-with-floor exception. Withdrawn; strict `> store floor` with one atomic batch is cleaner.

## 1. What is sound in A–C [OK]
- Ninth kind with its own domain, `RECOVERY` authority from the **current held** root (embedded anchor pre-genesis, "never a payload-supplied self-signed anchor"), root keys never counting, reuse of the existing verifier owners, cardinality owned by the root schema (≥3 of ≥5) without a fixed equality.
- `RootBinding` uses the **existing** domain-separated root digest (root.1/root.2), not a raw file hash — consistent with `trust.rs` (the `root` kind already routes two domains, l.1907/1984/2003, so a kind→{domains} precedent exists for `payload`).
- **No hash cycle**: authorization binds roots and role predecessors; the manifest commits the authorization body and envelope; the authorization does not hash the manifest. The **prospective-root TR-BUNDLE** step is sound: the old recovery authority signs the exact replacement root digest, that root delegates the bundle keys, those keys authenticate the manifest *and its `payloadKind`*; lost old TR-BUNDLE keys cannot deadlock, and an unsigned kind cannot select a weaker route. `EnvelopeKind::Payload` already routes to `TR-BUNDLE`.
- Strict advancement over **both** store floor and authority root version; no role authorizes an unlisted role; one fence, all guards before any head change, one capsule publication; REVOKED preserved; `ROOT_CHANGED` reset with evidence; "continuation join still consumes actual states".

## 2. Flaws in A–C

### F-1 [FLAW A–C] — exact per-role `acceptedUnder` makes a publisher-wide application install-history-specific
A: "Every non-null per-role prior binding must match the held role record". But an authorization is signed once by the publisher's recovery quorum and delivered on removable media to many installs. Installs legitimately differ: one accepted TR-CORE under root 5 and never refreshed, another under root 6; a third has TR-BUNDLE never established (`null`). One signed body can match only one such history; with six roles the variants multiply, and the recovery quorum would have to sign one application per *history population* — or installs with an unanticipated history cannot recover at all. `authorityRoot` has the same shape of problem but only one dimension (the install's head), which is tolerable and necessary (it identifies whose keys signed).
v14's `oldRootIdentification` — "the from-root is the last accepted install-scoped root for this role, or there is no prior root" — is an *identification the install makes*, and `oldRootNewRootRoleBinding` binds "old-root, new-root, and role … as one recovery step". That binding is satisfied by `authorityRoot → replacementRoot` plus the role list in the signed body, with the per-role `acceptedUnder` recorded as **local event evidence** and checked locally (`acceptedUnder` is null or a root at or below `authorityRoot` on the retained chain). Bounded alternatives: (a) drop `acceptedUnder` from the signed body, keep it in the capsule/event; (b) keep it signed but as a *bound* ("not above version v") rather than an exact binding. I recommend (a). This also removes the schema's inability to express unique-by-role (only `uniqueItems` on whole objects today).

### F-2 [FLAW A–C] — a fixed signed role set meets per-install role states that the publisher cannot know
C: "Each role must independently satisfy its existing event applicability; a TRUSTED role cannot be silently put into RECOVERY" and "Recovery authorization, not a locally chosen role list, fixes the batch's scope". v14 has no `EV-RECOVER-BEGIN` from `ST-TRUSTED`. If the application lists `[TR-CORE, TR-INDEX, TR-COMPONENT]` and on this install TR-INDEX is `TRUSTED` (its clock has not reached the expiry another install has), BEGIN is inapplicable for one listed role — and under all-or-nothing the install cannot recover TR-CORE either, with no smaller lawful application available unless the publisher pre-signs every subset. States are *mostly* uniform when the cause is a revocation (publisher-wide) and not uniform when the cause is expiry/staleness/quorum (clock- and payload-dependent).
Needs one explicit rule. The least one that keeps root's principle: the batch is `listed ∩ locally applicable`, **determined by retained state, never by an operator choice**; listed-but-inapplicable roles are treated exactly like unlisted roles (reset `ROOT_CHANGED`, which for a `TRUSTED` role is the same outcome every unlisted role already gets); an empty intersection refuses. If root prefers strict all-or-nothing, the owner must say that such installs are unrecoverable by that application and why that is acceptable.

### F-3 [FLAW A–C] — the payload's own newer revocation list is admitted *after* the signatures it could invalidate
B step 2 verifies the authorization "with the CURRENT … complete revocation context"; step 4 filters "previously accepted revoked keys"; step 5 then admits the payload's new-root revocation list. A legitimate ceremony is often *caused* by key compromise, so that list may revoke a recovery-authority key that was counted in step 2 or a new-root bundle/root key counted in steps 3–4. The draft never says what happens then. It cannot be verified the other way round (the list is authenticated under the prospective root, which the authorization authorizes — circular), so the safe closed rule is a **second pass**: after step 5, recompute every quorum counted in steps 2–4 against `current context ∪ the newly authenticated list`; if any falls below its threshold, refuse staging. Without it, a payload can be self-contradictory and still commit, and the union history then contains a revocation of keys the store has just relied on.

### F-4 [FLAW A–C] — staging demands TRUSTED-entry predicates that v14, 208 and 211 place at COMMIT
B step 5: "Verify … typed role availability and **current TRUSTED-entry prerequisites**" during staging; A: "all current TRUSTED-entry predicates must pass" (unqualified as to when). v14: recovery-typed PRESENT "Stages ceremony inputs and is ACCEPTED without changing state"; BEGIN's guard is "Ceremony inputs are present"; only `EV-RECOVER-COMMIT` requires `recoveryTrustedEntry`. The frozen kernel encodes that separation deliberately — `PresentRecovery { staging_admissible }` has no entry observation, and 208's README: "recovery staging validity is distinct from TRUSTED-entry activation".
Answering root's direct question: **no, staging should not require the TRUSTED-entry predicates**, including when the prior root is expired and old keys are lost. Staging = authenticity, completeness and exact binding (steps 1–4 plus member joins, plus F-3's second pass). Freshness, expiry, future-time, `notAfter` and anti-rollback belong to COMMIT at that moment's `tEval` — A already says "at commit `issuedAt <= tEval < notAfter`". Evaluating them at staging creates two judgments at two times, a staged batch that can silently become "invalid yet staged", and an `ENVELOPE-INACTIVE` question at a point where v14 has no `whenInactive` branch. (Staging is still an attempted event and S4's write-ahead applies to it; that is unchanged. Historical Phase B remains free of fresh S4, as root says.)

### F-5 [FLAW A–C] — locating "exactly one applicable envelope" is an unbounded pre-authentication scan
`members.envelopes` allows **100,000** `{path, sha256}` entries and an envelope's kind is inside the envelope file. "Find exactly one applicable `root-recovery-authorization` envelope" therefore means opening up to 100,000 untrusted files *before anything is authenticated* (step 2 precedes step 4). Fix in the schema, not in prose: `members.rootRecoveryAuthorization = { "body": {path, sha256}, "envelope": {path, sha256} }`, the envelope reference also required to occur exactly once in `members.envelopes`; the reader opens two named files. "Conflicting/extra applicable authorization refuses" then needs only a check that no *other* listed envelope, when later read for its own purpose, has the ninth kind.
Related bound: "Boundedly parse the complete candidate manifest" should name the bound — the existing 4 MiB metadata loader limit applies to the manifest itself (payload1's arrays otherwise admit manifests far larger than any product bound).

### F-6 [FLAW A–C] — a staged-but-not-begun batch has no discard path
C: "a different staged/begun payload cannot replace the existing batch by re-presentation". v14's abort exists only from `ST-RECOVERY` (`RECOVERY-ABORT-NOT-IN-CEREMONY` otherwise). So a payload staged in error and never begun can neither be replaced nor aborted — and C also makes any staged ceremony outside a new batch block that batch. Distinguish the two cases: *before* BEGIN a new valid recovery payload replaces the staged one (nothing is bound yet; v14's staging member is simply accepted again), *after* BEGIN only the identical payload is accepted and replacement requires ABORT. Batch ABORT must also be stated: all selected roles leave together, each to its **own** `toFunction` target from its own retained evidence.

### Schema field mismatches (exact)
- `payload-schema.v2.json` `$id` is still `urn:opensip:design:payload:1` (copied from the parent); two schemas with one `$id`.
- `schema.json` has no `$id`, unlike its sibling metadata schemas (`urn:opensip:design:…`).
- `envelope.schema.json` (v2) closes `subject.kind` to six kinds and `subject.domain` to six domains; the ninth kind and `opensip.metadata.payload.2` need an envelope-schema successor too (A/B list route/reader/model/fixture/registry, not this file). In the product, `EnvelopeKind::Payload.route()` returns a single domain; it needs the two-domain treatment `root` already has.
- `recoveries`: `uniqueItems` deduplicates identical objects only; unique-by-role and canonical order are semantic (the `$comment` says so) — moot if F-1(a) reduces entries to role tokens, where `uniqueItems` *is* exact.
- `issuedAt`: `minLength` 1 in payload (inherited) vs 20 in the authorization; harmless, inherited.

## 3. Consequences worth stating in C (not flaws)
- After a batch for a strict subset (say `[TR-INDEX]`), TR-CORE becomes `UNBOOTSTRAPPED/ROOT_CHANGED`, so the continuation join refuses everything until an **ordinary** payload under the new root arrives — a recovery payload can never supply that (v14: "NEVER enters ST-TRUSTED via EV-PRESENT-PAYLOAD"). Safe, but it is an availability property of every partial batch and should be said.
- "selected role restrictions end without deleting historical revocation observations" — agreed (root's Q1); the evidence references must remain resolvable afterwards.

## 4. Blocked on D/E, not flaws in A–C [BLOCKED D/E]
Exact capsule/role record and event/batch-descriptor shapes (so "match the held role record" in A and "prepared event set" in C cannot be checked yet); pre-genesis authority (A names the embedded anchor; the "store root floor" comparison has no value until D's phase sum fixes it — say explicitly that pre-genesis the replacement must exceed the anchor's version); available-key quorum evidence; revocation-history bounds (F-3's second pass consumes that reader); command surface and request bodies for stage/BEGIN/COMMIT/ABORT; crash rows for a partially written event set; restore.

## 5. The ancestor-target root head — bounded analysis of root's alternative
My 209 reconciliation (§4) said the ancestor target keeps its **own** root head while counters take the max. Root's objection is right and I withdraw that rule: it leaves the *old* head's `recoveryAuthority` as the current ceremony authority in a store whose floor is already higher. Recovery-authority keys rotated out between root N and root M — possibly because they were compromised — would again be able to authorize a replacement (any version above the floor) merely because an ancestor was re-selected. That is a real authority regression, not a bookkeeping nicety.
**Can the highest already-accepted head be carried without relaxing S5? Yes, under conditions that are all existing law or direct consequences of it:**
1. *Same-install proof, not a payload.* M was admitted by this installation through S5 (continuity + possession per link) and its documents and chain nodes are retained install-level (`I/trust/documents`). Carrying the head re-uses that admission; it is not a new acceptance event and no signature from outside is trusted.
2. *Ancestry is required and checked.* The target's own head N_t must be an ancestor of M on the retained chain (bounded walk, ≤ `rootChain` 64 per payload and one node per rotation). Same version with a different identity anywhere on the path, or N_t not an ancestor of M, **refuses the transition** before effects — a fork inside one installation is never resolved by choosing.
3. *No role gains standing.* Every non-revoked role is reset; REVOKED stays; per-role `acceptedUnder` stays the **old** binding. The carried head supplies only (i) the floor-consistent identity (`heads.root.version == clock.rootVersion` holds again, so no special "floor above head" case is needed) and (ii) the current ceremony authority. S5's "the final root must be unexpired at tEval" is a TRUSTED-entry condition and is evaluated at the next ordinary PRESENT, exactly as today; "Intermediate expiry is never consulted" already covers the carried path.
4. *The target core must be able to read it.* Unchanged: `rollback_floors` refuses `ROOT.FLOOR_ABOVE_CORE` when the old core's chain reach or root-schema readers cannot verify M. That existing gate is precisely the "can this core hold M" test; nothing new.
5. *Historical target metadata is not revalidated.* The target's old catalog stays historical and inert (all roles reset); the revocation history is merged upward (no-forget). Only the catalog head leaves a choice: keep the target's own (then `indexSnapshotVersion` floor may exceed the catalog head in a reset store) or carry the highest accepted catalog reference as well. Either is safe because no role is trusted; carrying it keeps the head==counter invariant uniform. Owner's call.
6. *Continuity companion:* `targetAfter` simply contains head M and the merged history; nothing else in the BEFORE/AFTER scheme changes.
Net: the alternative **shares known current authority without relaxing S5**, and it is strictly safer than my rule. The one thing it must never do is let the carried head stand in for any role's `acceptedUnder`.

F-1 and F-2 rest on a deployment assumption (one application delivered to many installs on removable media, v14 `airGapPayload`); if root intends per-install applications, F-1 changes character and should be stated as a requirement. ## 7. Summary (no verdict — nothing here is a candidate)
**The authorization chain, prospective TR-BUNDLE step, strict floor advancement and atomic batch are sound and correct my 214 sketch in two places. Six concrete problems sit in A–C, not in the omitted sections: exact signed `acceptedUnder` is install-specific (F-1); a fixed signed role set can be inapplicable on an install and deadlock it (F-2); the payload's own newer revocation list is admitted after the quorums it may invalidate and needs a second pass (F-3); staging requires TRUSTED-entry predicates that v14 and the frozen kernel place at COMMIT (F-4); finding the authorization envelope is a 100,000-file pre-authentication scan that a paired reference removes (F-5); a staged-but-not-begun batch cannot be discarded (F-6) — plus an unchanged `$id` and the envelope-schema enumerations. On the ancestor head, root's alternative is right and my 209 rule is withdrawn.**
