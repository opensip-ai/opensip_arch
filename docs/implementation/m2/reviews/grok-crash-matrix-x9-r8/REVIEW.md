The next publication then writes a determined list of content-addressed names. Membership of this leaf in that list, and whether the bytes on disk equal the bytes being written, is fixed by which census occurrence the kill is. Item 5 already says each `x4t.floor-publication` occurrence is a function of the script and the product, and two census runs agree point for point, before any kill. The occurrence index is part of the point identity (`name#k`).

The development split is that determination: `create.after#1`, `write.before#1` and `write.before#3` refused, and `create.after#4`, `create.after#7` and `write.before#6` committed. Those indexes distinguish the points. They do not license one disjunction for the whole class. A row that accepts either outcome accepts a lawful refusal and a lawful commit for a single point, so it does not record the owning law's outcome. The window has to be transcribed from census positions and point names before any kill run, one value per occurrence:

- the next publication writes that leaf and the on-disk bytes differ: `CONFIG.CUSTODY_REFUSED`, subject `installation-incomplete` (X4T r9 item 10);
- the next publication does not write that leaf, or the bytes already equal the bytes being written: Committed.

`create.after` leaves the file empty: the create effect has returned and the write has not started. `write.before` does not leave it empty. `primitive_write` writes the first half of the buffer and then holds, so the leaf is a torn prefix. Both differ from a non-empty object, and the equal-bytes rule decides them the same way. The header's "present and empty" covers `create.after` only.

`INSTALLATION.INCOMPLETE` is not a detail. X4T r9 item 10's incomplete row is `CONFIG.CUSTODY_REFUSED`, subject `installation-incomplete`, which is what `TrustRow::Incomplete` returns at `a2c5e8b`.
