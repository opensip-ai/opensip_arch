## 1. What is currently owned
**Receipt identity and shape — owned, exact. [E]** `MutationReceiptV1` (repair.schema): "Retained record of an **attempted** host mutation. **Retained even when the effect FAILED or a later verification failed.** receiptId = 'receipt2:' + H('workflow.mutation-receipt', this object without receiptId)." Required members: `schemaFamily, schemaMajor, receiptId, requestId, stepId, executionId, operation, idempotencyKey, effectOutcome ∈ {COMPLETED, FAILED, INDETERMINATE}, commitClass ∈ {REVERSIBLE, IRREVERSIBLE}, replayed`; optional `repairPlanId, baseSnapshotId, appliedSnapshotId, fileOutcomes, rollback, domainDetail`; `additionalProperties:false`.
**Idempotence and replay — owned. [E]** workflows §1: "Generic `mutation` steps use the bare 64-hex `H("workflow.mutation-intent", MutationReplayScopeV1)`. The closed retained scope is exactly `{schemaVersion:1,requestId,stepId,projectId,operation}` … Receipt lookup is never an effect-authorization mechanism. A same-scope COMPLETED receipt permits delivery replay with no second effect. **Failure, unknown state or incomplete execution requires the operation's existing recovery law, not blind re-execution.**" `retryPolicy=none` for `mutation` by schema. "`ExecutionId` stays out [of the key] … each attempt keeps its separate `ExecutionId`." Replay delivery "produces a separately identified receipt with the new request/attempt binding and `replayed=true`" (stated for repair-apply; the `replayed` member is generic).
**Operation vocabulary — owned and closed. [E]** `MutationOperation` has 24 enum members in the schema I read (the prose says "two of the 23" of import/native-preparation — a one-off count difference I note without resolving); `byCommandGenericMutationStep`, `admissibleGenericFieldDomain`, `byStepKindReceiptOperation`, `receiptIdempotencyKeyByStepKind` are published maps "enforced at" the workflow checker. **`evidence-export` / `evidence-restore` are not members**; adding them is an explicit vocabulary + map change, never a free string.
**Attempt identity — owned for all modes; durable attempt custody — owned only for commits. [E]** identity §2: RequestId/ExecutionId "use independent 16-byte host-CSPRNG draws, reserved with uniqueness checked in the corresponding operational ledger before use … applies to **every** RequestId and ExecutionId, in every request mode. It is stated here only as the pre-use uniqueness rule; **it is not by itself a durable permanent record of an attempt.**" And: "**Separately, and only for durable-authoritative commit-capable attempts** … `AttemptCustodyV1` … Its scope is exactly the attempts that can publish an authoritative commit receipt through the guarded commit facade." So: **no generic durable attempt / `operationRef` mapping exists for mutation steps.** That is a verified scope sentence, not a not-found.
**Read-only recovery — owned for commits only. [E]** identity l.1685–1730: `recover(ExecutionId)` "reads **one** consistent committed ledger snapshot carrying the receipt, the private recovery association **and** the `AttemptCustodyV1` phase together … The negative answer requires **all** of: phase `settled`, `settledOutcome` exactly `refused`, and both the receipt and the association confirmed absent … phase `admitted` with no receipt is `unknown-attempt-open`; **no attempt row is `unknown-attempt-unobserved`.** A purged historical receipt can never become never-committed". "Receipt" there is the Run **commit receipt**.
**Uncovered plumbing [G] — I found no rule, and no contrary rule, for:** which carrier durably holds `MutationReceiptV1` (the phrase "mutation receipt"/`receipt2` does not occur in identity, security-and-lifecycle, the build plan or `commit-recovery-readonly.v3.md`); in which transaction a generic mutation's effect and its receipt are published; what journal records a generic mutation appends; how a FAILED/INDETERMINATE receipt is written after an effect fails; what `recover` means for a mutation ExecutionId. The one adjacent sentence is purge's: "Revocation and purge occur in **the existing protected mutation transaction**" (workflows l.1618) — it presupposes such a transaction without defining it. The reference model "does **not** … emit an import or native-preparation receipt; that is a stated qualification limit". None of this contradicts α; it is simply unwritten.

## 2. Smallest precise α integration **[P]** — the existing receipt is the completion identity
**One ledger transaction publishes four things, in this dependency order (acyclic):**
1. `body` = the imported-evidence record set and its retention-root rows (they name RunIds, the origin seal, the origin inventory, the local `executionId`, `requestId`, `stepId`; **not** the receipt, not the association).
2. `MutationReceiptV1` — **unchanged schema**, `operation:"evidence-restore"` (new enum member), `idempotencyKey = H("workflow.mutation-intent", {schemaVersion:1,requestId,stepId,projectId,operation})`, `commitClass:"IRREVERSIBLE"`, `effectOutcome:"COMPLETED"`, `replayed:false`, optional members absent. `receiptId` = the inherited `receipt2:` + H over the receipt without `receiptId`.
3. private association `{executionId, receiptId, bodyDigest}` — it points **at** the receipt and the body; nothing points back. `bodyDigest` = SHA-256 of the canonical `body` (projection still owed).
- **Fixed before publication:** every receipt member. `requestId/stepId/executionId/operation/idempotencyKey/commitClass` are known at admission; `effectOutcome:"COMPLETED"` and `replayed:false` are *constants of the success transaction* — the receipt row exists iff the transaction committed, so writing COMPLETED inside it is truthful (the same way the commit receipt is written inside the commit transaction). No receipt member depends on the ledger commit's own result, so there is no self-reference.
- **Unsupported by the current schema:** the receipt has **no member for the body digest or an imported-evidence reference** and is closed. Do not add one: the association carries that join, exactly as S6 places commit correlations in "the private association" rather than in a closed record. `domainDetail` is an existing optional member but is an error-detail projection, not a place for a digest.
- **Is the receipt enough as completion identity?** Yes for *identity* and *idempotent delivery replay* (that is its inherited job, and its `receiptId` needs no journal position); no for *what was published* — that is the association's `bodyDigest`. Together they are sufficient; neither needs an ICO or SEAL.
- **Non-success endings:** under α nothing is published on refusal, so no ledger row exists. Inherited text says receipts are "retained even when the effect FAILED", i.e. a FAILED/INDETERMINATE `MutationReceiptV1` is lawful — but *where and when* it is written is part of the uncovered plumbing **[G]**. Minimal choice: a **FAILED receipt is written only for a refusal after admission to the final checkpoint** (its own tiny transaction, no body, no association); an uncertain barrier writes **nothing more** and reports `durability-undetermined` with the ExecutionId — an `INDETERMINATE` receipt may be written only by a later authorized recovery that has actually observed an undeterminable footprint, never by the failing attempt guessing.
- **Export** (`evidence-export`) follows the same pattern with `commitClass` to be decided by its pin semantics (pins are revocable ⇒ arguably `REVERSIBLE`); not traced further here.

## 3. Read-only recovery under α — what each observation can prove
All under the inherited discipline: one consistent committed snapshot, stability brackets on carrier/floor observations, no repair, no fence, no authority from lookup.
| Observation in one admitted snapshot | Proves | Does **not** prove |
|---|---|---|
| receipt (COMPLETED) + association + every `body` row, `bodyDigest` matches | this ExecutionId published exactly that body — historical fact ("revives no authority") | that the evidence is still available, or that its closures are trusted now (evaluate at read) |
| receipt present, association or body rows missing/mismatching | contradiction ⇒ **unavailable history**, never "not published" | — |
| FAILED receipt, no association | that attempt reached the checkpoint and was refused | anything about other attempts of the same scope |
| **nothing** for this ExecutionId | **nothing**: with no admitted-attempt row this is the analogue of `unknown-attempt-unobserved`. A raw missing row is equally produced by never-admitted, died-before-publication, ledger rollback below the journal/floor witnesses, purge, corruption or a not-yet-visible commit | never "never published" |
| carrier quarantine / journal tail below floor / `witnesslessRestore` | custody is unknown ⇒ every answer is `unknown-custody` | — |
A purge of imported evidence must leave the tombstone/provenance that 228 already requires, so "purged" stays distinguishable from "absent". No lookup result authorizes re-execution: a fresh restore is a fresh request with a fresh scope.

## 4. Is a sibling admitted-attempt record needed?
**For correctness of α: no.** The effect is one atomic transaction; an attempt that published nothing had no effect to account for, and idempotence is scoped by the retained invocation, not by attempt custody.
**For terminality and audit: only if root wants a provable negative.** Without an admitted row, read-only recovery can never answer "this restore attempt was refused / never published" — only "published" or "unknown" (§3). If that answer is wanted, the minimal truthful sibling is **[P]** `MaintenanceAttemptCustodyV1`, private, product-canonical, keyed like its commit counterpart by `(storeGenerationDigest, namespaceId, executionId)`: `{phase: admitted | settled, settledOutcome: null | published | refused, operation}` — `admitted → settled` only, never reopened, settle ordered **after** the publication transaction, `published` provable only with the receipt+association present, `refused` only when both are confirmed absent; a durability-uncertain attempt stays `admitted`. It must **not** widen `AttemptCustodyV1` (its scope sentence says "exactly", and `committed` would be untruthful), carries no `operationRef` because α appends no journal record to correlate, and changes nothing about ExecutionId minting: the all-mode pre-use uniqueness reservation stays the single source of ExecutionIds.
My recommendation: ship α without the sibling, state the consequence ("absence is unknown, not negative") in the restore owner, and add the sibling only with an explicit audit requirement — it is one more ledger write at admission on every restore.

## 5. Distinguishing current law from proposal, in one place
**Current law:** receipt shape and `receipt2:` recipe; idempotency key and scope; `retryPolicy=none`; no blind re-execution; all-mode ExecutionId uniqueness; `AttemptCustodyV1` and `recover()` scoped to commit-capable attempts; closed `MutationOperation`. **Uncovered:** the generic mutation publication transaction, receipt carrier, FAILED-receipt timing, mutation recovery. **Proposed here:** two new `MutationOperation` members and map rows; the body/receipt/association dependency order; the rule for FAILED/INDETERMINATE receipts; the optional sibling custody record.
