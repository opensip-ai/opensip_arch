## 1. Capsule genesis
**[E]** `TrustClockRecordV1` types `rootVersion`, `indexSnapshotVersion`, `revocationVersion` as **`I64Positive`** and requires all eleven members ("missing is not null", S&L l.2484–2490). The closed record therefore *cannot represent* "no accepted root": there is no zero. **[E]** v2 §4.2 Restart: `evalHighWater` "if absent (fresh install) it is `max(wallClockNow, issuedAt of the presented root)`" — the owner already treats the pre-genesis clock as *absent*, not as a zeroed record. **[E]** v14 `airGapPayload.mustCarry` includes root chain, signed index snapshot and last-known revocation state, and `missingMember` refuses — so the first accepted ordinary payload establishes all three counters at once.
**[P]** Genesis is typed absence of the whole trust record, all-or-nothing:
`"clock": null` ⇔ `"heads": null` ⇔ `"eventHead"` may be null ⇔ every role `{state: ST-UNBOOTSTRAPPED, bootstrap: {"kind":"initial"}}`. My 209 shape (`heads.root` non-null with `version: n`) was wrong for this state. No member is defaulted; `sourceFence: null`. The first accepted TRUSTED-entry publishes the first complete 11-member record and all three heads in one revision. The embedded bootstrap anchor lives in the admitted core closure (`bootstrapAnchorCustody`), never in the capsule.
**[P]** Per-role `bootstrap` replaces my `resetReason` (issue 8): `{"kind":"initial"}` | `{"kind":"reset","cause":"RESTORED"|"MIGRATED","evidence":EventRef}`. Invariants: `clock == null` ⇒ all six `initial`; `kind:"reset"` ⇒ `clock != null` and `evidence` resolves (§3) to the reset's audit event. A reason string alone can never assert that a role has accepted history; the non-null record and a resolvable event do.

## 2. Ceremony state
My "`beganEventSeq` non-null iff `ST-RECOVERY`" was wrong as an *admission invariant*, because I had not defined what happens to ceremony data on the exits v14 names. **[E]** exits from `ST-RECOVERY`: `EV-RECOVER-COMMIT`→TRUSTED; `EV-RECOVER-ABORT`→still-true/UNBOOTSTRAPPED; `EV-REVOKE`→REVOKED; `EV-QUORUM-OBSERVE` below threshold→QUORUM-LOST ("still leave RECOVERY because those are named transitions"). **[E]** v14 is silent on the fate of staged inputs on any exit and on re-presentation during a ceremony (no `honestyRepairs` entry addresses it; T18 only says "Invalid payload: stay RECOVERY and refuse").
**[P]** Identity binding, not a boolean:
```
"ceremony": null | { "staged": { "payload": hex64, "by": EventRef },
                     "begun":  null | { "payload": hex64, "by": EventRef, "from": <state token at BEGIN> } }
```
- BEGIN requires `staged != null` and sets `begun.payload = staged.payload`. COMMIT is evaluated only against `begun.payload`.
- Recovery-typed PRESENT **before** BEGIN: accepted, replaces `staged` (nothing is bound yet). **After** BEGIN: a payload whose digest equals `begun.payload` is the accepted no-op T18 allows; a *different* digest is refused with the existing `PAYLOAD-NOT-ADMISSIBLE` (it is not admissible *to this ceremony*). Replacing the authorized root requires ABORT and a new staging. This is a proposed tightening of T18's "invalid payload", to be stated in the owner — and it needs a conditional input in a 208 successor (`PresentRecovery { staging_admissible, matches_begun: Option<bool> }`); the frozen 208 kernel is unaffected.
- Dispositions, each in the same capsule revision as the state change: **COMMIT** → `ceremony := null`, role restrictions `revokedBy`/`quorumLostBy := null` (the role's restriction ends; per Q1 the retained observations in §6 do **not** shrink). **ABORT** → `ceremony := null`; target from retained evidence (`revokedBy`, `quorumLostBy`) and clock; staged input discarded so no authorized root lingers under a later BEGIN. **REVOKE / QUORUM exit** → `ceremony := null` likewise, `revokedBy`/`quorumLostBy` set from the new event. Discarding is the safe direction: the newer revocation may concern keys inside the staged payload, and re-presenting is cheap and audited.
- With these dispositions "`begun != null` ⇔ `state == ST-RECOVERY`" becomes a *writer postcondition that admission can check*, rather than an assumption.

## 3. Evidence references and R5
**[P]** Every retained reference is a full immutable address: `EventRef = {"store": S, "seq": k, "sha256": h}` ⇒ `I/trust/stores/S/events/k-h`, resolvable without walking or listing, and unambiguous after forward/ancestor carry because `S` names the store that wrote it. `DocRef = {"sha256": h}`, `NodeRef = {"sha256": h}`. My "`eventSeq ≤ eventHead.seq`" check is withdrawn; the rule is **each reference resolves independently, rehashes, and its record names this role and the claimed event kind**, else *unavailable*. Consequence under Q3: a retired store's `events/` directory is a live dependency of its successors and must be retained.
**[OPEN] R5 is not closed.** v14's audit record is `{role, from, to, event, outcome, refusalReason?, payloadDigests, clockObservation}` — it does not say *which* signer set, threshold, root, namespace or subject was observed. I can name the minimum a sound record needs — quorum: `{document: DocRef, root: NodeRef, role}` (signer set and threshold are then recomputable by re-verification); revoke: `{list: DocRef, root: NodeRef, subjects applied to this role}` — but **the producer and checker of those facts (signature/threshold admission over metadata) is not an owned, implemented component in any tree I have**, so the shape cannot be frozen honestly yet. It should be owned together with that admission code.

## 4. Accepted heads on ancestor re-selection
My "take the side with the greater version" was wrong twice: it silently picks one document when versions tie, and it lets a higher *source* root stand in a store whose core may be unable to verify it or whose own metadata was never chained to it.
**[E]** v2 §5.5: restored/retained counters are **floors** and "The payload, not the restored bytes, re-establishes trust"; rollback "refuses when the new store accepted a root the old core cannot verify" (`ROOT.FLOOR_ABOVE_CORE`); S5 evaluates N+1..M **from the held accepted root**.
**[P] Smallest complete law:** on ancestor re-selection the target **keeps its own root and catalog heads**; only the six counters take the per-field max (unchanged law). Hence in a reset store `clock.rootVersion ≥ heads.root.version` is lawful, and *equality is required before any TRUSTED-entry can succeed* — which S5 already delivers, since an ordinary payload must chain from the held root to a version ≥ the floor. No source document is ever used to validate older target metadata, and no chain-linkage walk is needed. My 206/209 invariant `heads.version == clock.version` is narrowed to: equality unless every role is `bootstrap.kind == "reset"`.
**[P]** If source and target hold the **same version with different hashes** for root, catalog or revocation, that is a fork inside one installation: refuse the transition at Phase C admission, before jLEASED (existing `REQUEST.PRECONDITION_FAILED` class), never choose.
**[P]** The three timestamp members are not copied from whichever side had the larger counter: `rootExpiresAt`/`catalogExpiresAt` are recomputed from the **target's own selected documents**, `revocationIssuedAt` from the newest list in the merged history (§6), and `evalHighWater`/`lastAccepted` by the floor law, all through the clock owner's admission of the complete record — a record the clock owner would not itself produce is *unavailable*.

## 5. Continuity companion
My `carried` (merged source+target) compared against a post-fence *source* projection cannot be right when the target has history the source lacks. **[P]** Replace projections with exact BEFORE/AFTER images:
```
TrustContinuityV1 = { continuitySchema:1, executionId:E, intentDigest:D, case, source:{S,gen,schema}, target:{S,gen,schema},
  "sourceBefore": hex64, "sourceAfter": hex64,
  "targetBefore": hex64 | null,          // null = forward case, target capsule must be absent
  "targetAfter":  hex64 }
+ immutable siblings in the carrier root:  source-after.v1, target-after.v1   (the exact bytes to publish)
```
- AFTER images are fully determined at preparation: STP forbids any S4 evaluation or floor write between the image and the fence, and the audit events the AFTER capsules reference (source-fence reset; target genesis/merge) are written *first* as immutable files — orphans until a capsule references them — so `eventHead` in each AFTER image is already exact. This answers "source fence write also advances eventHead".
- **Retry rule, no clock and no guessing:** `sha256(source capsule)` ∈ {`sourceBefore` → not yet fenced; `sourceAfter` → fenced by this execution}; anything else ⇒ with an admitted matching companion binding, the existing QUARANTINE row; without one, *unavailable*. Same for the target with {`targetBefore` or absent, `targetAfter`}. A target whose floors are already high from an earlier transition is simply its `targetBefore` bytes — it is never mistaken for a partial write of this one.
- Publishing is "copy the sibling image → replace-publish", idempotent. Cross-check at preparation and at resume: `target-after.v1`'s six `FLOOR_KEYS` equal the separate floor image's `floors` (the two companions must not disagree); the closed floor image and the journal gain no member.
- Orphan AFTER images and orphan events prove nothing was committed; only the capsule hash does.

## 6. Revocation history without overflow amnesia
My "leave the capsule and refuse this call" was unsafe exactly as root says: the next call would not know the observation existed. And the "≈40,000 subjects" figure was an invented promise; withdrawn.
**[E]** `opensip-revocation.1`: `entries` `maxItems` 4096, `subject` ≤ 256 chars — each list is already bounded well inside the 4 MiB metadata bound. **[E]** nothing states lists are cumulative.
**[P]** Append-only history head, constant-size in the capsule:
`heads.revocation = {"version": n, "node": NodeRef, "depth": d}`; `RevocationHistoryNodeV1 = {nodeSchema:1, version, list: DocRef, prev: [NodeRef] (0..2), depth}` with `depth = 1 + max(prev.depth)`; two `prev` only for the ancestor merge of two histories.
- **A valid newer list is always accepted and the head always advances** — acceptance is never refused for size. Evaluating "is this subject revoked" traverses at most `D_max` nodes, each reading one bounded list; memory is one list at a time.
- **Exhaustion always refuses:** if `depth > D_max`, or any node/list is unavailable, every TRUSTED-entry, INSTALL and continuation evaluation for the store refuses with the existing reasons. Because `depth` is in the published head, the refusal is durable across calls with no separate blocked flag (root's preference), and nothing can be forgotten.
- Per Q1 nothing shrinks the history, including RECOVER-COMMIT; current authority predicates decide whether a retained subject still applies. Per Q3 no GC; compaction is a future separately reviewed owner. `D_max` is an owner number — I do not propose one; the only requirement is that it be finite and that its exhaustion is a refusal.
- No growing `lists` array anywhere; old lists remain retained documents reachable from nodes.

## 7. Audit record size and content
**[P]** My 4 KiB estimate is withdrawn: `payloadDigests` for a full air-gap payload and a closed `clockObservation` are not constant-size. Rule: the encoded event is preflighted against the existing product 4 MiB bound **before any effect**; over-bound ⇒ the event is refused as a resource precondition and nothing is published.
**[E]** `recoveryAuthorityShape.requiredOnRecoverCommit` has seven conjuncts (old-root identification, authority set, application, threshold, old/new/role binding, non-self-authorization, anti-rollback); `ceremonyTermination` is "a separate … record … Joined to the accepted abort event". **[P]** the COMMIT event therefore carries explicit references — `{oldRoot: NodeRef|null, newRoot: DocRef, role, authorityApplication: DocRef}` — rather than relying on `payloadDigests`; ABORT is two immutable events, the accepted abort at seq k and the termination at k+1 (`prev` = k), and the capsule revision references k+1. **[OPEN]** the byte shape of the *authority application* document: v14 reserves it (OD-112-1), v1 §4.1 gives numbers, S4.5's `recoveryAuthority` is the clock-floor authority — I found no schema for the root-ceremony application, so this cannot be frozen from available law.
**Honest language for attempts and crashes [P]:** a refused attempt publishes an event and a capsule revision whose roles are unchanged. If the process dies between the event file and the capsule, the orphan is *an unpublished record*, evidence of neither acceptance nor refusal; so v14's "Every ATTEMPTED event … appends" is satisfied for every attempt whose publication completed, and **not** for attempts interrupted before it. That limit should be stated, not engineered around with a second commit point.

## 8. `EV-REVOKE` on a reset role
**[E]** v14 fallback: `EV-REVOKE` "From ST-UNBOOTSTRAPPED … REFUSE stay", where `ST-UNBOOTSTRAPPED` means "No accepted root/index snapshot for this role". **[P]** Minimal current-owner change (one paragraph): that refusal applies to `bootstrap.kind == "initial"` only; a role with `kind == "reset"` — which by §1 implies a non-null record and resolvable evidence — dispatches `EV-REVOKE` as a bootstrapped role does; a standing reset leaves `ST-REVOKED` roles `ST-REVOKED`; ordinary PRESENT heals QUORUM-LOST under the entry guard and never REVOKED (agreed). **208 successor:** one conditional input on the event, e.g. `Revoke { newer_and_byte_valid, accepted_history: bool }`, asserted by the caller *from the classification in §1, never from the audit reason*. Until that law freezes, 208's refusal is the correct implementation of the retained machine, as root says.

## 9. Restore
**[E]** v2 §5.5: "Restoring any SC-TRUST bytes marks every role `ST-UNBOOTSTRAPPED` with audit reason `RESTORED`"; detected cases include "any restored state, because restore itself is the trigger"; not detected: "a coherent rollback of the whole install root by an attacker who also suppresses **the restore marker**". v8 §5.5: "declared restores".
**[OPEN — precisely]** *No owner defines the restore marker or the declaration.* The phrase occurs once (v2 l.465) with no carrier, shape, writer or reader; v8 says "declared" without saying how; the command inventory has no restore entry; and root rules out inventing a CLI. I therefore cannot state a lawful restore *path*; only its constraints, which are compatible with everything above:
- **[P]** admission of restored bytes is a fenced capsule **publication** (never an in-place acceptance), refused while any role is `ST-RECOVERY` and while any active transition slot is present (Q6);
- it applies the §1/§8 reset (`cause:"RESTORED"`, evidence = the restore's audit event), keeps `ST-REVOKED`, keeps `sourceFence` as restored — safe only *because* no active slot exists, so a later transition sees an old fence and supersedes it (no permanent deadlock);
- **[E]/[P]** v2's "counters below any document still on disk" is a **detection trigger that refuses**, never a way to *accept* roots: consistent with root's rule, a directory listing may cause refusal but can never supply a head. My 209 "merge upward against documents on disk" is withdrawn.
- Whole-install rollback remains undetectable, as stated.
