## 1. What the current formats and law already fix [E]
- **An ordinary payload is complete and single.** `payload.schema.json`: `members` is closed and **all eight are required** — `rootChain` (1..64), `catalog`, `revocation`, `manifests`, `envelopes`, `artifacts`, `permissionPolicies`, `repairMaterial` (an object **or** a typed absence). `payloadKind` is in the signed preimage. v14 `airGapPayload.missingMember`: "Refuse. Do not fetch. Do not refresh." So every ordinary import presents the root chain, one catalog and one revocation list **together**; there is no "catalog-only" or "revocation-only" payload.
- **Counters are shared.** One `rootVersion`, `indexSnapshotVersion`, `revocationVersion` per store (`TrustClockRecordV1`); S5 advances the root counter.
- **Events are per role.** v14: ordinary PRESENT → `TRUSTED` from `UNBOOTSTRAPPED/TRUSTED/EXPIRED/STALE-REVOCATION/QUORUM-LOST`; from `REVOKED` and `RECOVERY` it is `PAYLOAD-NOT-ADMISSIBLE` ("ST-REVOKED is not this member").
- **Role activity is in the signed root.** `root.schema.json` roles: `keys`, `threshold`, `namespaces`, optional `standing ∈ {active, typed-absence-DR-110}`.
- **Command surface.** `trust-import`: `opensip trust import PATH`, `flags: []`, steps `mutation, render`, parity fields `revocation-version, catalog-version, receipt-id, termination-class`. No role argument exists, and none is needed.
- **Not fixed anywhere:** whether acceptance is atomic across roles (GAP-1). v2 §4.7's "catalog 7 after 9" row shows a refusal with "state unchanged" and dashes elsewhere; it is *consistent with* the proposal below and proves nothing beyond itself.

## 2. Proposal [P] — all-or-nothing over a derived target set

**Target set (derived, never operator-supplied):**
`T = { roles whose standing is active in the payload's final root } ∩ { roles whose retained state ∈ UNBOOTSTRAPPED, TRUSTED, EXPIRED, STALE-REVOCATION, QUORUM-LOST }`.
Non-targets, with their reason: `REVOKED` and `RECOVERY` (v14 makes ordinary PRESENT inapplicable to them), and roles the final root leaves typed-absent. A non-target is **inapplicable, not refusing**: it does not veto. This distinction is what keeps one revoked role from blocking every future import — and therefore every future revocation list — forever.

**Order (one command, under the installation fence):**
1. Pre-dispatch: bounded parse, manifest authentication, member joins, member availability (`repairMaterial` must be the typed-absent form iff the final root leaves TR-REPAIR typed-absent — v14: "may omit repair material only as a typed absence, never as a silent hole"), S4 preflight. Refusals here write nothing (r4 D).
2. **S4 write-ahead revision** (`F`/`L`/anchor) — separate, first, and it stands even if everything after refuses (r4 K-4).
3. Admit the **shared triple as a unit**: root chain from the held head (S5), catalog, revocation list — signatures under the admitting root, anti-rollback against the three shared counters, expiry/freshness at `tEval`. Any failure ⇒ the import refuses; **no head, no counter, no role changes.**
4. Dispatch the list's newly applicable role-level revocations (`EV-REVOKE`, namespace / TR-INDEX snapshot frames as settled in r4). A target that becomes `REVOKED` here **leaves T**; that is a named accepted event, not a veto — revocations must flow.
5. Evaluate the ordinary TRUSTED-entry guard of every remaining target against the admitted triple. **Any target's refusal ⇒ the whole import refuses**, including steps 3–4: nothing is published.
6. All pass ⇒ per-role event records, then **ONE capsule revision**: the three heads and counters advance once; every target is `TRUSTED` with `acceptedUnder` = the new head; roles revoked in step 4 are `REVOKED`; non-targets keep state and `acceptedUnder`.
7. **One necessary addition:** a role that *had* standing and that the new head no longer activates cannot remain `TRUSTED` under a root that does not list it; it takes the private standing-reset operation (r4 K-7) in the same revision. This is the only case where an ordinary import changes a non-target.

**Consequences that make this minimal:**
- For every role with standing, `acceptedUnder == head` after any accepted import, so the divergence I worried about never arises outside the two already-owned cases (`REVOKED`, reset). No "which root owns this context" rule is needed for ordinary operation.
- `REVOKED` is never healed: it is never a target, its `acceptedUnder` never moves, and its later ceremony finds the current head as authority.
- No new signed kind, flag or role scope: T is a function of the **signed** final root and the **retained** states.
- A begun batch already blocks a head-advancing ordinary import (r4); a same-head import simply has `RECOVERY` members as non-targets.

**Command outcome.** Existing surface only. Accepted ⇒ success with the new `revocation-version`/`catalog-version` parity fields; per-role results (including a role that became `REVOKED` in step 4) are diagnostics of a *successful* import. Refused ⇒ the existing refusal of the failing step, with the versions unchanged. There is no "partially imported" class.

**Availability cost — stated, not excepted.** One applicable role's failure blocks the shared metadata for everyone, *including a newer revocation list in the same payload*. That is a real cost: a publisher error in, say, the catalog delays delivery of revocations by air-gap until a correct payload exists (the consented refresh path is separate). I considered "accept root+revocation, refuse only the catalog" and reject it for this owner: it is partial shared-head acceptance, it creates exactly the head/`acceptedUnder` divergence that then needs a second rule set, and the payload is *one* TR-BUNDLE-signed unit. If the revocation-delay cost is judged too high, the right instrument is a separate, explicitly owned revocation-only delivery — not an exception inside this one.

## 4. Producer join A — "not expired" in v1 §4.1 and the closed key format
**[E]** v1 §4.1 counts role keys "listed in the current accepted root document, **not expired**, and not revoked". **[E]** `root.schema.json` keys are `{keyId, publicKey, label}` — **no per-key expiry exists**; v1 §3.1's table says role keys' lifetime is "listed in root", i.e. the *document's*. **[E]** v1 §4.2: root expiry ⇒ "`ST-EXPIRED` for every role" through `EV-CLOCK`.
So in the closed format "not expired" has no independent key-level representation, and it must **not** be read as "when the root expires, availability is zero": that would turn a root expiry into `QUORUM-LOST` — a stickier state with a different rank than the `EXPIRED` v1 §4.2 prescribes. **[P] statement for the owner:** key availability for a role = `|role.keys listed in the context root| − |those whose keyId is in the retained revocation history|`, **independent of any document expiry**; expiry is reported only through `EV-CLOCK`. (`EV-QUORUM-OBSERVE` from `ST-EXPIRED` can still yield `QUORUM-LOST`, by v14's named transition, when *revocations* drop availability below threshold — never because of the expiry itself.) If per-key expiry is ever wanted, it needs a root-schema successor; nothing should infer it today.

## 5. Producer join B — abort of a never-established member with no accepted head
**[E]** v14 abort `toFunction`: "selects the first **still-true** candidateInOrder [REVOKED, QUORUM-LOST, EXPIRED, STALE-REVOCATION], else ST-UNBOOTSTRAPPED. Never ST-TRUSTED." **[E]** such a role's only pre-BEGIN state is `ST-UNBOOTSTRAPPED`, where `EV-REVOKE` refuses and `EV-QUORUM-OBSERVE` is an accepted stay — v14 attributes no revocation or quorum condition to a role with nothing accepted.
**[P] rule:** "still-true" means *established by retained evidence*, evaluated in the **outside-ceremony** context, because ABORT closes the ceremony and r4 clears the staged reference. For this role: `REVOKED` — no OLD subjects ⇒ false; `QUORUM-LOST` — the outside-ceremony context is "the current accepted root document" (v1 §4.1) and **none exists** ⇒ not established ⇒ false; `EXPIRED`/`STALE` — clock phase is not `retained`, accepted times are null = **unknown, which is not "true"** (r4 K-6). Result: **`ST-UNBOOTSTRAPPED`, initial, `acceptedUnder` null** — exactly its pre-BEGIN state.
Neither candidate context is used: the **bound candidate root** stops being a context the moment the batch is closed (using it would be a fabricated accepted root); the **embedded core anchor** is an *authority* for authorizing a ceremony (215 A) and for S4 time evidence, not an accepted root whose role keys define this role's availability. One adjacent case to state so it is not mistaken for this one: if such a role left `RECOVERY` *during* the ceremony through the prospective-root quorum observation, it is `QUORUM-LOST` by a named, evidenced event and receives no abort (r4); its evidence record carries the candidate binding, and both of v14's exits from `QUORUM-LOST` (ordinary PRESENT, BEGIN) remain open to it.
