## 3. Findings

### S-1 (Medium–High) — restore-recovery launders `REVOKED` for a member that entered `RECOVERY` from `REVOKED`
r4: "Retain N's Revoked standing … **Reset every other established role to UNBOOTSTRAPPED** … If N has a begun batch, close it with private batch-termination cause RESTORED … do not fabricate v14 ABORT." A batch member that BEGIN took from `REVOKED` has state token `RECOVERY` in N, so it falls under "every other established role" and becomes `UNBOOTSTRAPPED`. From there an **ordinary** import is a lawful TRUSTED-entry (215 C.3), and 215 C.1's amended `EV-REVOKE` from reset-`UNBOOTSTRAPPED` fires only for *newly applicable* OLD subjects — the revocation that put the role in `REVOKED` is not new. Net effect: rollback + `acknowledge-restore` converts "`REVOKED` ends only through authorized recovery" (r4's own RoleRecord text) into "healed by the next ordinary payload". v14's own abort would have returned this member to `REVOKED` (first still-true candidate). Probe P1 on the owner's model: role before BEGIN `REVOKED`, in N `RECOVERY`, after restore-recovery **`UNBOOTSTRAPPED`**; the model's mapping is `'REVOKED' if tip.role=='REVOKED' else 'UNBOOTSTRAPPED'`.
**[P] one rule:** when restore-recovery closes a recovered batch, an established member still in `RECOVERY` returns to **`REVOKED` if its retained `conditionEvidence.revokedBy` is non-null** (equivalently, its `BeginBatch.beforeRoles` state was `REVOKED`), with the RESTORED ceremony-termination evidence; otherwise `UNBOOTSTRAPPED`/`RESTORED`. No ABORT and no S4 are needed — this is evidence-only, like root's never-established rule. Add the model case and a variant. (The same question exists for 215 C.4 resets meeting a begun ceremony; not reviewed here.)

### S-2 (Medium) — the system itself writes the entry that makes its bucket unexaminable, turning "publications blocked" into "all authority denied, no recovery"
Per-bucket bound 64; "the 65th refuses this profile, with no automatic cleanup". Every publication attempt that fails after its descriptor barrier (crash, failed replace) leaves one orphan at the **current tip**; each retry builds a different descriptor (events carry invocation identity), so nothing is idempotent. Probe P3: with 64 orphans the 65th `prepare` is still **permitted** (bucket ≤ 64 ⇒ clean) and writes entry 65; from then on `detect` is `Unavailable:bucket-bound`, so by r4's own law *all* authority admissions are denied, S4.5/ABORT are blocked, and `acknowledge-restore` is unavailable too — permanently, with no owned remedy.
**[P] minimal rule:** a publication whose bucket already holds the bound **refuses before writing** (it would make its own predecessor unexaminable). The store then degrades to "no new publications from this tip" while detection stays *clean* and existing authority keeps working — the restrictive half of the failure instead of the total one. The residual stuck state (64 consecutive failed publications at one tip) still needs the owed adoption/cleanup owner; say so next to the bound. Add `orphan-64-then-publish-refuses` as a model case; today `orphan-65` asserts the brick as expected behaviour.

### S-3 (Medium) — unknown or non-canonical names make the bucket unavailable, which adds no detection power and one realistic permanent denial
"Unknown names are left untouched and cause unavailable, never adopted … or ignored as clean." A successor can only be evidence at a name that is 64 lowercase hex **and** equals the content hash; a non-canonical name can never be a descriptor, so ignoring it cannot hide a proven successor — renaming a real descriptor away is just deletion, i.e. the disclosed coherent-rollback gap. What the rule does add: any stray entry in the *tip* bucket (on macOS, a Finder-created `.DS_Store` written by the same user who owns the directory; editor/backup droppings) permanently denies all authority, and nothing may remove it. **[P]:** non-canonical names are charged to the profile, reported by diagnostics and left untouched, but are **not** an unavailability cause; *canonical*-named entries that fail admission (unreadable, hash mismatch, malformed, wrong store/revision/predecessor) stay unavailable, as now. The 64 bound then counts canonical entries for the decision and all entries for work.

### S-4 (Low–Medium) — which descriptors may *prove* a predecessor
The durability inference is stated for a descriptor whose native predecessor **is** its logical predecessor. A `restore-recovery` descriptor names N as `previousCapsule` while the file it reconfirmed was n, so by itself it is not independent evidence that N was durably current — N's evidence is the chain it retains. The model counts any bucket entry: probe P2 (crashed recovery leaves orphan D′; the ordinary prover D(N+1) later disappears) still reports `behind`, with N now "proven" solely by a `restore-recovery` descriptor. Harmless while D′'s retained proof must itself admit, but the text never says so. **[P]:** a descriptor proves its `previousCapsule` iff `nativeBefore` equals it; a `restore-recovery` descriptor counts as a prover of N only when its retained proof chain (including the original terminal witness) admits — otherwise the result is unavailable, not proven. Also choose the terminal witness retained in the restore event from **ordinary** entries of N's bucket; the model takes `sorted(bucket)[0]`, which after a crashed attempt can be the previous recovery's own orphan.

### S-5 (Low) — the null predecessor needs the same law
"First creation has no predecessor and follows its separate creator law" — agreed that the creator is owed, but r4 introduces `initial/S/D` as a bucket, so one obligation belongs here: a store whose capsule file is **absent** while `initial/S` holds a descriptor whose child is proven is the rollback-to-nothing case; the owed creator must run the successor check on `initial/S` and refuse (behind/fork/unavailable) rather than create. One sentence now prevents the creator from becoming the bypass.
