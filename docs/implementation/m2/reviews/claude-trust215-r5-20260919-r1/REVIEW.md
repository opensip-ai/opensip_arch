## 3. Findings — finite policy / reachable-state contradictions

### F-1 (High) — a begun batch whose members have all been interrupted can never be closed
**[E]** v14 names `ST-RECOVERY --EV-REVOKE--> ST-REVOKED` and `ST-RECOVERY --EV-QUORUM-OBSERVE--> ST-QUORUM-LOST`; `EV-RECOVER-ABORT` outside `ST-RECOVERY` is the fallback refusal `RECOVERY-ABORT-NOT-IN-CEREMONY`.
r5 C: an interrupted batch "cannot commit; remaining RECOVERY members and the batch binding are closed together by ABORT"; "a begun batch blocks a different BEGIN"; head-advancing ordinary PRESENT refuses "while a batch is begun (including interrupted members not yet closed)".
**Reachable:** a one-role batch (or any batch) whose every member exits by REVOKE/QUORUM-OBSERVE. No role is in `RECOVERY`, so ABORT is inapplicable to every role; the binding stays begun; a new BEGIN (the only lawful exit from the member's new `REVOKED`) is blocked; every root-advancing import/refresh is blocked. No operator action exits this state.
**[P] correction (one rule):** the batch binding is closed by a private, evidenced *batch-termination* record (same family as C.4; not a v14 event). It is published (a) in the same revision as the event that removes the **last** `RECOVERY` member — cause `INTERRUPTED`, no operator step, no fictional ABORT; or (b) by the ABORT command together with the per-member `EV-RECOVER-ABORT` events of the members still in `RECOVERY` (≥1). Both clear the staged reference.

### F-2 (High) — C.2 and C.3 contradict each other on key loss, and the safe reading is the one the text excludes
C.2: on publication, derive available-key observations "from the admitted AFTER context … include their applicable named events in the outcome revision"; "REVOKE observations precede available-key observations". C.3: after tentative REVOKEs, "check every remaining target's prospective entry. Any failure abandons ALL …"; "All remaining targets become TRUSTED".
**Case:** head root 5; TR-COMPONENT keys {k1,k2,k3}, threshold 2, `TRUSTED`. Payload: same root 5, root-signed list 10 with keyId entries for k1,k2 (**[E]** v1 §3.1: revocation entries are "signed by root threshold", so the list authenticates independently of the role). AFTER-context availability is 1 < 2.
- If availability is part of the target's entry (C.1 says so for recovery: "too few unrevoked replacement keys also refuses"), the **whole import refuses and list 10 is never accepted**: the install keeps trusting k1/k2, and S6 never sees them. The list that reports the compromise is the one payload that cannot be delivered.
- If it is not, COMPONENT becomes `TRUSTED` and, by C.2, `QUORUM-LOST` in the same revision — contradicting "all remaining targets become TRUSTED".
**[E]** v14 gives this situation a named outcome (`TRUSTED/EXPIRED/STALE → QUORUM-LOST`, guard "observed signers < threshold AND REVOKED does not also hold"); v1 §4.1 defines the count.
**[P] correction:** treat key loss exactly as C.3 already treats role revocation. Tentative order: (1) OLD-subject `EV-REVOKE`; (2) AFTER-context `EV-QUORUM-OBSERVE` for every remaining target — a target below threshold takes its named `QUORUM-LOST` event (or, if already `QUORUM-LOST`, its accepted stay) and **leaves the target set; it is not a veto**; (3) entry guards of the remaining targets. "All remaining targets become TRUSTED" is then true as written. Residual cost, to state rather than hide: if the payload also carries members that only that role's lost keys sign, F-3's scope rule decides whether they matter; the publisher's complete remedy remains v1 §3.1 root rotation.

### F-3 (Medium) — "REVOKED/RECOVERY are not vetoes" is false for the two roles whose signatures the import itself relies on, and "relied-on" is undefined
**[E]** the manifest is TR-BUNDLE-signed and the catalog TR-INDEX-signed; v14 `roleToKeyAndDelegatedNamespace`: "the signer is authorized for this trust role and namespace". r5 C.3 publishes the catalog head as part of the one unit even when INDEX is a non-target, and authenticates everything through BUNDLE even when BUNDLE is `REVOKED`. It also says "complete member joins" and "all relied-on incoming signatures" precede dispatch without saying whether a non-target role's own members (e.g. component envelopes while COMPONENT is `REVOKED`) are relied on — if they are, one `REVOKED` role refuses practically every real payload and the worked "one REVOKED" outcome is unreachable.
**[P] correction (two sentences):** (i) *Shared-member authentication is a signature predicate in the PROSPECTIVE frame, independent of the signing role's retained state:* keys and namespace/snapshot subjects delegated by the payload's final root, filtered by the retained∪incoming revocation view. If those prospective subjects or keys are revoked the import refuses (so a BUNDLE whose current namespace is revoked does veto, inherently); if the final root re-delegates healthy ones, the member authenticates while the role's *state* stays `REVOKED` and unhealed. (ii) *Relied-on = manifest + root chain + catalog + revocation list + the members owned by target roles.* Members owned by non-target roles are inventory-verified against the BUNDLE-signed manifest and otherwise inert: not admitted, not vetoing. This keeps C.1's OLD/PROSPECTIVE discipline and makes the empty-target case (below) well defined.

### F-4 (Medium) — atomic refusal conflicts with v14's outcome determinism and audit rule unless it is made a guard conjunct
**[E]** v14 `outcomeBranchDiscipline`: an applicable member whose guard holds yields `accepted`; `auditAndWaiver`: "Every ATTEMPTED event — including guard failure and fallback — appends {…}". r5 C.3 abandons would-accept siblings' events and tentative REVOKEs; D says a dispatched event requires its record. As written, a sibling whose guard *holds* is neither accepted nor recorded — an actual conflict with retained law.
**[P] minimal amendment:** add one explicit conjunct to every ordinary TRUSTED-entry member — *import completeness: every target's remaining conjuncts and all shared guards hold*. Then v14's own discipline produces the atomic result: on failure the guard is false for **every** target, each takes the existing fallback (`to == from`, `PAYLOAD-NOT-ADMISSIBLE`, "invalid or incomplete payload"), each is audited as refused (≤6 records, one audit-only revision after the S4 revision), and no sibling is mis-recorded. Tentative REVOKE/QUORUM observations are *evaluations*, dispatched only on success; say so, so D's "dispatched" boundary is exact. The diagnostic names the first failing conjunct; no new reason or result class.

### F-5 (Medium) — the REVOKE subject frame for a member *inside* `RECOVERY` is unstated; it decides whether never-established `REVOKED` is reachable
C.2 fixes only the availability context in `RECOVERY`. **[E]** v14 allows `RECOVERY → REVOKED`; `EV-REVOKE` from `UNBOOTSTRAPPED` refuses; `EV-QUORUM-OBSERVE` there is an accepted stay. So a never-established role can reach only `UNBOOTSTRAPPED`, `RECOVERY`, `QUORUM-LOST` (via the prospective observation) — and `REVOKED` only if a revoke is dispatched to it in `RECOVERY`, where it has no OLD subject.
**[P]:** inside `RECOVERY`, `EV-REVOKE` is dispatched only for newly applicable **OLD** subjects; a hit on the BEGIN-bound **prospective** subjects is a COMMIT-guard refusal (C.1 already says it "refuses role activation"), not an event. Consequences to write down: never-established `REVOKED` is **unreachable** (so C's "must be tested with pre-genesis REVOKED/QUORUM-LOST/RECOVERY" should read: QUORUM-LOST and RECOVERY reachable, REVOKED a must-refuse fixture); C.2's abort paragraph ("no established subjects ⇒ revocation not established") becomes a theorem rather than a separate rule.

### F-6 (Low) — BEGIN can publish a member that exits in the same revision
C.2 derives availability on "begun ceremony binding" publication. If a derived member's prospective availability is already below threshold, BEGIN publishes `RECOVERY` and `QUORUM-LOST` together — an interrupted batch at birth (and, for a one-role batch, F-1). **[P]:** make "every derived member's prospective availability ≥ threshold under the current revocation view" a BEGIN guard (`RECOVERY-BEGIN-REFUSED`); staging step 6 already computes the inputs.

### F-7 (Medium) — "missing proof ⇒ dependent operation unavailable" has no stated exit
D makes every "dependent trust operation" unavailable when `T` is missing/unadmittable, without defining dependent. If import, refresh **and** S4.5 are all dependent, a retained-phase store with a lost proof has no remedy at all, although S4.5 "replaces the provenance of L". F/L are honoured as numbers regardless (never lowered), so blocking adds no clock safety; what the proof protects is any claim that L is *authenticated*.
**[P]:** keep the strict choice, and close it: *dependent* = every operation that publishes a role/head outcome or carries L as admitted time across continuity; *not dependent* = read-only diagnostics, ABORT/batch termination, and S4.5 challenge/import in phase `retained` (which relies on R, the pending challenge and recovery authority, and installs a new `T`). In P1 the remedy is the already-named fresh installation/adoption. Also state the retained closure for a witness taken from an import that is later **refused** (manifest, its envelope, root chain, revocation list — metadata-cap bounded), and that a chain-valid root appearing only inside a proof context is *authenticated-not-accepted*: never a head, never authority (consistent with E's "highest ALREADY ACCEPTED root").
