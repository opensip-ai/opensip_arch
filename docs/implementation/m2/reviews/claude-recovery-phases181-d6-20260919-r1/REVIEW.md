## Result: no conflict found with an existing owner. Three points need to be said explicitly.

### 1. "No S4 writes" is too broad as worded — floor carry *is* a write of S4 state
S9: "Floors (`rootVersion`, `indexSnapshotVersion`, `revocationVersion`, `evalHighWater`, `lastAccepted`, `recoveryEpochSerial`) copy forward into the new store." `evalHighWater` and `lastAccepted` are the S4 floor F and L. Resumed store work in Phase B therefore writes S4 *state* into the new store, as a copy. What Phase B must not do is perform an S4 **decision evaluation** (which computes tEval and writes F write-ahead, and can refuse `CLOCK-EXCURSION-FORWARD`). Suggested wording: "no S4 decision evaluation and no evaluation-driven floor/anchor write; floor carry is a forward-only copy owned by `migrate_floors`/`rollback_floors`." Otherwise the enumerated Phase B exception list contradicts its own prohibition. The same sentence should keep S9's existing rule visible: "a poisoned floor is not lowered by migration or rollback; only S4.5 lowers it."

### 2. Moving PRESENT/roles to Phase C creates a durable resting state that should be declared lawful
S9 places "roles re-establish by the PRESENT event over the embedded chain" inside the migration paragraph. If PRESENT belongs to Phase C, then after Phase B completes a resumed store commit and the slot is durably retired, the installation can rest indefinitely in: **new store selected, floors carried, roles not yet re-established** — whenever Phase C refuses (that is exactly the expired / floor-ahead vector V1) or the process stops between B and C. I believe this state must already be reachable today (a crash between the final rename and PRESENT), so this is not new behaviour; but the phased text makes it a normal, reachable outcome rather than a crash window, and the trust-only commands are then admitted against it (slot absent). One sentence should say this state is lawful, what a reader or trust-only command observes in it, and that the next S4/S5-owning entry performs PRESENT. If some owner requires roles to be established for a store to count as "selected", that would be the conflict — I did not find such a sentence, but I only searched S9/S9.2/S15.

### 3. A structural reach/schema check that can fail *after* the footprint says `RESUME-COMMIT` has no action in the recovery table
S9: rollback "refuses when the new store accepted a root the old core cannot verify (schema or chain reach)"; and "a new core whose embedded chain does not reach the accepted root refuses `ROOT.FLOOR_ABOVE_CORE`". The direction keeps these as Phase B reads "for the retained journaled target during resumed store work". `recover_transition_journal`'s outcomes are `ABORT`, `RESUME-COMMIT`, `RELEASE-ONLY`, `QUARANTINE`, `BUSY`, `REFUSE(fence)`. For a store operation at `PREPARED` with the old store fenced `RESTORED`, the table says `RESUME-COMMIT` from step 3 — the old store is already fenced, i.e. past the point where `ABORT` is the footprint's answer. **Open question I could not answer from prose:** are the structural checks evaluated only before `PREPARED` is reached (in which case a resumed commit can never fail them and Phase B merely re-reads what was already true), or can they be evaluated at resume time and fail? If the latter, the owner must name the Phase B outcome (it cannot silently be "refuse and leave the slot nonterminal forever", since that re-creates a wedge that no executor can clear; `QUARANTINE`/`MIGRATION.CORRUPT` is the existing fail-closed vocabulary, but it is a strong claim for a merely unreachable root). If the former, say so, and the "limited Phase B trust-state reads" are then confirmations with no refusing branch — which is the cleanest result and worth a vector.

## Two smaller consistency points

- **Pending challenge.** S9: "the boot anchor and any pending challenge do not [copy forward]". So after a resumed store migration an S4.5 challenge issued before the transition is gone regardless of `bootId`/`expiresMono`. This belongs next to the 178 N-2 wording (challenge expiry/reboot cost) the owner already plans, and it supports — it does not conflict with — blocking `trust recovery-challenge` on a nonterminal slot.
- **D2.** Agreed and consistent with S9's "Recovery from the durable footprint only" and S9.2's "a committed transition is finished, never reversed, even after the rollback window". The S15 sentence "Commit rechecks generation and current target trust" needs the qualifier "first-pass commit of a Phase C transition" *in S15 itself*, not only in S9.2, or the two owners will still disagree on a plain reading.
