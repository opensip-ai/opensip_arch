## Issue 1 — "nothing under I/trust … written" vs the S4 write-ahead. **Root is right; my invariant was wrong.**
**[E]** S4 (`security-and-lifecycle.md` l.410–453): a *decision evaluation* is ordered steps 1–5 ending "tEval = max(F, W, A). The floor written is exactly tEval (write-ahead, §5.6 durability) … L advances to A when A > L. The anchor is rewritten when continuity is unavailable…"; only "Report-only evaluation (doctor) computes the same decision, states and findings, labels `evaluationMode: report-only`, and returns `writes: []`". S9.2 exempts only transition Phases A/B from evaluating S4. A restore is a decision-mode mutation that admits closures under **current trust**, so it owes the ordinary evaluation: F (and possibly the anchor) may advance, and the evaluation may dispatch ordinary `EV-CLOCK` role transitions (e.g. `TRUSTED → EXPIRED`), after which closure admission may lawfully refuse. Under 222 that is a clock revision (and possibly a role-event revision) published by the capsule owner, preceded by the successor check and predecessor-durability reconfirmation like every other authority admission. "Byte-identical capsule/floors across every outcome and crash point" contradicts this and must not be adopted; disabling the write to satisfy it would break S4's "no later evaluation runs earlier than an earlier one".
**[P] corrected property — non-interference plus monotonicity, not immutability:**
1. *No bundle-supplied input.* The bundle is not a signed trust payload; its S4 evaluation is the 225 "no new signed source" row (no witness, null presented root). No byte of the bundle is an input to any `I/trust` write.
2. *Host-owned effects are allowed and unsuppressed:* F/anchor write-ahead and any ordinary clock-driven role events, exactly as the same invocation would produce them with an empty or refused bundle.
3. *Unchanged by restore:* L and its `T`, the three heads and counters, `recoveryEpochSerial`, revocation history, `selection.pair`, lineage, journal floors. *Never:* any floor or counter lower than before.
4. Demonstration **[I]**: a *differential* check — for the same record and observation, the `I/trust` outcome of "restore bundle X" equals that of "restore rejected at pre-dispatch + the same decision evaluation", modulo operation/event identities — at every crash point; plus refusal of bundles carrying trust-shaped members. That is what "backup restoration preserving trust floors" can honestly mean.
*Correction to reconcile §2 item 4 and §4:* replace "nothing under `I/trust` … is read for authority or written" with the four points above.

## Issue 2 — receipts in the bundle. **Root is right; a name-based ban is wrong. The inherited unit is the commit inventory.**
**[E]** identity l.1379–1383: "`commit-inventory` is the record digested by `commit-receipt.inventoryDigest`: `{schemaVersion: 2, runId, objects, blobDigests}` — **the exact set of typed object identities and retained raw blob digests the commit published for that Run**. The receipt authenticates RunId and this inventory and **remains operational custody evidence excluded from semantic IDs**." l.539–540: "Nonces, expiry, signing receipts and local executable paths are not fields in the semantic projection." l.1674–1676: "Receipt signing is operational custody evidence and excluded from semantic IDs."
**[E]** but some *receipts are evidence inside the closure*: native `stageReceipt`s are part of host capture — `native-evidence.md` l.3046–3051: after Coverage/Complete "`capture_occupancy` / `bind_worker_occupancy` require dispatch **and** receipts/views. The matching selected view digest MUST appear in that receipt's `outputRefs`"; l.3107 lists "`hostCapture.stageReceipts` (capture)". Likewise an `import2` carries "its execution provenance" (identity l.536) and `ImportObservationV1` inside the wrapper (workflows §4). A replayable Run "retains them all" (identity l.1411).
**[P] corrected rule:** *the bundle's object set for a Run is exactly that Run's `commit-inventory` (`objects` + `blobDigests`), byte-for-byte — whatever typed objects it names, including native stage receipts, import2 wrappers and their provenance/observation records — carried as **inert referenced evidence** and re-verified by complete replay.* What is **never** carried is the origin's *ledger custody layer*, identified by record role, not by filename: `commit-receipt`, attempt/`AttemptCustodyV1` rows, recovery associations, pin rows, lease/witness/journal state, grants and authorization descriptors' nonces, the native-preparation **execution receipt as an authority** ("an execution receipt alone does not supply evidence", native l.4216), and anything under `I/trust`. An origin receipt that *is* a member of the commit inventory travels as data; it confers nothing locally because local authority comes only from a local `CommitSession`. The origin `commit-receipt` may be *described* in custody metadata (signer key id, sequence) for provenance display, never admitted as a receipt.
*Correction to reconcile §2:* delete "execution or custody receipt" from the blanket exclusion list; substitute the rule above.

## Issue 3 — a foreign Run cannot be slipped into the authoritative ledger; the two cases differ
**[E]** build plan l.84–90: "Maintenance cannot insert an authoritative Run by using a restore or migration helper: imported evidence is revalidated before local adoption"; l.62–80: the only publication path is `prepare_commit(ReplayedRun, CommitSession)`; "`ReplayedRun` establishes semantic validity, not compiler truth, present custody or current availability. `CommitSession` establishes operational admission, not semantic validity … created only by security admission over registered project/store custody, an owned live platform writer guard, actual grants and operation identity … acquisition never follows from a Run's semantic grant projection."
**[A] narrowly:** `identity-schemas.v3.json` (and v2) define `commit-receipt` with exactly `{schemaVersion, runId, executionId, namespaceId, commitSequence, inventoryDigest, sealedAssurance, signerKeyId}` and `availability` with `{schemaVersion, runId, generation, state, missingRefs, reason}`; neither has a custody/origin/operation discriminator, and no `$defs` entry for an imported-custody record exists; the words "imported-custody receipt" occur once (identity l.1805). I did not find an imported-custody row in the storage boundary table of the build plan. So the concept is inherited; its record, its ledger row and its consumers are not.
**Case A — restoring a Run this project already sealed locally.** **[E]** identity l.1596–1602 and l.1842–1855: "Regeneration … publishes recovered availability only if all required bytes agree"; "An availability transition increments generation and never rewrites a sealed Run"; "Verified restoration requires the same complete identity closure and replay result before availability returns to retained". This needs **no new standing**: the local commit receipt already exists; the restore supplies bytes, replay verifies, availability advances. It is an authorized maintenance API use of the kind the build plan allows, because nothing authoritative is inserted.
**Case B — a Run never committed here.** Maintenance is forbidden; the lawful path is the guarded facade: local complete replay ⇒ `ReplayedRun`; security admits a `CommitSession` for the **`evidence-restore` operation** (local ExecutionId, local namespace, the producer closure admitted under current trust); `prepare_commit` publishes. The resulting local `commit-receipt` is truthful about what it says — *this host committed this inventory under this ExecutionId* — but says nothing about who evaluated the Run. **[P] smallest typed distinction:** one additional closed record published in the same commit, keyed by `runId` and joined to that `executionId` — the inherited "imported-custody receipt": origin (bundle seal digest, origin ProjectId, origin host release) + local verification (replay result, closure trust origins). `commit-receipt` stays unchanged. A Run's *local standing* is then derived, not asserted: `evaluated` iff its commit attempt's operation is an analysis/verify seal; `imported` iff an imported-custody record exists for it.
**Consumers — the union must be written, not implied.** **[E]** the only existing closed list of authority consumers is for the ephemeral branch (workflows l.242–246): an ephemeral result "cannot satisfy **baseline adoption, repair preview/apply, verify or authoritative replay**". **[E]** baseline eligibility today: the descriptor pins "the **authoritative** `run3` and `plan2` (an ephemeral result is refused: `BASELINE.SOURCE_EPHEMERAL`)" and "Adoption pins the Run and the pivot closures as retention roots". **[P] smallest rule for `imported`:** the same four consumers refuse it as an authority source (a typed detail is owed; no existing code fits — `…EPHEMERAL_CANNOT_SUPPLY_AUTHORITY` would be untruthful); it **is** eligible (i) on read surfaces (`query`, `inspect`, `candidates`, `review-brief`, `baseline show`) with its standing displayed, (ii) to *satisfy retention/availability* of a Run that a tracked baseline already pins — which is exactly what a freshly adopted project needs, and requires no authority because the baseline artifact, not the local Run, carries the comparison base ("Comparison never reads the origin machine's store"). Portable baselines therefore keep working through the tracked artifact; `baseline adopt --run` of an imported Run is refused until a contract deliberately admits it. *Correction to reconcile §2 step 3(b):* replace "only where those contracts already accept…" with this explicit union.
