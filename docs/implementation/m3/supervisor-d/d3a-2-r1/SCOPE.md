# D3a-2 r1: item 16's ceilings and bounds, and item 12's tool class (M3-D r5 items 12, 14, 16, 17 and 22's tool row; D3a plan r4, sub-unit D3a-2)

**Lead scope record, 2026-10-17. Unreviewed candidate, round 1.**

It implements sub-unit D3a-2 of the D3a plan r4 (`../d3a/PLAN-r4.md`, accepted by Codex `codex-d3a-plan-r4` with the LD-D3A-17 amendment): item 16's ceilings and bounds, the tool-materialization accounting interface (LD-D3A-16), and the zero-fit refusal. By the lead's decision on the D3a-1 r2 question, it also lands **the supervised tool class**: item 12's tool path (fds 0 to 2, fd0 at EOF, skipping `Handshaking`, :434), with the tool output bound and the materialization accounting that own it (items 12; 16, :533, :548, :549; 17; 22, :722).

- **Library only:** no production caller. MC item 12's `cargo metadata` adapter (C3b) builds the tool's launch and reads its output; C3's materializer calls the accounting; J2b composes the provider path with D4.
- **Base (LD-D3A2-5):** product main `72e0787`, with D3a-1 r3 integrated (Codex `codex-d3a-1-r3`, ACCEPT-UNIT) on the C1a4 blind unit's `0772eb7` and `3742822`. D3a-2's diff is three files, all of which D3a-1 added.
- **Not here:** D3a-3's records (including `supervision.limit.breached`'s registration and the `tool.process.*` records, item 21, :692), discard and the admission gate; D3b's descendant step, user cancellation, revocation and harness coexistence.

## The tool class

| Rule | Where | Implementation |
| --- | --- | --- |
| Launch class `Tool`: fds 0 to 2, no control plane | item 1, :188; item 5, :274 | `prepare_tool` requires `DescriptorSet::Tool`. The platform (D1a) closes fd0's write end at spawn, so the tool reads EOF at once; fds 3 and 4 do not exist. |
| Tools skip `Handshaking` | item 12, :434 | `start` goes `Spawning` → `Running` and appends `Running`; no control frame is sent, so no hello, health, liveness or shutdown runs. |
| fd1 is the tool's output, under a bound | item 5, :274; item 16, :548 | The loop reads fd1 itself (a tool has no participant), at most 16 reads of a 64 KiB buffer per turn (a service quantum, as stderr's, LD-D3A1-8). Each read's bytes are charged to `ToolOutput` **before** they are kept. Past 268,435,456 B the refusal `ToolOutputBound {observed, limit}` is recorded, nothing more is kept, fd1 is closed, and `byte-bound(tool-output)` starts the ladder (LD-D3A2-3). The bytes are never parsed here. |
| stderr | item 17 | As every child's: read continuously, counted, never kept. |

| The end | item 13 (J-3); item 22, :722 | A tool's end of output is fd1's EOF. Its exit, with every channel at EOF (or the drain expired), is its end: **`clean` with the tool's own exit, whatever it is** (LD-D3A2-2). |

## Lead decisions

- **LD-D3A2-1. One state machine for both classes.** Item 12 states one `Supervision` per child, with one state table in which tools skip `Handshaking` (:434). So the tool class is the same machine, not a second one: the ladder, reap, settlement guard, trigger gate, unwind, tree confirmation, stderr count, scratch removal and item 16's sampler are shared, with every rule D3a-1's three review rounds settled. The class is fixed at preparation (`Class {Provider, Tool}`). The provider-only parts (the selection, participant, protocol waits, control session and reader) are `Option`s, present exactly for the provider class; every provider-only path reads them through their `Option`, so a tool cannot reach them. The tool's participant type `NoProvider` is uninhabited: the compiler proves no participant call is made for a tool.
- **LD-D3A2-2. A tool's end, and its fault.** A tool has no terminal frame. Its end of output is fd1's EOF, and its death after that is expected: its supervision ends `clean`, the exit recorded as the tool's own, zero or not. `clean` here says only that no teardown trigger fired; item 22's tool row routes "a tool fault" through MC item 12's adapter (:722), which reads the exit (NE:1789-1791). A tool's death with fd1 still open at the drain's expiry (a member holding it) is `unexpected-exit`, as a provider's death before its terminal is, and the ladder kills the group. No cause is added.
- **LD-D3A2-3. `byte-bound(tool-output)`.** Item 12's closed causes include `byte-bound(kind)` (:446), and item 16's byte-bound table has the tool's fd1 row (:548). The breach is that cause with the kind `tool-output`, and the settlement carries item 16's internal `ToolOutputBound {observed, limit}`, which J1 projects (item 22, :722). `observed` is the total the refused read would have reached; nothing past the bound is kept.
- **LD-D3A2-4. D3a-1's member-spawning controls.** Four D3a-1 fixtures spawn group members on purpose, to drive a join or a wait: `normal-exit-first`, `early-exit-held`, `early-exit-brief-hold` (a member holding fd1) and `term-survivor` (a member surviving `SIGTERM`). A provider tree is one process (item 16, :533), so the sampler would stop each first with `process-count`. Their tests run with the process count off, through a test seam; D3-T14 is its own control, and the tool controls use the tool's limit.
- **LD-D3A2-5. The base.** D3a-2 was first built while D3a-1 r3 was under review, on a local, never-integrated WIP baseline commit holding D3a-1 r3's twelve paths byte for byte. That lane (on main `3742822` with the baseline `183dec5`, its base suites in `opensip-d3a1`) passed every check, with all fourteen mutations caught; it is history (`/tmp/opensip-implementation/d3a2-r1-checks-wip-base`). Once D3a-1 r3 integrated as `72e0787`, which holds exactly those bytes, the baseline commit was dropped and the worktree moved onto main with D3a-2's three files unchanged. The lane of record ran there, base suites on main's checkout, and the package's parent pins are main's.
- **LD-D3A2-7. Zero fit for a tool.** Item 16's ceiling is per child tree (:528), a tool's included. A memory budget below one ceiling therefore cannot hold a tool's tree either, and `prepare_tool` refuses it with the same `MemoryBudgetBelowCeiling` before anything is prepared (:534's rule, "before any provider starts", is met a fortiori: a tool runs before PlanId, so before any provider).
- **LD-D3A2-6. Item 16's limits are test-shortenable.** As `Waits` (LD-D3A-7), `Limits` has one release value (`Limits::RELEASE`), the only one production constructs. A test lowers the ceiling to 48 MiB, the sampling interval to 20 ms, a scratch limit to 100 bytes, or the tool output bound to 1 MiB, so that each control runs in seconds. The release values are each asserted against their rows, and the exact accounting at the release bounds is tested directly (`ToolOutput`, `ToolMaterialization`).

## The tests

- **The constants:** each of item 16's values and the tool's wall clock against its row; `Waits::TOOL` differs from `Waits::RELEASE` only in the wall clock.
- **D3-T13:** `allocate` past a lowered ceiling is `memory-ceiling`, one breach, the group killed; `assert-small` (an asserted 1 byte while 96 MiB is observed) is still `memory-ceiling`; `assert-large` (an asserted 9 GiB) is `memory-ceiling` at the release ceiling; `normal`, sampled every 20 ms under the release ceiling, is `clean` with no breach.
- **D3-T14:** `fork` is `process-count`.
- **D3-T15:** stderr at 262,144 bytes is not truncated and at 262,145 is, both `clean`; the tool output exactly at its bound is `clean` with every byte, one byte past it is `byte-bound(tool-output)` with the refusal; `ToolOutput` at the release bound.
- **D3-T16:** a TS2 stream whose admitted payload bytes, counted from the participant's accounting, total exactly 1 GiB is `clean`; one byte more is `byte-bound(response)`, not admissible; the same accounting under Rust3 is never D3's bound.
- **Zero fit:** one byte below the ceiling is refused before anything is prepared, for a provider and a tool; at the ceiling it prepares, with the ceiling unchanged.
- **The scratch at settlement:** 100 one-byte files at a 100-byte limit are `clean` and admissible; at 99 they are `scratch-bound`, not admissible, and still removed; an exhausted measuring ledger is `scratch-bound`; TS2's limit is its own.
- **Tool materialization (LD-D3A-16):** charges reaching exactly 32 GiB + 1 GiB admit; one byte more refuses `ToolScratchBound {observed: limit + 1, limit}` with the total unchanged (no write made); an overflowing charge refuses with the total unchanged; a charge past the provider's 2 GiB is admitted (the wrong-limit control).
- **The tool class:** `tool-ok` skips the handshake (no control frame either way), settles `clean`, exit 0, its 12,000 bytes handed out once and exactly, its stderr counted (16 bytes), its scratch removed, never admissible; `tool-stdin` reads EOF at once; `tool-fail` settles with exit 101 and no output; 16 processes are within a tool's limit and 17 are `process-count`; the tool's wall clock is `deadline` from T-2 (no cancel, `SIGTERM` sent); a member holding fd1 past the drain is `unexpected-exit`; `prepare_tool` uses `Waits::TOOL` and has no protocol waits; each class refuses the other's descriptor set; `Drop` of a running tool kills, reaps and removes, `GroupKilledPlatformLimited`, `signaled(9)`.
