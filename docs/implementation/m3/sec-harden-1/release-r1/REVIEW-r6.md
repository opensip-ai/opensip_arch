1. **Required funding: candidate discovery is added work without a charge or coverage proof.** `trust/live_observation.rs:714-743` calls `start_component_candidates` once to count candidates and again to find a match. Each filter examines the retained list, including noncandidate entries. The charge at `:770-776` is only `c*n` edges, where c is the candidate count and n the number of start digests. It does not cover either discovery pass; the first pass also happens before that charge. ITEM2-r2:42 expressly acknowledges the walk is not separately charged and offers only that the list is already held.

   Holding the list avoids capture/allocation; it does not establish payment for these additional classification/comparison passes. For a newer list containing m unrelated namespace entries, n>0 and c=0, the added filter work is nonzero while the added ledger cost is zero. The second pass can visit the entire list as well. The revised helper also places the newer-version condition inside the filter, rather than returning before iteration; its source does not establish a same-version no-walk guarantee. No compiler optimization is credited as a funding proof.

   The list bound makes this tractable: m<=4096, with at most two full discovery passes per predicate invocation, followed by at most c*n digest comparisons. But a bound alone is not the selected charged-or-covered proof. Charge the discovery work before it runs, or identify an existing charge with a derived bound explicitly covering these extra passes and a control. Include a newer nonempty list with c=0, and an over-limit/ordering witness for the added work if newly charged. If retaining the existing zero-cost cases, prove coverage rather than asserting zero work. The analogous uncharged count/filter walks in `trust/trust_bootstrap.rs:553-572`, included in ITEM2-r2's table, need the same explicit coverage distinction; r5 did not accept a blanket traversal exemption.

   The new real-predicate tests correctly establish which subjects can match and the ledger's digest-comparison delta. They do not establish that candidate discovery is covered. This keeps ITEM-2-FUNDING open, and therefore the implementation's adopted accounting obligation open. It does not require changing constants or choosing a cheaper scan merely to avoid a lawful budget refusal.

2. **Required C-SR-5 repair: the constructed clock event omits an S4-prescribed write, and the new checker cannot detect it.** In the successor branch, `trust/accepted_store_fixture.rs:857-865` uses the predecessor's exact clock anchor as the new evaluation observation. Thus boot id, monotonic value and wall value equal that anchor: expected wall equals observed wall and continuity deviation is zero. S4 requires rewriting the anchor within tolerance (architecture `docs/v2/contracts/product-v1/security-and-lifecycle.md:353-368`). The current kernel makes this explicit: `crates/security/src/trust_time.rs:336-347,375-395` selects an anchor write for that case. Yet the new clock event records only `writes: ["evalHighWater"]` (`accepted_store_fixture.rs:944-951`), with kept evidence (`:961-967`). The anchor's resulting value can remain byte-identical; that does not make the selected anchor-write effect disappear from the event describing the evaluation.

   Copying the floor publication's shape is insufficient. That producer derives `writes` from the actual S4 result and includes anchor when `time.anchor_write` is set (`trust/floor_publication.rs:809-839`), then applies that result (`:847-864`). The fixture instead hard-codes the write set. It never derives or checks it against its recorded evaluation.

   `assert_lawful_successor` (`trust/root_payload.rs:1068-1126`) establishes useful structural joins and counter monotonicity, but neither called binder evaluates this S4 effect. The successor binder explicitly describes its result as structural, not authenticated event effects (`trust/successor_record_bindings.rs:1-3`); its event replay treats clock-write as a null role change (`trust/publication_events.rs:202-214`). The current trace does likewise (`trust/current_event_trace.rs:184-195`). The later read authenticates the current view, not the complete original evaluation/write semantics of this ordinary-import transaction. Consequently both binders plus a successful tick can accept the missing-write witness.

   Derive or independently check each synthetic publication's S4 result, event write set and resulting clock projection, including kept/new time evidence. Preserve the scratch-only scope: no production publisher is required. Add a negative that omits a prescribed clock write and is rejected by the fixture's semantic validation, rather than relying on binders that do not check it. Then demonstrate the same dropped/unrelated/revoked sequence on both begin and durable paths. ITEM2-r2:58's definition of “lawful” as merely accepted by these binders and the read is honest about its limits, but insufficient for the adopted C-SR-5 premise. This is a control/evidence defect; it is not a new production S4 defect in this delta.
