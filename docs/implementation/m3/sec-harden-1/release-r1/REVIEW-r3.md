**S2: adoptable mechanism; amend its consequence statement.** Keeping the existing list-order loop is a coherent minimal selection. `current_trust_admission.rs:825-835` preserves entry order and :945-961 returns the first match. Adding a new match can therefore replace an old returned subject: for example a component release entry followed by a matching namespace entry previously returned namespace; it now returns release:d. Reversing those two entries preserves the namespace result. The public row family is unchanged but its subject changes. This is not a promise that all previously refused stores keep the same row/subject. **S3: adoptable carried-body mechanism, with explicit qualifications.** Raw SHA-256 of the carried authenticated body is sound; it is not the envelope digest, metadata preimage digest, or canonical re-encoding. On a successfully joined read it equals the catalog manifestDigest. The mismatch disposition in finding 3 prevents circular reliance on a join that acceptance does not run. Two different rows are lawful: an old stored Trusted record reaches S2 and yields release:d; a newly recorded Revoked role is rejected by item 1's standing join first. Both use already-owned rows. There is no migration, and no new diagnostic collapse is selected. `conditionEvidence.revokedBy` naming the Revoke **event** is correct for the actual record producer (`trust_bootstrap.rs:911-938`); do not change it into a direct document reference.

**S4: adoptable start-view mechanism, with the nonretaining obligation explicit.** R2's dropped-component argument remains valid. Whole-view reread refusal and the immutable-start predicate have distinct coverage. The latter must not depend on P-0 retention, nor replace start digests with newer catalog contents. Existing newer-list, floor, and fail-stop rules stay in force.
