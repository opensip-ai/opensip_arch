1. **Required: the observer scans subjects excluded from its charge.** `trust/live_observation.rs:714-730` charges only release subjects with byte length 64. The actual new arm at `trust/root_payload.rs:1783-1787` performs `component_releases.iter().any(...)` for every release subject not matching the core set; it has no length guard. A newer admitted list containing a short unrelated release subject, with a nonempty start inventory, therefore causes n added comparisons for zero added edges. The revocation schema admits such subjects: architecture `docs/coop/completion/security-schemas.v8/revocation.schema.json:36-39` allows lengths 1 through 256, with no digest-only restriction. An unrelated `closure2:` release also reaches the added scan if it misses the core set. These entries cannot change the match result, but their work is real.

   Align the actual predicate with the charged candidate set, or charge the full actual scan. Preserve core release matching and exact byte equality. Add a control through the actual predicate for a newer list with only noncandidate releases and nonempty start subjects; a test of the cost estimator alone is insufficient. `trust/current_trust_admission_tests.rs:1695` checks the estimator's zero cases, while the actual predicate test at `:1751-1791` uses only two 64-byte unrelated subjects. Those controls and the F4 mutant do not detect this discrepancy. ITEM2-r1:33's zero-new-comparisons claim is false for the current observer. This blocks both item 2 and funding.

**Answers on implementation and precedence.**

S2 preserves the existing single list-order pass (`trust/current_trust_admission.rs:995-1019`). It extends only the release arm: the core equality remains first and the component scan is its alternative. The first old or new matching entry returns the same continuation row and its exact subject. There is no separate component-first pass. The stored-standing join and authentication still precede it (`:1153-1158`), as do heads, closure limits and evidence-floor checks (`:1162-1169`). Budget refusal before a comparison is an explicit selected boundary, not permission to reorder trust matches. I found no additional trust-semantic precedence change in this portion.

S3 uses the carried manifest's raw body SHA-256 rendered as lowercase hex (`trust/trust_bootstrap.rs:548-575`); it does not hash the envelope, preimage or canonicalized reserialization, and does not invent a catalog join at acceptance. The existing role sequence still applies Present, applicable Clock, then Revoke. `revokes` returns immediately when an existing applicable subject already revokes the role (`:527-542`), preventing a second added Revoke. Matching any carried component body revokes the role. Existing authentication remains before acceptance events and writes.

The controls at `trust/trust_bootstrap_tests.rs:1721-1880` explicitly distinguish uppercase/unrelated subjects, stale and expired core precedence, one Revoke for overlapping subjects, earlier revoked index, H/D mismatch in both directions, typed component absence, and below-quorum/no-write refusal. An old stored Trusted record is not migrated: it reaches S2 if earlier checks pass. Start retention runs at `trust/current_trust_admission.rs:1181-1193`, after item 4 and the component-authority guard, before policy/time and before consuming the authenticated input. The accessor's expectations are justified by the construction chain, independently of whether every component has a quorum proof. `trust/ordinary_targets.rs:755-770` walks inventory components. `crates/security/src/trust_ordinary_metadata.rs:331-389` parses and validates the catalog before selecting its release row, validates the component inventory, joins body/envelope/preimage identities and only then constructs Component with that row. Catalog validation shapes manifestDigest as a lowercase 64-hex value. The accessor cannot obtain an unshaped row through the reviewed private construction path. The quorum-completeness guard addresses a different property and is not used as a substitute for row validation.

Reread views deliberately contain an empty component_releases vector (`current_trust_admission.rs:1183-1185`). A component absent at start but present and revoked in current is therefore refused by whole-view reread, as required; this is distinct from S4's dropped-start-component case.

The length prefilter is semantically valid where applied. Rust str::len measures bytes, not characters: byte equality with a lowercase 64-byte ASCII digest is impossible at any other length. Length 64 is necessary, not sufficient; uppercase and arbitrary other 64-byte strings remain nonmatches under exact equality. Keeping them in the charged candidate set is conservative. Core `closure2:` handling remains separate. Finding 1 is that the observer's actual loop fails to apply its own charged filter, not that the filter changes which component can match.

**Direct ruling on charge_owned and the budget boundaries.** Keeping the old local record counters separate is a fair reading, not by itself a way around the pin. Architecture `docs/implementation/m2/trust-admission-x4t/PROPOSAL-r13.md:280-288,308` expressly distinguishes stored-byte closure limits and the linear `(records read, their total size)` pin. New owned start identities are not new stored records. `Budget::counters` is the retained record/directory/current accounting (`trust/retained_metadata_index.rs:221-226`), and closure_total consumes its bytes before the new retention (`current_trust_admission.rs:1163`). It would be misleading to silently redefine that measurement as aggregate allocation accounting.

The binding aggregate budget still must include added work. Here `charge_owned` invokes the real shared scope or sink (`retained_metadata_index.rs:167-187,228-234`) before allocations, with failure latching through the Budget guard. Production native sessions use `Budget::charged` (`trust/native_read_session.rs:85`); borrowed read/observer paths use the existing ledger (`trust/floor_publication.rs:922,962`, `trust/live_observation.rs:582`). Source census found local Budget::new/view_budget callers in tests/fixture code, not an active production route. The constructor/helper themselves are not universally cfg(test), so the defensible statement is about current callers, not a type-enforced prohibition on future use.

I accept local-only tests preserving the record-accounting pin while charging no new owned work there, provided their results are not offered as aggregate budget coverage. NATIVE_MEASURED `(33,291,40885)` remains that local native measurement (`current_trust_admission_tests.rs:831-847,1417,1471`), not the revised operation's complete cost. Real-ledger C-SR-6 controls, rather than preserving a passing constant, are the evidence for the new retention charge. This ruling does not close CP-X4T-CEILING-1 or the observer defects.

For n>0, retention precharges one vector allocation with n*size_of::<String>() slots and one owned 64-byte digest per component (`current_trust_admission.rs:963-981`). Multiplication is checked; n=0 returns without allocation. With the supplied target's String size 24 and existing RECORD allowance 128 (`crates/security/src/cost.rs:8-15`), cost is n+1 objects and `128 + 216*n` bytes: n=1 is 2 objects/344 bytes. The vector charge precedes with_capacity and each digest charge precedes to_owned. There is no new digest set allocation in ClosureSubjects. The additional match-result allocations in finding 2 remain outstanding.

Read comparison charging is n edges before the actual candidate scan (`current_trust_admission.rs:951-958`), conservatively allowing early match. Acceptance charges a body hash/hex plus candidate comparisons before hashing (`trust_bootstrap.rs:556-572`): one object, body length+64+128 bytes and c edges for each reached manifest. No candidate means no added hash or digest allocation. This does not literally mean no added work of any kind: the candidate-count/filter traversal still occurs. The table should keep its claim to the named comparison/hash/allocation costs, and any broader claim of complete traversal coverage must identify its existing bound/charge.

The three stated boundary classes are acceptable: (1) a fenced read can newly exhaust objects/bytes on retention, before policy/time; (2) candidate comparisons can exhaust edges on a read or observation and fail closed; (3) acceptance can exhaust budget before publication. Charging comparisons in edges is consistent with the existing comparison-cost form. The successor expressly permits changed budget outcomes and changes no constants. No cheaper algorithm is required merely because edges are tight. A claim about the exact reachable threshold needs total existing work, the 4096-entry bound and number of components, not the invalid example in finding 4. CP-DURABLE object/byte margins and per-attempt observer residual edges were not measured here or established by ITEM2-r1. Two observation attempts share the existing ledger; that does not cover uncharged work in either attempt.
