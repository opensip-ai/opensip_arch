# security-completion §4.5: the `release` revocation subject for a component release

**Standing.** Contract successor SEC-HARDEN-RELEASE. It adds no law. COMPONENT-RELEASE-SUBJECT r1 §3 and SUCCESSOR-SECHARDEN-RELEASE r2, copied here byte for byte, control; if this text differs from them, they win. The parent is `security-completion.v2.md` §4.5's revocation list entry, inherited by v8 §4. Neither parent's bytes change.

**The spelling and consumer identity.** For an authenticated, catalog-joined inventory, P-1 and immutable operation-start subjects, a `release` entry names the component release when its `subject` is byte-equal to the catalog row's `manifestDigest`: 64 lowercase hexadecimal characters. The joined inventory verifies that it is SHA-256 of the manifest's exact raw stored body. X4B acceptance instead matches the lowercase hexadecimal SHA-256 of the authenticated carried manifest body; acceptance does not perform the catalog-to-body join. If the catalog names D but the carried body hashes to H != D, a list naming H records the carried role's Revoke, whereas an entry naming only D does not revoke that different body. Neither mismatched inventory becomes usable: the unchanged join refuses if reached, and noncontinuable standing can refuse earlier. There is no prefix or case folding, and neither consumer substitutes a canonicalized-body, envelope or metadata-preimage digest. The core's `closure2:` spelling and handling, the schema and the other three subject kinds are unchanged; the core and component syntaxes cannot coincide.

**The four consumers.** Effects below assume their preceding checks pass.

| Consumer | Applies to | Effect |
|---|---|---|
| **X4T admission** | Every component of the read's current inventory, in every read mode | The whole view refuses on `Continuation("release:<manifestDigest>")`, within item 4's existing check. The first matching entry across existing subjects and new component matches in the same admitted-list loop wins |
| **X4 observer** | The `manifestDigest` of every component in the fenced read's inventory, retained as immutable start subjects even when a later catalog drops the component | After a successful whole-view reread, a genuinely newer list naming a start subject gives the existing revoked-during-operation result, subject `trust-revoked` |
| **X4B acceptance** | Authenticated carried component manifest bodies in an otherwise admissible payload, using their exact body digest as qualified above | A matching body causes TR-COMPONENT's `Present`, then `Clock` where applicable, then `Revoke`, ending `ST-REVOKED`. Acceptance records the transaction; this release match does not itself refuse the payload |
| **P-1** | A component whose release row's `manifestDigest` is a `release` subject of the same read's admitted list | The whole view refuses on the same row. It stays as defence in depth behind X4T admission |

**Precedence and retained cases.** X4T preserves authentication, stored-standing and all checks preceding the list loop; a successful release match preempts the later quorum-completeness guard and policy/time/floor work. The observer still requires successful whole-view reread: current-inventory revocation and earlier reread failures retain their existing classification and order. Same-version suppression applies only to the additional start-subject predicate, not to current-view admission. Acceptance still refuses below-quorum manifests before `Present` without writes, leaves a payload with no components `Unbootstrapped`, and does not duplicate an already applicable Revoke event. Confirming admission can refuse despite the recorded acceptance transaction; its prior core/index/component standing and other preceding checks retain their order.

At admission/use a component is refused with the whole view, never filtered out. Acceptance's matching-body case records the revoked state as described above. Publication of such lists is not established here: no publisher or release tool is added, and no stored record is migrated.
