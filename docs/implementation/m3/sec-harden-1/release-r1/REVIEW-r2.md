## Item 1: completeness, equivalence, ordering, and controls

**All `remaining()[1]` cases.** The stored standing check is before authentication (`current_trust_admission.rs:1096-1101`); `trust/role_machine.rs:56-66` requires TR-COMPONENT Trusted. Recovery, revoked, quorum-lost, unbootstrapped, expired, and stale component states therefore do not reach the new check. The authentication scope explicitly supplies `old_hits: [false; 6]` and no recovery roots (:728-747). The planner initializes remaining from active/non-Revoked/non-Recovery roles, removes old-subject hits, then removes below-threshold roles (`ordinary_targets.rs:63-118`, :248-302). In this read, the stored-state and old-subject alternatives are already excluded; availability of the active TR-COMPONENT delegation determines the bit. An inactive/absent delegation cannot supply a valid component authority either; it offers no route around the final count guard.

If the bit is true, `prepare_scoped` visits every inventory component, verifies its own retained body/envelope under the signing root, filters the shared revocation union, requires `QuorumState::Met`, and pushes exactly one proof for that path (`ordinary_targets.rs:347-411`). Any failure aborts, rather than returning a partial vector. If false, it returns zero authorities. The new private accessor (:750-758) compares those authorities with the same inventory's length. Consequently n > 0 and false always refuse; true can reach the guard only with all n proofs; n = 0 compares 0 == 0. There is no separate caller-controlled count or accepted flag.

All production entries converge: supplied-store admission calls `admit_current`, which calls `admit_bound` (:1250-1290); native admission calls its thin `admit_bound_native` wrapper (:1298-1328); fenced first/read/report publication calls `admit_current` (`floor_publication.rs:948-972`). The guard is outside the mode/retain/report branches. Bootstrap's confirming read uses this same admission path. Test-only construction of retained evidence is not a production bypass.

**Threshold equivalence.** Let K be the signing root's authorized component keys, R the shared list's revoked keys, and S a manifest's distinct valid authorized signers. A filtered threshold proof requires `|S \ R| >= t`, while `S \ R` is a subset of `K \ R`. If availability is below t, no such proof exists. Refusing the skipped component proof is therefore equivalent in admission outcome to demanding that proof; it does not assert identical intermediate work, cause strings, or precedence. It is the current signing root M, not root N's former delegation, that supplies K. A role at quorum but a particular manifest below quorum still fails earlier in the unchanged verifier. Unknown namespace, malformed envelope, digest/path join, and other inventory failures retain their existing checks; the integer comparison does not substitute for those owners.

**Placement and effects.** After signature preparation, opening heads, closure-size accounting, and evidence-floor checks 1/2 (:1101-1110), closure subject extraction and item-4 revocation admission run (:1112-1113). A valid listed signer in the skipped-proof case thus retains `Continuation("keyId:…")`; a component already rejected by the non-skipped quorum verifier continues to fail there. These are different precedence cases, correctly distinguished by the matrix.

The new refusal occurs before project policy and time, before a pending proposal is formed, and before any `Admission::View` or `Admission::Clocked` is returned. `fenced_first_read` propagates this error at `floor_publication.rs:971`; its own retained-floor check 3 at :973-975 and floor publication at :977-998 are not reached. Earlier evidence-floor **checks** do run; no floor **write** has run. Native completion may still report an existing custody/I/O failure; this change does not relax that precedence. A report read gets the same quorum refusal and no proposal publication. A reread gets the same quorum refusal and existing `Unauthenticated` classification. See finding 1 for refusals occurring later in the base.

Real bootstrap verifies all carried component manifests at threshold before building acceptance (`trust_bootstrap.rs:480-493`); healthy confirming reads therefore retain all authorities. The new check does not edit bootstrap events or acceptance bytes. As always, acceptance may already have been durably published before its confirming read; “nothing written” for this new admission path is not a promise to undo a prior acceptance. X4B r6:135-136 explicitly preserves recorded but unusable acceptance. For the already-retained witness used by begin/durable, the candidate's early refusal prevents the later lease and floor publication.

**Acceptance: RECORD-REVOKE.** When the otherwise admissible, threshold-authenticated bootstrap carries one or more component manifests and its verified list names any of their catalog `manifestDigest` values, dispatch Present, applicable Clock, then Revoke for TR-COMPONENT, ending ST-REVOKED. Do not filter a component away, write Revoked directly as Present's result, or turn a revoked-but-authenticated document into a new all-or-nothing authentication failure. X4B r6:111-140 explicitly distinguishes those phases, names the component manifests as the role's documents, records all accepted events, and requires honest durable acceptance followed by possible continuation refusal. The `revokes` comment and implementation (`trust_bootstrap.rs:512-533`) currently identify only the core release; that omission is what the proposed extension changes.

This selection preserves authentication failures: a manifest not at quorum after revoked-key filtering still fails before Present, and no acceptance is built. It also preserves n = 0 as Unbootstrapped. With healthy core/index and a component release hit, confirming admission sees ComponentContinuation("component:revoked") from stored standing, rather than getting as far as the release-subject admission check. If other earlier failures exist, their existing precedence still applies. REFUSE would require a different explicit exception to X4B's established sequence. **Observer: retain the start view's component manifest digests in its immutable release subjects.** Keep the existing core closure subject, signing keys, namespaces, catalog snapshot, counters, floor checks, and required-grant behavior. **The dropped-component case is a real coverage gap in the reader/predicate composition, but no implemented updater execution is established here.** Let start view S contain component A, with digest d, and list version v; the operation retains A. Let an otherwise admissible later view T omit A, keep other continuable components B, have nondecreasing floors/root/catalog counters and list version v+1, and revoke only `release:d`. T's signatures and remaining inventory can be entirely valid. A fixed current-inventory read sees no d to reject, and the current core-only predicate sees no matching release; it continues with unrelated drift. Adding d to S's immutable release subjects makes the predicate revoke. Core, keyId, namespace, and catalogSnapshot matches do not accidentally supply the missing release match in this example, since the new list has only `release:d`.

There is no read-side requirement that a later catalog contain every component from an operation's start catalog: the source checks current closure joins and monotone floors, not cross-view membership inclusion. Ordinary import's old-subject rule must nevertheless be respected when claiming a lawful publishing sequence: a simultaneous drop/revocation that hits a role's old subjects may already record Revoked and make the reread fail. The stronger example is **drop A in an earlier lawful update without revoking it, then later publish the revocation of d while the long-running operation still holds S**. The intervening store's subjects need not still include A, whereas S's must. The two current/start view checks cannot replace that lifetime distinction. This is a source-level necessary observer obligation, not a demonstration that today's bootstrap producer performs either update, or an executed fixture of a future ordinary publisher.

When A remains in T, the fixed reread already refuses `release:d`, and `classify` produces a revoking observation. The observer predicate is redundant for that subcase only. Require an item-2 control with A absent from a successfully admitted current view, a genuinely newer list, and an unchanged start operation holding A; demonstrate that omitting start digests would continue and the proposed predicate revokes. Also retain unrelated-release, distinct envelope/preimage digest, case-sensitive spelling, unchanged core closure, and shared-all-platform digest controls.
