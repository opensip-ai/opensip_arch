### Required finding 1 — the erratum's exact root N is inadmissible

`ASSESSMENT-r1-ERRATUM-1.md:16` declares TR-COMPONENT keys `{A, B}`, threshold 2. Security §3.1, lines 161-163, requires active delegated roles to have `|keys| >= threshold + 1`. The actual root admission enforces it: `trust/retained_root_semantics.rs:178-186` emits `ROOT.ROLE_THRESHOLD_POLICY:TR-COMPONENT` for this root, and `trust/admitted_roots.rs:148-153` rejects any such semantic failure. ### Bootstrap/read correspondence and quorum edge cases

1. **Same component population.** Acceptance iterates every payload `members.manifests` row (`trust_bootstrap.rs:479-493`) and retains every manifest/envelope row in its closure (`:698-729`). The read requires exact equality between the signed manifest's declared paths and the retained closure's member set, rejecting duplicates/missing/extraneous paths (`trust_ordinary_inventory.rs:172-204`), then selects every manifest into its pair map (`:244-255`). This is not a catalog-only census that can miss an extra admitted component.
2. **Pairing difference cannot substitute a weaker envelope on accepted bytes.** Bootstrap indexes envelopes by stored body digest and rejects a second envelope for that digest (`trust_bootstrap.rs:220-240`). It then verifies the selected carrier for the required kind. The read checks route, domain, stored digest, a unique candidate and preimage (`trust/retained_metadata_index.rs:628-709`). Given bootstrap's stronger global uniqueness, the latter can reject a mismatch but cannot select a different listed envelope for the same accepted component body. Both body and envelope bytes are digest-bound.
3. **Same root and revocation union for the producer case.** Bootstrap authenticates the chain to its final root, derives the key set from the embedded list, refilters the anchor/links/list, then verifies the catalog/components under that final root (`trust_bootstrap.rs:383-493`). The read binds `heads.root` as the final signing root and the closure's first root as its anchor (`trust/current_trust_admission.rs:689-726`). It passes an empty prior-key set; `trust_ordinary_quorums.rs:251-267` adds exactly the closure list's key entries. Acceptance binds the heads and closure to that same list; the floor write preserves both. This does not assert equivalence for arbitrary independently rewritten heads and closures.
4. **Set proof, including namespaces and duplicate ids.** Let K be the role's declared key-id set, R the revoked key-id set, and V the valid counted signers for the exact envelope under the final root and its namespace. `verify_quorum` selects role keys only for a listed namespace (`verified_envelopes.rs:63-80`); a wrong namespace yields no valid signer, not a vacuous quorum. It maps selected ids through the root key table and deduplicates valid signatures into a set (`:87-110`). Root admission rejects duplicate key ids, unknown references and cross-role reuse (`admitted_roots.rs:56-61,102-117`); retained semantics also reject duplicate public keys and mismatched ids (`retained_root_semantics.rs:130-138`). Consequently V is a subset of K. Acceptance requires `|V minus R| >= t` (`verified_envelopes.rs:435-447`, `trust_bootstrap.rs:284-287`), so `|K minus R| >= t`. Availability computes exactly the latter set (`trust_role_availability.rs:54-72`). No namespace/table/duplicate edge reverses that implication.
5. **Standing and time qualification.** The assertion that the component check runs applies to a real accepted store that reaches authentication, not to every unusable acceptance result. A stored Revoked/Unbootstrapped component already refuses the first standing join (`current_trust_admission.rs:1075-1080`; X4B:135-136). On a continuable producer state, `old_hits` is false, there is no recovery context, and component availability is not below threshold; `ordinary_targets.rs:73-118,373-399` therefore does not skip component quorum. Later expiry/staleness is applied by `clock_roles` to the stored states (`current_trust_admission.rs:1048-1060,1151-1178`). That does not turn key availability into a mutable capsule quorum-loss event.

### a.3: the requirements and corrected quorum statement

The necessary conditions stated in a.3 survive, with the current-root interpretation and the counterexample correction above:

- An admitted ROOT-signed list must leave positive but below-threshold component-key availability for this bypass. Zero available signers cannot pass the subsequent envelope check and revocation-subject check. An absent/inactive role likewise cannot produce the required valid envelope evidence.
- Even when `prepare_scoped` skips full component quorum, `closure_components` still calls `verify_envelope` on every non-root pair (`current_trust_admission.rs:862-888`). That requires at least one valid authorized signer (`verified_envelopes.rs:423-425`); a recognized signer named by the current list causes the continuation refusal (`current_trust_admission.rs:929-940`). “A signer that is not revoked” is necessary; no recognized valid signer may be revoked on an admitted view.
- Every component returned by the scoped inventory passes the four-part release lookup, namespace/publisher equality, and body/preimage/envelope digest joins (`trust_ordinary_metadata.rs:326-371`). The catalog is authenticated under TR-INDEX at filtered threshold (`trust_ordinary_quorums.rs:228-267`). No below-threshold component is exempt from these identity joins.
- The BUNDLE-authenticated payload fixes the complete member population and raw digests (`trust_ordinary_inventory.rs:139-204`; `retained_metadata_index.rs:594-604`). `Budget::capture_in` checks the actual bytes against the expected digest (`retained_metadata_index.rs:403-418`). Thus the citation at :595 needs these upstream/downstream checks, but its conclusion is correct. Stripping a signature changes the envelope bytes; an unchanged catalog and payload cannot still bind them.
- “At quorum under the current signing root cannot use this” is correct for the same exact envelope, with quorum understood before applying the current revocations. If `|V| >= t` but `|K minus R| < t`, some member of V is in R; the later signer-subject check refuses. If quorum instead means already filtered quorum, the below-threshold premise is itself impossible.
- A key removed from the role is ignored, not counted (`verified_envelopes.rs:100-103`); the signed message includes subject, role and namespace, not the root (`:411-416`). With valid N/M roots as corrected above, separate unrevoked ROOT quorums can satisfy N's self-envelope and M's continuity/possession; chain contiguity and issue ordering still must hold (`verified_root_chains.rs:103-165`). A catalog under M can pin the unchanged E, and a newly signed payload can list that catalog, E and the complete N-to-M chain without a digest cycle. The exact first/last root and DocRef joins remain obligatory (`trust_ordinary_roots.rs:178-203`; X4T:99-102). These qualifications make the repaired example consistent with the joins; no signed fixture or release-tool execution is claimed.

**First score:** REFUTED solely because the submitted erratum's literal example violates root admission. The acceptance invariant, digest pins and current-root impossibility argument stand. Correcting N's key population does not change the latent bypass conclusion or establish new production reachability.

## 3. Rewritten-store scope

**IN, narrowly and directly on X4T's explicit read requirement.** X4T:111-112 mandates reverification and expressly rejects trusting stored flags because a locally rewritten store could otherwise grant trust. An input cannot escape that requirement merely because current built writers would not create it. X4T owns the current-trust read being assessed, so its specific unconditional authentication obligation governs this behavior.

Security §1:98-108 assumes the kernel, distribution chain, loader/libc and first-party code running with user authority are trusted; it excludes local root and coherent unmarked whole-install rollback. Section 8:675-680 scopes the macOS verify-to-spawn residual race using a trusted same-UID premise. Those statements limit claims of isolation and adversarial execution. They do not state that a reader may grant threshold authority from an unsigned local acceptance flag, or repeal X4T's explicit check on presented records. No expansion of the global threat model is needed to identify this local conformance failure.

This score therefore does **not** decide that arbitrary hostile same-UID code is globally outside the TCB, that the host confines such code, that an attacker can acquire all requisite signatures, or that the current unqualified real-home path is exploitable. The adopted texts do not provide those proofs. A broader claim of security against same-UID code replacing the executing host, racing arbitrary files or coherently restoring the whole installation would require a separate threat-boundary/anchor ruling and evidence. Resolving the broad wording tension as a universal same-UID guarantee would also require that ruling. It is unnecessary for the narrow X4T score.

Severity wording should reflect this distinction: the assessment's d.3 “a ruling that a rewritten store is in scope” is not a prerequisite to treating the skip as an existing X4T defect. Operational urgency and the coordinator's publisher/consumer gates remain separate decisions; this review does not alter LD-Q-252's schedule or claim a production exploit.

Consequently the component-only release entry does not set TR-COMPONENT Revoked. With unexpired/fresh inputs and no other matching revocation, `:643-665` records Trusted. 4. `accept_bootstrap` publishes the fully built acceptance (`:1148-1157`); `bootstrapping_first_read` performs its confirming X4T admission (`:1227-1262`). The confirming read collects component signers/namespaces, but its release subject is only `inputs.core_closure` (`current_trust_admission.rs:838-905,1090-1098`), and `admit_revocation` matches release only to that one subject (`:929-934`).
