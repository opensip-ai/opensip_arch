1. **J1-R1 — The precedence table can manufacture the committed-run projection for an uncertain commit.** Location: item 8.3, :409-417; phase C :405; outcome rows 38 and 42.

   Rule 1 applies to state 3, without requiring a successful evidence COMMIT, and selects X7's F39 row with a runId before rule 2 considers `CommitUndetermined`. A signal can latch 1→3 while evidence COMMIT is in flight, and that COMMIT can then return undetermined. X3D:170 explicitly preserves that uncertainty; X7:100-101 distinguishes `Committed` with a latch from `CommitUndetermined`, which has an ExecutionId and no RunId. Product `commit_session.rs:943-983` returns the undetermined branch without creating `PublishedCommit`. Phase C, matrix row 38 and S12-U correctly require the durability row, contradicting the stated first-applicable-rule table.

   **Fix:** make uncertainty precede the committed-latched rule, or qualify rule 1 with the actual `Committed(PublishedCommit)` outcome. Match the outcome first; state 3 alone proves neither commitment nor a RunId. Make J-C14 and S12-U verify the corrected precedence.

2. **J1-R2 — Settlement is declared before the required render step is terminal, and S12-D is on the other side of the declared boundary.** Location: :260-268, :283-288, :406-424, :571.

   The step list includes required `render`, but the proposed render decision point occurs before SOP2 finalization and before rendering. It then declares every required step terminal and ignores subsequent signals as phase E. WS:224-228 and OPP:337-338 define settlement by actual required-step terminality; X7:85 includes projection, rendering and output in required delivery, and product `finalization.rs:310-318` does the same. A render failure can still occur after this proposed settlement point, although phase E says the decided class stands. SOP2:623 explicitly precedes envelope rendering, so placing a cancellation check there does not establish completed rendering.

   The control is also inconsistent: S12-D holds at `x7.delivery.required.before`, which product `finalization.rs:283-318` reaches inside delivery before calling the renderer. In the proposed order that follows the decision point and SOP2 finalization, so the signal is E under J1's own table; the control expects D and an interrupted envelope.

   **Fix:** specify when each required step actually becomes terminal and distinguish that from an output decision or emission boundary. If single-envelope delivery requires cancellation deferral during the final output section, explicitly reconcile that exception with the WS/OPP owners and gate the successor; do not claim the existing before-settle rule remains unchanged by calling unperformed rendering terminal. Place the D control at a genuinely cancellable point and add a separate control after the output decision. Preserve `bootstrap.rs:57-58`'s prohibition on a replacement envelope after output has begun.

3. **J1-R3 — A successful creation followed by failed ordinary admission loses its disclosure.** Location: item 3 :149, :162-172; item 9 :459-469.

   `enter_durable_analysis` returns `Result<DurableEntry, InstallationTermination>`; creation metadata exists only in the successful `DurableEntry`. After `Published`, fresh attempt B can fail its producers, gate, barrier or rechecks. The error path then carries only the termination, and R3 has not succeeded. Item 9 authorizes durable `retentionDisclosure` only once R3 succeeds, while :172 requires later refusals after publication to carry `firstUse: true`. The existing product routing has precisely this information-loss shape (`installation_routing.rs:107-118`); the new composition does not repair it. A normal gate-busy or barrier-failure envelope can therefore omit the completed creation and its backup status. The notice is additional disclosure, not a substitute for the promised non-interrupted envelope carrier.

   **Fix:** retain a value-only creation disclosure on both success and failure, for example an entry error carrying `{termination, creationDisclosure}`. It must come from this act's actual `Published` result, not a later existence scan or intent-minted flag, and carry no attempt-A authority. Start the presence rule at publication for eligible non-interrupted failures, rather than only at successful R3. Add Published→attempt-B producer/gate/barrier failure controls; keep LostRace/NotPristine `firstUse: false` and ENV7's empty-errors interrupted branch free of retentionDisclosure.

4. **J1-R4 — ExecutionIds are drawn but their pre-use uniqueness reservation is unspecified.** Location: item 2 :121-131; R12 :241; J-ζ :277; J3a/J3b :609-610.

   IE:77-81 requires uniqueness-checked reservation in the corresponding operational ledger before use for every RequestId and ExecutionId, in every mode. IE:83-88 separately adds durable attempt custody. J1 supplies process reservation for RequestId, but supplies only draws for the prelude, durable analysis, ephemeral analysis and render ExecutionIds, with the durable attempt row reserved later. Providers use the durable id before that row exists. Product `CommitSession::open` draws and stores it (:327-372); it does not perform an identity-registry reservation. `RequestAuthority` reserves RequestIds only (`request.rs:18-40`). Budget charging is not an identity reservation. The invocation also has multiple ExecutionId draws, so the one-request-per-process limit does not remove the within-process uniqueness obligation.

   **Fix:** name and gate the process-custody reservation owner for every ExecutionId before P0, provider frames or operational records use it. Keep that distinct from attempt_custody's later durable reservation and preserve the security-owned durable draw. Update the affected identity/session successors and units; add a collision control showing no pre-use emission, caller-selected identity or silent reuse. This needs no permanent RequestId or ExecutionId ledger at M3.

5. **J1-R5 — J3d drops the required F2 and G3 dependencies.** Location: item 14 :607-619.

   Accepted M3P's J2→J3 row (:218) requires F2 and G3 for J3. The exact draft-r5 pin repeats them at :211 and :303. J1's J3d dependency list contains neither. They are not inherited through J2b's explicitly enumerated J2 set, and J3a/J3b cover security/finalization rather than the providers. The law's durable end-to-end unit thus admits integration before the two producer prerequisites that its governing plan retains.

   **Fix:** add F2 and G3 to J3d, or to an explicit inherited predecessor. Restate the conditional critical path with these gates retained alongside J3a, J3b, X3c-3 and serialized lead-set completion. Their assumed early completion may preserve the estimate; it does not remove the dependency.

7. **J1-R7 — The future M4 CLI instruction enables audit before its M5 prerequisite.** Location: item 1 :85, :88-98; successor S1 :578.

Alternatively gate the collective replacement until the latest prerequisite; do not call that collective enablement an M4 unit.
