1. **J1-R2-01 — Closing on successful preparation disables cancellation throughout publication.** Location: item 8.1, :449-462; 8.6, :535; J-C15, :561; S10/S11; response to r1 J1-N1.

   The rule closes the window on **every return of `prepare_commit` and `publish`**. A successful `prepare_commit` returns `Ok(PreparedCommit)`, before `publish` starts. That is a continuing result, not one of the five terminal outcomes listed underneath the rule. The window was opened at attempt-row COMMIT; closing it at this successful return leaves `WINDOW_CLOSED` permanently set. The specified latch then returns `OutsideWindow` throughout publication, including both S12-B and S12-C. Phase B's 0→2 cancellation and phase C's 1→3 cancellation cannot occur as promised. Reopening cannot repair this under the proposed monotonic closed-bit rule.

   **Evidence:** Product `crates/storage/src/commit.rs:465-557` returns the prepared value on success; its separate `PreparedCommit::publish` begins at :571 and reaches the final gate and evidence COMMIT later. X3D:119-156 separates these two methods; :168-171 preserves F38/F39/F41. Subject :480-481 requires cancellation through publication, and :674-677 puts the B/C/U controls inside it. This is a new defect in the response to the r1 window observation. Storing window bits in the gate word is otherwise sound.

   **Fix:** distinguish continuing preparation success from terminal returns. Keep the window open across `Ok(PreparedCommit)` and close it on every unsuccessful/terminal preparation return and every terminal publication outcome, including the successful publication sample. Update 8.1, 8.6, S10/S11 and J-C15 consistently. Add a control that first obtains a successful prepared value and then cancels during `publish`, alongside the close-versus-latch races. The CAS loops must preserve the full word's window bits while matching/changing only the two state bits; state decoding remains masked and no state resets.

2. **J1-R2-02 — Phase O's unconditional F16 route mislabels renderer failures without a committed Run.** Location: 8.2 phase O, :483; J-C14, :560; S18, :705; matrix rows 43-44, :623-624; response to r1 J1-R2.

   The new rule says a renderer failure inside O takes X7's F16 row in place of the decided envelope. F16 is the **committed** delivery-failure row: it retains the RunId and uses `DELIVERY.RENDERER_FAILED_AFTER_COMMIT`. But the required render step also projects an analysis refusal, and the ephemeral DAG has the same required render step. For example, an ephemeral evaluation can succeed and its JSON renderer can fail before the first byte. No Run committed, so the after-commit detail is false and there is no RunId to retain. The same problem occurs when rendering a pre-commit rejection. The proposal's own row 44 already names the correct distinct route.

   **Evidence:** Subject :318-327 defines the durable and ephemeral render steps and requires rendering refusals. X7:88-91 allows authoritative RunId only from `PublishedCommit`, and X7:99 makes F16 a `Committed` row. WS:1376-1377 separately specifies renderer failure after commit and required projection/renderer failure without a committed Run. The latter is operational-failed / 4, `DELIVERY.REQUIRED_FAILED`, `delivery-required`, detail `DELIVERY.REQUIRED_PROJECTION_FAILED`, with no RunId. WS:233-240 still governs aggregation and ties between required-step failures.

   **Fix:** make the O rule and S18 conditional on the actual committed evidence. Use F16's after-commit route when a `PublishedCommit` exists; otherwise use WS:1377/the existing row 44, subject to the required-step aggregate rules. Preserve the ExecutionId/recovery disclosure when an uncertain analysis outcome must still be reported; never manufacture a committed Run. Before any output byte, construct the appropriate failure envelope through the reviewed failure projector. Test both a committed renderer failure and an ephemeral or pre-commit renderer failure. Preserve exit 4 with no replacement envelope on required-output failure.

3. **J1-R2-03 — The new output exception is not gated or reconciled for the ephemeral entry.** Location: 5.1-5.3, :323, :340-352; item 6, :387-388; S18, :705; J2c/J3d, :717-720; response to r1 J1-R2.

   The shared DAG places its required render/output work in phase O, and 5.3 defers signals there while step 1 is not yet terminal. That applies to the ephemeral invocation as well as the durable one. Yet item 6 still says ephemeral cancellation has phase A only, and S18 gates only J3d's output code. J2c is explicitly the ephemeral entry **end to end**, with no S18 dependency or restriction leaving its output unwired. An ephemeral signal after the output decision point therefore has two incompatible dispositions: 5.3 preserves the decided envelope, while the phase-A-only rule and the currently governing WS before-settle rule require `interrupted`. Its output can also be wired without acceptance of the exception that would authorize preserving the decided envelope.

   **Evidence:** WS:224-228 applies to required-step terminality without a durability restriction; WS:242-248 gives ephemeral authority rules, not a cancellation-deferral exemption. Subject :323 gives the ephemeral invocation the same required render step, :351 identifies O as an exception requiring S18, and :717 lists only J2b, S3 and S7b for J2c. The explicit unwired-output allowance at :515 applies to J3d, and :720 repeats that durable gate only.

   **Fix:** specify the ephemeral cancellation phases explicitly: cooperative analysis/pre-output cancellation without a commit gate, O for final output, and E after actual required-step terminality. Make S18 acceptance a gate on every wired output path using its exception, including J2c, or explicitly leave J2c's output unwired until the shared reviewed output implementation is available. Authoring pure state models can proceed earlier. Add ephemeral controls before the decision point, inside O, and after settlement; retain no RunId or durable effect.
