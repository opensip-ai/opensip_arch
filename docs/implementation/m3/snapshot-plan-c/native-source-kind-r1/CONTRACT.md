# NSK-1: original source family and acquisition select native sourceKind

Prospective narrow design unit. Existing R3-MR1/C-ENV1/NKC-1/CSJ-1/MWS-1 remain closed. This selects sourceKind classification and its allowed acquisition combinations only; it does not establish actual acquisition/source admission, authenticated producer/profile, manifest/activation/custody/namespace/failure/library/product or full R3.

For DependencyPackageSourceV1 and its joined NKC-1 dependency owner witness, use the exact original admitted lock tuple and actual owned acquisition witness. For a nonpath source, use the pinned Cargo1.95 SourceId::from_url interpretation already selected by CSJ-1 on the original raw lock source, and require the separate actual CSJ-1 metadata/source comparison and full manifest/tree correspondence. SourceKind::Registry and SourceKind::SparseRegistry are the native original registry family; SourceKind::Git is the original Git family. This is the exact pinned kind interpretation, not starts_with tests, a guessed generic URL parser, the replacement DirectorySource kind, a vendor directory name or metadata text substituted into the raw tuple. Preserve raw lock sourceId/pkg1/own2/file-manifest bytes. Sparse remains the existing native registry family: no enum member or semantic normalization is added.

For the path case, require the actual admitted path witness, absent lock source represented as existing empty sourceId and actual null metadata source under CSJ-1, plus the actual sealed snapshot/manifest correspondence. Empty sourceId or null metadata source alone is not a path witness. Dependency path owners and their complete DS-4 source manifests are not dropped. MWS-1 still selects whether an activated path package is snapshot or dependency owner. A workspace snapshot-member keeps its already selected NKC-1 path sourceKind and actual sealed snapshot/path witness; this table does not create a DependencyPackageSourceV1 or AcquisitionV1 record for a workspace member merely to restate that existing rule.

| Original admitted source family | Actual acquisition mode | Required native sourceKind |
|---|---|---|
| registry (Cargo Registry or SparseRegistry) | imported-descriptor | registry |
| registry (Cargo Registry or SparseRegistry) | in-snapshot-vendored | vendored |
| Git | imported-descriptor | git |
| Git | in-snapshot-vendored | vendored |
| path | in-snapshot-path | path |

Nonpath sources with in-snapshot-path refuse. A path source with imported-descriptor or in-snapshot-vendored refuses. Any original source protocol outside the selected parsing/family cases, unknown acquisition mode, missing/wrong/ambiguous owned acquisition/source witness or conflicting advertised sourceKind refuses. No first-row choice, coercion, prefix fallback, relabelling registry/Git as path or default vendored/imported source is selected. This table does not admit an arbitrary file URL, fetch, ambient cache or a local registry merely because a Cargo API calls it a registry.

AcquisitionV1 descriptorId/vendorPath shapes/bounds and complete existing correspondence/custody rules remain unchanged. Imported and in-snapshot modes must still join their actual admitted import/snapshot trees; a caller's mode string or path is no proof. Existing checksumVerification/lockChecksum/provenanceAssurance are not derived from the sourceKind label. In particular vendored does not erase the original registry/Git family: registry retains DS-1/DS-2 exact tarball versus self-consistent declared-tree rules, Git retains DS-3 exact-revision tree/not-applicable/declared, and path retains DS-4. An extracted registry tree or a directory-source checksum never becomes registry-authenticated merely because it is called registry or vendored. The synthetic zero checksums are not tarball authentication.

All acquired candidates still finish admission/rejection and all admitted candidates materialize whole before activation. The sourceKind classification is conditional on complete actual source/acquisition/manifest/producer/profile admission and never a replacement for it. Cargo metadata success, a schema-valid descriptor or the older trusted-observation reference helper does not establish these prerequisites. Its lexical prefix checks/path exclusion are historical helper scope, not complete new-M3 admission authority. Actual activation derivation, original manifest and complete retained file population, source-slot injection, compatible sealed carrier/profile, physical/worker namespaces and provenance-aware public failure/coverage routes must still be published and implemented before product use. No code/origin/remedy or fallback is invented here. Native schema/identity/witness recipes/grant rules, effectiveL/O7/D3/D13/GT/qualification remain unchanged and full R3 stays open.

## Evidence standing

Two actual installed Cargo1.95 locked/offline/frozen synthetic first-party metadata controls preserve ordinary registry and sparse registry original source strings through directory replacement, preserve locks and return the actual fixture package manifest. Source inspection of the exact pinned Cargo commit distinguishes Registry/SparseRegistry/Git/Path under from_url. Zero lock and package checksums are self-asserted fixture values, not authenticated registry archives. CARGO_HOME remains the prescribed /Users/sb/.cargo; HOME is not assigned. Fixture code is not built or run, and nativeCC2/constructed environment/profile/carrier/source/owner/custody/launch/product admission and qualification are not proved. Closed source-kind and acquisition schema fragments are copied by value, not re-registered or extended. Existing Git/path controls remain their accepted narrow scopes; no repeat review or reinterpretation as full source admission.
