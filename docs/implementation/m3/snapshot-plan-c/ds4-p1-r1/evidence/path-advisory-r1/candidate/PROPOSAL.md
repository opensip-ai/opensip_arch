# DS-4 path source population: proposed resolution

Unfrozen prospective recommendation, not selected law. No implementation or source/owner admission is asserted. All accepted units and historical bytes remain closed. This proposes a separately reviewed compatibility successor; it does not amend S10, R3-MR1, C3-R2, NIJ-1, MWS-1 or NSK-1 by implication.

## Recommended source population and custody

Keep DependencySourceSetV1's final protocol population exactly the activated admitted non-path packages. Keep acquisition counters exactly the supplied non-path candidate population and finish every candidate before activation. Path sources are not imported, inserted into the external set, counted twice, or mounted from DependencySource frames. Existing imported wrapper payload.set H must still equal the context dependencySourceSetId under NIJ-1. A retained imported set must never be rewritten to add path rows or change lockfileIdentity.path. Newly admitted descriptorId and prepared importId remain literal null.

Introduce a security-owned snapshot-path source capability for the separately published native profile. It is not a caller constructor, public identity, import, new transport frame, or reclassification of a nonworkspace package into snapshot-member. It retains the actual sealed snapshot admission, selected workspace/target/configuration and exact bundled metadata observation association, the actual admitted path manifest locator and the original lock tuple. Its lifetime is tied to those owned inputs, not a global map indexed only by a NativeContextId, pkg1 or own2 hash. Equal context ids or equal source content do not merge observations or waive custody.

Select dependency-closure-member for an activated path package not in workspace_members of that same observation, as MWS-1 requires. Workspace members retain snapshot-member and their existing complete Blob sourceInventory recipe. Empty lock source plus null metadata source is necessary but not sufficient for path admission. The package's actual Cargo.toml must be a retained snapshot file, parsed from those exact bytes by the compatible bundled profile. Lock name/version, the actual package and opaque metadata/resolve identifiers must join uniquely under the selected context. Multiple actual manifests with the same raw path tuple retain distinct own2 through their admitted manifest locators; a source slot or PackageId winner must not collapse them. No basename, path prefix, metadata null, default_members, resolve.root or directory existence establishes ownership.

## Proposed complete path file manifest

For each admitted DS-4 dependency owner, the proposed path source carrier is the complete retained sealed snapshot inventory, including shared workspace manifests, sibling packages and retained config/read-set inputs. Construct one Native DependencyFileManifestV1 array from every Blob row in that exact inventory, preserving snapshot-relative logical path and order, mapping sha256 to contentSha256 and bytes to byteLength. This conversion belongs to future path source admission, before owner admission or hashing, rather than to R3's digest function. It adds no filesystem read, excluded file, symlink target, guessed Cargo subtree, package-file include/exclude filter or missing source. Each resulting content digest/length is tied to the actual retained snapshot blob. The original snapshot Blob preimage remains unchanged.

This is a proposed deliberate conservative dependency sensitivity: unrelated retained edits change every admitted path dependency's file-manifest identity, just as they change snapshot-member owner manifests. The actual package locator still selects which Cargo manifest/package is being admitted. Equal complete carrier manifests do not make packages, owners or observations interchangeable. A narrower dependency-sensitivity scope is a future owning successor, not an optimization chosen during implementation.

R3-MR1's dependency recipe stays raw SHA256(C(the actually admitted complete Native array)); its native domain digest stays H(native.dependency-file-manifest.v1, that same array). Do not hash the domain digest string, swap in Blob rows, normalize paths or digest a package subtree. NKC-1 raw pkg1/own2 preimages, MWS-1 source class and NSK-1 sourceKind=path remain unchanged. Path provenance remains declared, never registry-authenticated, and no path package imports or fabricated .cargo-checksum.json records are introduced.

## Bounds must be selected together with the path source rule

Existing strict path ordering/uniqueness, exact integer/scalar/UTF-8/lexical rules, depth32, DependencyFileManifestV1 schema and the 4 MiB canonical bound all apply before this capability is minted. No streaming exemption, raised cap, row splitting/truncation or partial manifest is proposed. Renamed Native row fields are longer than Blob fields: a legal near-limit snapshot can have a Native projection above the same 4 MiB bound. The source profile must explicitly disclose and route this additional admission precondition. It must not treat that predictable projection-size condition as a host bug or silently fall back to another recipe.

Recommended prospective route for a well-formed admitted snapshot whose complete proposed Native projection exceeds the canonical bound: pre-Plan request-rejected, REQUEST.UNSATISFIABLE, exit2, domainDetail absent, a retained internal diagnostic naming the actual projection bytes and existing limit. Remedy is to reduce the retained analysis snapshot/input selection or use a subsequently accepted representation successor. No promise that increasing a source transport/package-count allowance repairs the canonical descriptor exists. This route is a proposal requiring an owning D9/native compatibility selection, not an existing published detail code. Do not register a guessed new enum or label the condition missing-dependency-source, corrupt import, ProviderFault, host-io or a valid semantic negative.

The complete profile must distinguish that well-formed-but-unrepresentable case from invalid retained snapshot bytes, wrong identity/custody, malformed supplied metadata and a host defect constructing an invalid projection. Their already owning admission/custody boundaries retain priority. This recommendation does not select their full public composition or claim that the proposed one row is complete failure publication.

## Required S10 and native compatibility publication

S10's current dependency-closure-member requirement names membership in the sealed DependencySourceSetV1. The proposed narrow compatibility rule is: non-path dependency owners retain that exact set/id/package membership check; an admitted DS-4 path dependency owner instead proves membership through the security-owned snapshot-path source capability, including actual snapshotId, selected current context/observation, exact path package manifest and complete retained Native file array. Its source remains dependency-closure-member. The invocation's dependencySourceSetId still binds the admitted non-path set and all original native joins; path admission does not replace or fabricate it. RepoExecutionGrantV2 owner arrays and ownerSourceDigest keep their existing fields and byte recipes, and grant admission must consume the same owned source capability used for prepared freshness. The capability cannot be constructed from an equal hash or borrowed across snapshots/contexts.

This needs an explicit S10 passage successor plus native DS-4/custody and profile selection. Existing source/owner/authorization schemas do not themselves admit a path owner today. In particular this recommendation does not authorize repository code, declare confinement, select a parser's activation algorithm, or bypass C3/C2/effectiveL/O7 parents. Actual security library and harness must share the one owned admission/digest function after all parents are lawful. Actual producer/package/path/source and refusal controls are still required.

## Rejected alternatives

Adding path rows to an imported set or changing its lockfileIdentity breaks the exact NIJ-1 wrapper/set/context join and the current non-path protocol population. This recommendation preserves both instead. Making path owners snapshot-member violates MWS-1. A second external import of snapshot path bytes violates DS-4. A guessed package directory misses workspace/shared dependency sensitivity. Reusing snapshot Blob bytes for a dependency owner's raw digest changes R3-MR1's source-selected recipe. A larger canonical allowance inferred from the million-file protocol allowance has no authority. Hidden omission, empty catalogs and classifying every null-source package as admitted path input are not solutions.

Resolve source-slot aliases/precise conflicts before Cargo's SourceMap insertion. 4. Implement actual source admission over owned sealed bytes, exact producer observation joins, one security-owned owner-manifest/digest function and the same harness function. Exercise snapshot/path/source substitutions, shared manifests, same-tuple different path owners, wrong context/snapshot/observation and the canonical limit boundary with actual retained input controls.
5. Request exact whole-unit review, assent, separate code and inventory bind only after owning prerequisites; recensus operability at integration, next inventory171 unless another binds first. Do not claim complete C3/R3 or qualification from this recommendation.

Source loader/complete source profile, origin-aware missing/malformed Cargo failure handling, effectiveL/O7, owner D3/D13/S-M decisions, held E2s/J4a and all GT/qualification remain open. No repository, lock or inventory change is authorized by advisory acceptance.
