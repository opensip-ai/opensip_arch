# NKC-1: new Rust package and prepared-owner key encodings

Prospective narrow design successor. This publishes byte encodings and retained witness shape, not complete R3, actual native admission, a producer adapter, confinement, or qualification. Bound R3-MR1 and C-ENV1 remain unchanged. Earlier own1 advice was never selected law; it is preserved as advice, not a codec to replay as own2.

## Package witness and scope

For a new-M3 Rust native context, NativePackageWitnessV1 retains exactly name, version, sourceId, packageKey. Name/version/sourceId are exact admitted Cargo.lock package values under the existing native rules, including sourceId empty for a path package. Bounds copy the native source schema by value: name/version 1..256 and sourceId 0..4096 Unicode scalars. They are not UTF-8 byte bounds; canonical descriptor byte/depth/scalar constraints remain separate. No new semantic-version/name restriction or source spelling normalization is selected.

packageKey is exactly pkg1- followed by 64 lowercase hex digits of raw SHA256(C([name,version,sourceId])). Retain and recompute the tuple before every join; no host path, opaque Cargo id, acquisition path, raw metadata digest, context identity, wrapper, H domain or line ending enters this preimage. A key is scoped to the one admitted native context containing this tuple. It is not a global package-observation identity: two workspaces can each contain a path package with equal name/version/empty source. Within one context a tuple must identify exactly one actual package; ambiguity/conflicting records cannot become deduplication or a source priority.

## Owner witness and scope

NativeOwnerWitnessV2 retains exactly source, sourceKind, package (the full witness), snapshotManifestPath and ownerKey. It applies only to new Rust native build-script/proc-macro prepared owners. source is exactly snapshot-member or dependency-closure-member under security S10; sourceKind is the existing native registry/git/path/vendored vocabulary. This unit does not choose workspace membership or activation as a source rule: that prospective recommendation remains distinct until its full witness/producer selection is accepted. Source choice comes only from the actual admitted owner mapping, never a caller label or preferred lexical enum.

A snapshot-member owner must be a path source. Any path owner, including a dependency-closure path owner, requires the exact admitted in-snapshot package Cargo.toml LogicalPath, and its package sourceId is empty. A nonpath dependency owner requires literal null for snapshotManifestPath. The path must have basename Cargo.toml, be in the actual sealed snapshot inventory and identify this package through the actual admitted materialization mapping. These are semantic joins, not a suffix-only assertion. The copied LogicalPath definition and its owning per-segment/path admission apply; do not normalize, sanitize or create an ambient locator. A missing manifest, a different package's manifest, a host path or a caller's alleged mapping never suffices. Registry/git/vendored nonpath owners cannot insert a scratch/acquisition path into this field.

ownerKey is exactly own2- followed by 64 lowercase hex digits of raw SHA256(C([source,package.packageKey,snapshotManifestPath])). Recompute the package key first and then the owner key from the full retained witness. Equal-name/version path packages at distinct logical manifests have equal scoped PackageKeys but distinct owner keys. Moving the package manifest changes its owner key. Editing source files without moving the manifest leaves the key unchanged and changes the bound owner-file-manifest digest under R3-MR1; identity of the owner does not grant old source bytes. Changing source or sourceId changes the appropriate preimage. Neither this raw digest nor PackageKey substitutes for ownerFileManifestSha256, the native H dependency-file-manifest digest, ownerSourceDigest, inputBinding or an operational grant.

Both spellings are 69 ASCII bytes and a safe single segment for the existing virtual .opensip/out/v1/<ownerKey>/ prefix. PO1/PO4 exact configuration/site/kind/path/inputBinding and inertness checks remain mandatory; matching a key/path alone cannot admit a generated row or execute code. This unit changes no .opensip/deps/v1 worker mount, acquisition namespace, adapter scratch rule or filesystem alias proof. It adds no native/source/owner collection capacity or physical namespace admission claim. Historical records use their actual historical codec and selection; absent new-M3 selection is not permission to reinterpret them.

## Admission limits and remaining owning obligations

The adjacent schema checks only closed witness structure. The reference controls use synthetic tuples/paths and verify exact bytes and selected semantic shape/recomputation, including Cargo.toml basename; they do not obtain actual producer/custody/activation/snapshot membership. A standalone witness is not an admitted owner, source or launch permission. An implementation cannot expose a caller-witness constructor as admission or use arbitrary file lists to bypass the R3-MR1 source selection.

Actual bundled Cargo observation-to-lock/source matching, workspace/activation source selection, complete acquired-candidate materialization before activation, source-aware acquisition and adapter namespaces, physical alias/collision handling, producer provenance, real failure routing and public envelope composition still require their own complete publication. No new origin, failure code, missing-witness default, drop, source dedup or winner is guessed here. These gates prevent treating this selected encoding as an owning admission mechanism. The owning host must use actual provenance, and existing structural/custody/signature/schema/identity refusal laws precede this semantic join; missing/corrupt bytes keep their specific owning laws. Security's shared owner-manifest library/harness, actual product implementation and prepared controls remain owed. C3c, complete R3, effective L, owner O7/D3/D13, ground truth and qualification stay open.
