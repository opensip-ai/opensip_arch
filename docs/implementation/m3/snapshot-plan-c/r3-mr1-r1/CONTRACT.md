# R3-MR1: owner file-manifest membership and byte recipes

PROPOSED prospective security/native selection, not accepted law. This unit selects only R3 membership and file-manifest preimages. It does not select package/owner codecs or complete R3, enable C3c, implement a library, activate effective L, authorize a native launch, qualify a product or complete M3. Independent review, exact lead assent and contract bind are required. Historical selected law and artifacts remain immutable.

For an actually admitted snapshot-member owner, its owner file dependency set is the complete retained sealed snapshot sourceInventory. Every snapshot owner sees the same inventory: nested packages, siblings, shared manifests/configuration and the already admitted TypeScript read set are included if inventoried. This is dependency sensitivity, not exclusive ownership. Unrelated retained edits deliberately make prepared output stale. The recipe adds no files or reads: excluded symlinks/special files, pruned trees and outside-snapshot bytes are not added. Rust dependency inputs remain separately bound through DependencySourceSetV1. Selecting only a guessed Cargo subtree is forbidden.

For an actually admitted dependency-closure-member owner, the file dependency set is that uniquely admitted package's complete retained DependencyFileManifestV1 before mount-prefix rewriting. Do not filter checksum metadata, append vendor reads, infer a package directory or substitute another package with equal content. An admitted path dependency uses its retained dependency package manifest. The actual security source witness decides which recipe applies. A caller key, claimed digest, equal byte set or empty map is no admission credential. Missing/conflicting package/owner mappings remain a publication gate; no default owner or source is selected here.

The exact two retained preimage schemas and recipe table are adjacent. Snapshot preimages preserve Blob rows {path,sha256,bytes}; dependency preimages preserve {path,contentSha256,byteLength}. Arrays use strict unique UTF-8 path order, with no implicit sorting during canonical admission. Canonical JSON and its lexical/numeric/depth/byte limits follow identity section3. Reject invalid or duplicate rows before hashing. The digest ownerFileManifestSha256 is raw SHA256 of the complete source-selected canonical array bytes, with no wrapper or newline. Retain those exact preimage bytes, byte length and admitted source witness. ProjectId, snapshotId, ownerKey, sourceId, acquisition path and operational identities stay outside the preimage. Equal files with different ProjectIds retain this file-set digest. Different source classes can have different digests over equal files because their named row shapes differ; source admission remains mandatory.

For dependency owners, the native fileManifestSha256 remains H(native.dependency-file-manifest.v1, the same retained array); the raw owner digest is explicitly different. Never hash a domain digest string to manufacture the raw owner digest. Snapshot owners have no corresponding dependency-domain conversion. ownerSourceDigest remains raw SHA256 of the canonical security owner-row array, strictly unique and sorted by ownerKey. These three recipes preserve distinct preimages/frames.

Use the exact admitted arrays and existing applicable population and canonical bounds. Snapshot owner bytes are a subrecord smaller than the enclosing admitted snapshot and add no descriptor restriction. Dependency manifest bounds are unchanged and do not derive a larger canonical allowance from a one-million-file counter. No row expansion, new wrapper, arbitrary higher cap, splitting, truncation, partial manifest or late filesystem read is admitted. If a manifest lacks lawful canonical admission, its source admission must refuse before this recipe can run.

One security-owned library function selects and hashes the exact retained array from an opaque admitted owner/source witness. The harness calls that same function. No public constructor accepts an arbitrary file list or caller-asserted source. This states the future implementation duty, not an implemented API or completed owning control.

Staleness compares the actual resulting owner digest under PO1 along with the existing dependency set/toolchain/cfg joins. A differing field in an explicit prepared import refuses before Plan under the existing stale-prepared-output rule. Historical artifacts retain their historical schema/recipe and are not relabelled into new-M3 admission. Replay selects already retained historical authority, never a caller compatibility flag.

Exact order/shape/bytes/content/custody failures remain with the already owning source admission, preserving missing/corrupt/signature/identity/CRC1/correspondence precedence. The recipe consumes their admitted capability; it cannot repair or reinterpret an invalid source. Missing/conflicting owner mappings, actual codec provenance and complete origin-aware failure publication remain a separate mandatory gate before complete R3/product implementation. This narrow selection invents no public failure code, provider fault, host-bug origin or generalized fallback.
