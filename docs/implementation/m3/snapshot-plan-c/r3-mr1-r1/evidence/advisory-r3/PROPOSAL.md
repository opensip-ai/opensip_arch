# R3 owner file manifest: proposed selection and implementation gates

2026-10-08. Unaccepted lead proposal. No repository mutation, contract successor, product implementation, owner assent or gate closure follows from this packet. R3 remains open. This revision responds to measured 12-byte-per-row expansion in r1; the frozen r1 remains unchanged while its review completes. Closed NIJ-1 and O1 units remain closed.

## Recommended membership

For an actually admitted snapshot-member owner, select the complete retained sealed snapshot sourceInventory as the conservative file dependency set. Each owner in that snapshot receives the same file-set digest. This asserts dependency sensitivity, not exclusive ownership of every file. It intentionally includes nested packages, workspace-shared configuration and unrelated retained files; an unrelated retained edit can invalidate prepared output. It neither expands the snapshot walk nor reads anything new. A symlink, special file, pruned tree or outside-snapshot input cannot be added to this set by a caller. Files in the already admitted TypeScript read set are included if and only if present in that snapshot sourceInventory. Rust dependency bytes remain with DependencySourceSetV1 and its separately checked inputBinding dependencySourceSetId.

For an actually admitted dependency-closure-member owner, select that one package's complete retained dependency file manifest, before virtual mount-prefix rewriting. Paths are the package manifest's admitted relative logical paths. Preserve all admitted members; a checksum metadata file is included exactly when the admitted manifest includes it. Do not independently read or reinterpret vendor metadata at this stage. An in-snapshot path package admitted as a dependency owner uses the dependency package manifest, not a heuristic snapshot subtree. Security chooses the admitted source; equal content cannot transfer an owner between sources.

Owner admission remains indispensable. A string key or equality to a claimed file digest never establishes source membership. The host must retain a unique admitted owner-to-snapshot-package or owner-to-dependency-package witness. This proposal does not invent that missing package/owner codec: its exact identity, mapping, source conflict disposition and failure routes must be published before implementation. An empty admitted map makes the requested owner unavailable; it does not silently select another owner or authorize dropping an activated package.

## Recommended byte recipe

Select source-specific retained array shapes, without a wrapper or newline. For snapshot-member, the preimage is the complete admitted sourceInventory array of closed Blob rows `{path,sha256,bytes}`, exactly as retained in the sealed snapshot. For dependency-closure-member, it is the complete retained dependency file-manifest array of closed rows `{path,contentSha256,byteLength}`. Both preserve exact logical paths, lower-case raw file SHA-256 and exact uint64 file lengths, and require strict UTF-8 path order and uniqueness. No field renaming, row filtering or inferred default happens before hashing. The single security library function accepts a source-discriminated admitted owner witness and selects the corresponding retained array; the harness calls that same function.

Use identity-and-evidence section3 canonical JSON encoding: exact UTF-8 key order, ordinary integer spelling, escaping, no normalization or whitespace. ownerFileManifestSha256 is raw SHA-256 of these exact canonical array bytes. Retain the exact preimage bytes and byte length with the admitted owner witness. No ProjectId, snapshotId, dependencySourceSetId, ownerKey, sourceId, acquisition path or operational identity enters the file-set array. Equal file inventories under changed ProjectIds therefore retain the digest. Identical files admitted under different source classes need not have identical owner digests: their named row schemas differ. Security's source discrimination and owner witness are still mandatory; the digest is not an admission credential.

For dependency owners only, H(native.dependency-file-manifest.v1, the retained array) remains the native dependency file-manifest identity, while raw SHA-256 of the same array is the owner digest. The final law explicitly publishes this conversion over verified retained canonical bytes, never over an identity string. Snapshot owner digests preserve the existing Blob array fields and have no corresponding dependency-domain conversion. ownerSourceDigest remains raw SHA-256 of the canonical security owner-row array, a third preimage.

Capacity selection: reuse the exact already admitted source array and its existing applicable bounds. A snapshot sourceInventory array is smaller than its enclosing admitted snapshot descriptor, so the owner recipe adds no snapshot descriptor-size restriction. For dependency file manifests, require the currently selected manifest's own canonical bound and population/counter admission; this recommendation grants no larger descriptor or blob bound and adds no wrapper, row expansion or new independent arbitrary count cap. If the complete source authority still lacks an independently bounded manifest preimage, publish that gap before adoption rather than assume that a one-million-file counter permits unbounded canonical bytes. Existing depth/numeric/file-byte constraints and real owning failure routes remain mandatory. No truncation, splitting, partial manifest or budget substitution is allowed.

## Staleness and compatibility

An edited admitted row, inserted/deleted path or changed retained path spelling changes the preimage and invalidates a prior prepared inputBinding. Equal files under a newly admitted owner retain the file-set digest, but the owner key, source, dependency set, toolchain and cfg joins are still checked separately. A different sourceId with identical bytes does not reuse an owner admission. Historical owner manifest bytes and records retain their historical selected recipe/schema; they are never rewritten to this prospective preimage or automatically admitted to a new Plan.

## Why this selection

Selecting only a Cargo package subtree needs new precise rules for workspace-shared files, nested packages, declared paths outside the package and build-script reads. Hashing Cargo metadata alone misses source bytes. Compiler-traced reads launch code before the M3 Plan and O7 decision. Whole admitted snapshot membership avoids guessing those rules and preserves conservative staleness. Its cost is more false stale results. The source-specific retained-array recipe adds no snapshot descriptor-capacity restriction; existing dependency manifest bounds remain unchanged. If that cost is unacceptable, a tighter dependency-membership contract is required before choosing a smaller set.

## Required publication and owning controls

The complete R3 successor must publish this membership/recipe selection, a closed retained preimage schema and exact authority/passage selectors, the single security-owned library function and harness call, owner admission/PackageKey codecs, real provenance-aware failure routes and capacity consequences. R3/C3c do not unblock from this packet alone.

Controls owed: identical snapshot file sets with different ProjectIds preserve the file-set digest; unrelated retained edits make prepared output stale; package siblings and shared configuration edits are included; excluded symlink and target bytes remain excluded; equal package bytes under conflicting sources do not confer admission; snapshot/dependency retained row selection is exact; raw and domain hash confusion refuses; missing/corrupt retained witnesses keep their more specific owners; reverse order/duplicate paths/bad lengths reject before hashing; exact and one-over descriptor bounds; a caller's subset and injected outside file both reject; actual library/harness parity and current prepared inputBinding stale refusals. These are proposed control requirements, not passing product results.
