# O1-PKG r1: effective package permissions

This prospective contract resolves O1's package binding against the additive inventory profile. The raw repository-file inventory remains the file authority, with packages and pendingDecisions inherited unchanged by value. The existing inventory verifier and its five-pin acceptance profile remain unchanged. No file inventory is authored here.

The separate package-policy.json is admitted only through this exact four-pin contract successor: selected record, subject manifest, independent ACCEPT-DESIGN-UNIT review and root substantive assent. Its selected parents are the exact unchanged O1 r2 law and raw v167 inventory. All inherited package rows retain their values and order, except appending opensip-operability to the dependencies of opensip-components, opensip-host and opensip-storage. One final package row names opensip-operability, crates/operability, rust-library, depending only on opensip-platform. The exact purpose and standing are recorded in the machine artifact. No other package, edge, feature or external dependency permission follows. Security and platform remain below operability; CLI reaches it through host. Host declares its edge in O1-a; storage/components declare theirs only in the owning wiring units.

The effective package policy is a build boundary input, not runtime trust, component authority, installation/profile selection or qualification. It does not change pending decisions, any raw package row or inventory inheritance. The raw inventory supplied to the checker must be the lock's current selected inventory; its packages and pendingDecisions must equal the policy's base inventory by value. Thus later additive file inventories can use this policy while any raw package change refuses it.

A separately reviewed tooling unit extends tools/check_package_edges.py and its existing test file. The optional --package-policy, --architecture and --lock options are all required together. Without them the existing raw-inventory behavior remains. With them the checker first validates the full selected design lock using verify_design.verify. It then verifies the requested policy's exact path, bytes and SHA256 as a selected contract candidate, loads the authenticated successor record to prove the policy's baseInventory and authority are its exact accepted parents, and verifies both parents' bytes. Caller-supplied paths or policy-shaped JSON alone confer no admission. The raw inventory must match the verifier's current selectedInventory pin. The checker derives the effective rows itself from the fixed one-row/three-edge profile and requires equality with effectivePackages; the fixed profile cannot extend unrelated permissions or reorder inherited rows/dependencies. No new root lock field, schema version or verifier exception is introduced.

Controls must reject missing verification inputs, unselected or changed policy bytes, wrong profile or parents, stale supplied inventory, modified raw packages/pending decisions, extra or reordered rows/edges, security/platform/CLI additions, changed new-package kind/path/only-platform dependency, and additional feature/external permissions. These controls must exercise the same derive/verify path used by the CLI. Actual locked/offline Cargo metadata against the O1-a candidate must pass the admitted boundary after independent tooling acceptance.

The three passageOverrides in successor.json apply only to raw O1 r2 lines 130, 149 and 558. They have no earlier published meaning, so they are overrides, not supersessions. Every other passage and accepted O1-D1 definition remains unchanged. O1-p and accepted S-OP-2 drafts stay closed. No product code is accepted by this design unit. Sequence: design acceptance/assent/bind; tooling ACCEPT-UNIT and separate code commit; O1-a whole-unit acceptance/code then additive file inventory and separate verified lock bind; only then S-OP-2-P, S-OP-2-R, S-OP-2b. Timing qualification remains owning M6 work. No pushes.
